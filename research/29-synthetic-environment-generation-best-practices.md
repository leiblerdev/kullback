## 1. Fidelity: validating a synthetic environment against the real system

### 1.1 Software digital twins

Digital twin literature is dominated by manufacturing, IoT, and networking, not general software systems. The closest hits found:

Tiny-Twin, a CPU-native digital twin for cellular networks, claims it "preserves protocol timing and end-to-end behavior" and demonstrates "high-fidelity experimentation" through empirical testing on commodity hardware (arXiv 2601.08217, 2026-01-13). An Open Wireless Digital Twin paper reports it "demonstrated the validity of the emulation framework, revealing its capability to replicate real-world communication dynamics with high fidelity" (arXiv 2503.12177, 2025-03-15, updated 2025-03-15). Both fidelity claims are self-reported by the paper's own authors against their own test setup, not validated by an independent auditor. Neither addresses a general-purpose transactional software system (a customer-support backend), only network protocol behavior. This is a genuine gap: there is no mature "software digital twin fidelity" literature to borrow from for a customer-support environment; the agent-benchmark field (section 1.3 below) has effectively built its own answer from scratch rather than importing one.

### 1.2 API mocking and service virtualization

WireMock supports two capture strategies: recording (live capture) and snapshotting (retroactive conversion of already-received requests into stubs). Its own documentation states default body matching uses content-type-based rules, and for JSON "equalToJson" matchers by default "ignore array order" and "extra elements," which reduces match precision unless tightened by hand. WireMock's docs do not state an accuracy guarantee for how closely a recorded stub reproduces the real API's future behavior; the tool is explicit that manual post-recording adjustment is often needed.

Mountebank calls itself "the only open source service virtualization tool that competes with the commercial offerings in terms of protocol diversity, capability, and performance," supporting HTTP/HTTPS, TCP, SMTP, LDAP, gRPC, WebSockets, GraphQL, SNMP, Telnet, SSH, and NetConf via "imposters" (github.com/bbyars/mountebank, accessed 2026-08-28). Its README makes no fidelity claim beyond protocol coverage. Notably, mountebank's own project website (mbtest.org) has been squatted by an unrelated gambling site, a signal of reduced project activity that is itself worth recording: two of the three classic open-source service-virtualization tools (Mountebank, and to a lesser extent Hoverfly, whose docs site required a redirect to find) show signs of light maintenance in 2026.

Hoverfly's current docs (docs.hoverfly.io) describe the product as letting users "create realistic simulations of the APIs your application depends on" and "export, share, edit and import API simulations," but the fetched pages contain no technical detail on matching precision or a stated accuracy metric; matching-strategy documentation exists but was not reachable in this pass.

The consistent finding across all three tools: none of the major open-source API-mocking projects publishes a quantitative fidelity metric for how well a recorded or virtualized service matches the real one over time. Fidelity is asserted qualitatively ("realistic," "high-fidelity") rather than measured. This matches what the agent-benchmark field has separately concluded and then built proper measurement for (section 1.3).

### 1.3 Sim-to-real gap in LLM agent environments

WAREX (Web Agent Reliability Evaluation on Existing Benchmarks, arXiv 2510.03285, 2025-09-28) is the most direct measurement found. It argues "current benchmarks measure agent performance in controlled environments, such as containers or stable networks, where websites behave deterministically," while real deployments face "instability from multiple sources: client-side, server-side issues or broader system failures," plus live attacks like cross-site scripting and unplanned site changes. Applied to WebArena, WebVoyager, and REAL, "introducing WAREX leads to significant drops in task success rates." The paper does not give an exact percentage in its abstract, but the direction and the named benchmarks matter: WebArena's own headline numbers, taken at face value, systematically overstate real-world reliability.

OSWorld and its successors took the opposite tack from WireMock-style mocking: rather than measuring or minimizing a sim-to-real gap, OSWorld runs agents inside "real computer environments" (Ubuntu, Windows, macOS) directly, sidestepping the fidelity question by not simulating at all (arXiv 2404.07972, 2024-04-11). OSWorld 2.0 (arXiv 2606.29537, 2026-06-28) extends this to "108 long-horizon workflows requiring median 1.6 hours of human effort," still on real systems. This is a deliberate design choice worth naming: where AppWorld and StableToolBench build faithful mocks, OSWorld and Windows Agent Arena (section 3) build on the real thing and accept the reproducibility cost that comes with it.

"Environment drift" as a named concept appears in three 2026 papers, none of which propose a metric for it, all of which propose an engineering workaround:
- Firefly (arXiv 2605.17558, 2026-05-17) builds "a retrieval-augmented simulator that caches all exploration results and replays them during training and evaluation, enabling fully offline and reproducible RL" specifically "to address environment drift in live APIs."
- SKILL.nb (arXiv 2606.08049, 2026-06-06) notes that "artifacts that succeed once may fail under environment drift, underspecified tasks, or changing task distributions, especially in web automation," and responds with gate-conditioned execution rather than measurement.
- An AIBOM (AI bill-of-materials) paper (arXiv 2603.10057, 2026-03-09) observes that conventional software bills of materials fail to "capture runtime behaviour, environment drift, or exploitability context," proposing runtime monitoring rather than a static fidelity score.

No 2025 or 2026 paper was found that proposes a direct, numeric "distance between this synthesized environment and the production system it imitates" metric for LLM agent environments. What exists instead is indirect: task-success-rate drops under adversarial or real-world conditions (WAREX), or response-similarity scores for individual tool mocks against real recorded traffic (MirrorAPI, section 3). This is a genuine open measurement problem, not a coverage gap on our part; see section 10.

## 2. State and database synthesis

### 2.1 Synthetic Data Vault (SDV)

SDV's HMASynthesizer "uses a recursive technique to model the parent-child relationships of a multi-table dataset," modeling each table with Gaussian Copulas while capturing cross-table correlations. It is explicitly scoped: "optimized for smaller datasets with around 5 tables and 1 level of depth (a parent and its child table)," with SDV's paid HSASynthesizer offered for larger graphs (docs.sdv.dev, accessed 2026-08-28). Referential integrity beyond simple foreign-key matching is handled by a separate "Constraint-Augmented Generation" (CAG) layer with predefined constraint types, including ForeignToPrimaryKeySubset ("use this constraint when you have a 1-to-many connection between tables, but only certain values are allowed to have connections," for example only accounts with type PREMIUM may have rows in a linked Perks table) and PrimaryToPrimaryKey. This is a meaningfully finer-grained model of referential integrity than plain FK type-checking: it captures conditional relationships that a real customer database's business rules would actually contain.

SDMetrics, SDV's companion evaluation library, decomposes fidelity into four scored components rather than one number: Column Shapes (marginal distribution similarity), Column Pair Trends (bivariate/correlation similarity), Cardinality (child-rows-per-parent distribution, multi-table only), and Intertable Trends (cross-table column relationships, multi-table only). An example report gave Column Shapes 85.61%, Column Pair Trends 71.97%, Cardinality 70.0%, Intertable Trends 68.49%, for an averaged Overall Score of 74.02%. SDV's own documentation is explicit that "a score of 80% means that the synthetic data is about 80% similar to the real data" and that "perfect 100% scores are unlikely and unnecessary; the synthesizers intentionally smooth and extrapolate patterns rather than memorizing exact data" (docs.sdv.dev/sdv/evaluation/data-quality). SDV also ships an Empirical Differential Privacy metric: it compares synthetic output from a synthesizer trained with and without a given row, scoring 1.0 when "a single row of training data has no impact on what the synthesizer learns" and 0.0 when it has "a massive impact." This is a practical, model-agnostic privacy check that does not require an a priori epsilon target.

### 2.2 Gretel, acquired by NVIDIA

gretel.ai now returns a 301 redirect to nvidia.com/en-us/use-cases/synthetic-data-generation-for-agentic-ai (confirmed by direct fetch, 2026-08-28). Gretel's product line has been folded into NVIDIA NeMo Data Designer and NeMo Safe Synthesizer. This is itself an industry-practice data point worth recording: one of the three best-known standalone commercial synthetic-data vendors no longer exists as an independent product, and its original technical documentation and blog content on relational synthesis fidelity is no longer reachable on the open web. NVIDIA's replacement pages emphasize "domain-specific datasets, seed data configuration, structured outputs, and LLM-based quality validation" but, at the pages reached, do not restate Gretel's original relational-synthesis fidelity claims or numbers.

### 2.3 Mostly AI

Mostly AI publishes head-to-head comparisons against SDV. A December 2025 post ("A Comparison of Synthetic Data Vault and MOSTLY AI, Part 3.2: Foreign Key Experiment, Revisited") tests both tools on the GLEIF dataset's relations table (two foreign key columns, START_ID and END_ID) and reports that "MOSTLY AI is able to not only generate Synthetic Data which passes referential integrity sense checks, but also which largely maintains the statistical patterns, relationships, and sequences found in the underlying dataset," while SDV "struggles to create realistic data that maintains the statistical properties of the underlying data," and that "the data generated by MOSTLY AI is far more statistically similar to the underlying data" (mostly.ai/blog). No numeric scores were retrievable from the fetched excerpt. This comparison is vendor-authored and self-serving by construction: it should be treated as a hypothesis to reproduce in-house, not as an independent finding. Both tools, per this same post, satisfy referential integrity in the strict sense; the claimed gap is purely on statistical similarity.

### 2.4 Tonic (Structural)

Tonic Structural's stated approach combines "patented database subsetting" with consistent masking and format-preserving transformations, with automated PII/PHI detection and schema-change tracking. Its direct claim: "Tonic Structural maintains primary and foreign key relationships across complex schemas, ensuring applications and tests behave as expected after data is de-identified" (tonic.ai/structural). Customer-reported outcomes cited on the same page: eBay reduced an 8-petabyte dataset to 1 gigabyte while preserving coherence; Patterson Companies cut test-data generation time from 2.5 hours to 35 to 45 minutes. These are efficiency and adoption numbers, not fidelity scores; Tonic does not publish a statistical-similarity metric comparable to SDMetrics in the pages reached.

### 2.5 Academic database synthesis with referential integrity

PrivLava (arXiv 2304.04545, VLDB-track, 2023) is the clearest academic answer to "synthesize a multi-relational database with foreign keys under a formal privacy guarantee." It models the data distribution with graphical models, using latent variables specifically to capture "the complex correlations induced by the foreign keys," and supports "arbitrary foreign key references that form a directed acyclic graph." Tested on census datasets and the TPC-H benchmark, it reports it "significantly outperforms its competitors in terms of the accuracy of aggregate queries processed on the synthetic data." The paper's abstract does not state its differential-privacy epsilon values; that level of detail was not reachable in this pass.

PrivBench (VLDB Endowment 18(2):413 to 425, arXiv 2405.01312, first published 2024-05-02, updated 2025-04-10) targets a different fidelity axis: instead of optimizing for downstream ML accuracy, it optimizes for benchmark publishing, where "fidelity in both data distribution and query runtime performance" matters, because a synthetic benchmark database is often used to test a query optimizer or reproduce a performance bug, not just to train a model. It uses sum-product networks and explicitly supports "multi-relation databases with complex reference relationships" under database-level differential privacy. This distinction (fidelity to a downstream ML task versus fidelity to a system's runtime behavior) maps directly onto the difference between "does our synthesized DB support a correct verifier" and "does our synthesized DB reproduce the real system's latency and query-plan characteristics," which is a distinction worth keeping in mind if our environments are ever used for anything beyond agent scoring.

### 2.6 How fidelity and privacy are measured, across the field

Statistical similarity is measured the same way almost everywhere: marginal (per-column) distribution match plus pairwise (bivariate/correlation) match, sometimes extended to multi-table cardinality and cross-table trend components (SDMetrics is the clearest published decomposition).

Privacy measurement is far more fragmented. A 2025 survey, "A Review of Privacy Metrics for Privacy-Preserving Synthetic Data Generation" (arXiv 2507.11324, updated 2025-07-22), catalogs 17 distinct metrics in two families. Simulation-based metrics attempt an attack directly: ZCAP and GCAP measure attribute-inference risk via exact or Hamming-distance matching, AIR uses Euclidean distance and reports an F1 score, CRP computes "the probability of a synthetic individual being the exact same as a real individual." Distance-based metrics analyze the datasets without simulating an attack: Distance to Closest Record (DCR) and its median variant, Nearest Neighbour Distance Ratio (NNDR), Nearest Neighbour Adversarial Accuracy (NNAA), a LightGBM-based Membership Inference Risk (MIR) classifier, an Authenticity score, and several others. The survey's central warning is that "these metrics embody the same assumptions as the privacy-preserving synthetic-data-generation mechanism they were made to assess," meaning a metric built on the same modeling assumption as the generator can give a falsely reassuring score. This argues for validating privacy with at least one metric from each family, not just one.

Membership inference against synthetic tabular and relational data is an active, adversarial research area, not a solved problem. A multi-table-specific attack, MT-MIA (arXiv 2602.07126, updated 2026-05-08), finds that "single-table MIAs that audit at an item level underestimate user-level privacy leakage" and instead targets "learned representations of user entities via Heterogeneous Graph Neural Networks," incorporating "all connected items for a user." This is directly relevant to any environment built from linked customer, order, and ticket tables: a per-row privacy check on the orders table alone can miss the fact that the combination of a customer's rows across tables re-identifies them. Separately, a study comparing two popular diffusion-based tabular generators found "TabDDPM is more vulnerable to these attacks" than "TabSyn," which "exhibits resilience" (arXiv 2510.16037, 2025-10-16); the exact numeric gap was not stated in the reachable abstract, but the qualitative finding stands: the choice of generator architecture changes privacy risk independent of any stated formal guarantee.

There is a live, unresolved disagreement in the field about whether differentially-private synthetic data actually delivers a better privacy-utility trade-off than classical anonymization. A 2024 paper, "Synthetic Data: Revisiting the Privacy-Utility Trade-off" (arXiv 2407.07926, 2024-07-09), directly rebuts an earlier claim that "synthetic data does not provide a better trade-off between privacy and utility than traditional anonymization techniques" and that the same earlier work had identified "a breach in the differential privacy guarantees provided by PATE-GAN and PrivBayes." The rebuttal argues the original privacy game "operated in a highly specialized and constrained environment" and "did not satisfy a crucial precondition concerning data distributions," and reports that in a "more general and unconstrained environment," synthetic data "indeed achieves a more favorable privacy-utility trade-off." Whichever side is right in general, the existence of a peer-reviewed dispute over whether specific, widely-used DP synthetic-data methods (PATE-GAN, PrivBayes) actually hold their stated guarantee is a strong argument against taking any single tool's differential-privacy label at face value without independent verification.

## 3. Tool implementation synthesis

Two design poles recur across the tool-synthesis literature, and they trade off fidelity against reproducibility in opposite directions.

### 3.1 Pole one: simulate the API, cache and fall back

Gorilla (arXiv 2305.15334, 2023-05-24) established the docs-grounded starting point: a fine-tuned LLaMA model generating API calls from HuggingFace, TorchHub, and TensorHub documentation, addressing LLMs' tendency to "hallucinate the wrong usage of an API call." Adding a document retriever "adapts well to updated documentation and substantially reduces hallucination issues," an early instance of the retrieval-as-drift-mitigation pattern that Firefly (section 1.3) later generalizes.

ToolLLM / ToolBench (arXiv 2307.16789, 2023-07-31, updated 2023-10-03) scaled this to "16,464 real-world RESTful APIs spanning 49 categories from RapidAPI Hub," with instructions generated by ChatGPT and solution paths found by depth-first search. Calling real third-party APIs at that scale is unstable by nature, which is exactly the problem StableToolBench was built to fix.

StableToolBench (arXiv 2403.07714, 2024-03-12, updated 2025-03-05) introduces "a virtual API server and stable evaluation system," where "the virtual API server contains a caching system and API simulators which are complementary to alleviate the change in API status," paired with a GPT-4 automatic evaluator computing "solvable pass and win rates" specifically "to eliminate the randomness during evaluation." This is the direct precedent for a cache-then-simulate fallback architecture applied to third-party tools.

MirrorAPI (arXiv 2503.20527, 2025-03-26) goes further: instead of a general-purpose LLM improvising a plausible API response, it trains specialized models via supervised fine-tuning and chain-of-thought on "a comprehensive dataset of request-response pairs from 7,000+ APIs" to act as accurate "mirrors" of the real service. On its own MirrorAPI-Bench, MirrorAPI's SFT and chain-of-thought variants score 8.6 to 9.0 (out of 10) on instruction-following and documentation-fidelity metrics, against GPT-4o's 4.6 to 5.2 and o1-preview's 4.1 to 6.1. On response similarity, MirrorAPI-SFT reaches cosine similarity of 88.7 to 94.2 on in-distribution requests versus GPT-4o's 63.1 on out-of-distribution successful requests, with a similar BLEU gap (74.2 to 89.9 for MirrorAPI versus 13.4 for GPT-4o on the comparable slice). Integrated back into StableToolBench, the paper states MirrorAPI "closely matches the real environment across all tool-using methods." This is the strongest published evidence found that a trained, docs-and-traffic-grounded simulator can approach the real API's behavior closely enough to be usable for stable evaluation, and it does so by measuring fidelity directly against held-out real request and response pairs, not just by checking that agent pass rates look stable.

Firefly (section 1.3, arXiv 2605.17558) inverts the usual order: rather than generating a task and hoping it is solvable against a simulated tool, it lets a strong LLM explore real MCP servers first along a graph-guided DAG, then synthesizes the task backward from the observed outcome, "guaranteeing label correctness by construction." It caches every exploration result specifically to counter live-API drift, yielding "5,144 verified tasks spanning 240 servers and 993 tools," with a 4B-parameter model trained on this data matching Claude Sonnet 4.6 on the held-out test set.

### 3.2 Pole two: use the real system, accept the instability

Windows Agent Arena (arXiv 2409.08264, 2024-09-12) deliberately runs agents "within a genuine Windows OS," with "150+ diverse Windows tasks," made tractable by parallelizing across Azure so "a full benchmark evaluation" completes "in as little as 20 minutes." Its own Navi agent scores 19.5% versus a 74.5% unassisted-human baseline, a large headroom gap that a mocked environment could not have produced with the same credibility, precisely because nothing about the environment is simulated. OSWorld and OSWorld 2.0 (section 1.3) make the identical choice for Linux, Windows, and macOS. AppWorld (arXiv 2407.18901, 2024-07-26) sits in between: it implements 9 real-feeling apps as executable code from scratch (457 APIs total, 60,000 lines of code for the engine, 40,000 for the benchmark harness, 750 tasks, roughly 100 fictitious users), evaluated with state-based unit tests; this is "apps as code," not mocking of a pre-existing third-party service, so it avoids the drift problem entirely at the cost of building the whole application from zero. Reported difficulty: GPT-4o solves about 49% of normal tasks and 30% of challenge tasks.

Apple's ToolSandbox (arXiv 2408.04682, 2024-08-08, updated 2025-04-16) is a third variant: fully simulated, but with explicit statefulness and "implicit state dependencies between tools," plus a built-in on-policy user simulator. Its hardest categories for current models are State Dependency, Canonicalization, and Insufficient Information, i.e. failures that come from cross-tool state tracking rather than single-call correctness, a useful reminder that tool-implementation fidelity is not just about matching individual call/response pairs but about whether the simulated state machine behaves consistently across a multi-turn session.

### 3.3 The throughline

Every credible pipeline in this section either (a) measures its simulator's fidelity against held-out real traffic directly, the way MirrorAPI does with BLEU and cosine similarity, or (b) sidesteps the fidelity question entirely by using the real system and absorbing the resulting instability and cost, the way OSWorld and Windows Agent Arena do. Nobody in this section validates a tool simulator purely by checking that downstream agent scores "look reasonable"; that check alone was shown in section 1 (WAREX) and elsewhere in R22 (the tool-calling validity audit) to be insufficient.

## 4. Difficulty, solvability, and discrimination between models

### 4.1 Item response theory for LLM benchmarks

"Lost in Benchmarks? Rethinking Large Language Model Benchmarking with Item Response Theory" (arXiv 2505.15055, 2025-05-21, updated) applies an enhanced IRT model (PSN-IRT) across 11 LLM benchmarks totalling 41,871 items, finding "significant and varied shortcomings in their measurement quality" and showing the method can be used to construct smaller, more informative benchmarks from the same item pool.

"Fluid Language Model Benchmarking" (arXiv 2509.11106, 2025-09-14) takes this further into adaptive testing: because "the relative value of benchmark items depends on an LM's capability level," it uses an IRT-based item model to dynamically select which items to administer next, rather than a fixed random sample. On MMLU, it reports "higher validity and less variance... with fifty times fewer items" than standard evaluation. That is a concrete, reproducible number for how much cheaper adaptive item selection can be than exhaustive evaluation, once the item pool has been IRT-calibrated once.

A related IRT application to grading itself (arXiv 2605.00238, 2026-04-30) jointly models "latent grader ability and response difficulty" for automatic short-answer grading, finding that "even models with similar overall performance differ substantially in how sharply their grading accuracy declines as response difficulty increases." This generalizes directly to LLM-as-judge verifiers: two judges with the same aggregate agreement rate can behave very differently on the hardest cases, which a single aggregate accuracy number hides.

### 4.2 Benchmark saturation

"When AI Benchmarks Plateau: A Systematic Study of Benchmark Saturation" (arXiv 2602.16763, ICML 2026, dated 2026-08-06 on arXiv) studied 60 language-model benchmarks and found "nearly half of our benchmarks exhibit saturation, with rates increasing with age," and, most actionably, that "resilience to saturation is impacted by expert-curation, not by public test data." In other words, whether a benchmark's test set is public or held out matters less for longevity than whether it was built with expert review. An earlier, broader study, "Mapping global dynamics of benchmark creation and saturation in artificial intelligence" (arXiv 2203.04592, first 2022, updated 2025-10-07), analyzed 3,765 benchmarks across computer vision and NLP and found "a large fraction of benchmarks quickly trended towards near-saturation," establishing this as a long-running, field-wide pattern rather than something specific to recent LLM benchmarks. A construction-time countermeasure, SMART filtering (arXiv 2410.20245, 2024-10-27, updated 2025-02-10), reduces a benchmark's item count by 48% on average "while improving model differentiation," a concrete demonstration that a smaller, better-curated item set can discriminate between models better than a larger, uncurated one.

### 4.3 Adaptive testing

TestAgent (arXiv 2506.03032, 2025-06-03) is an LLM-powered adaptive-assessment agent that "customizes assessments by selecting the fewest test questions," reporting equivalent or better results "with 20% fewer questions than state-of-the-art baselines" across psychological, educational, and lifestyle assessment domains (human assessment, not LLM benchmarking, but the mechanism, computerized adaptive testing applied via an LLM controller, is the same one Fluid Benchmarking applies to model evaluation).

### 4.4 What this means relative to the pass-rate-band norm

Every RL-environment-generation pipeline surveyed in R12 and R25 calibrates difficulty once, at generation time, to a single fixed pass-rate band (Envs-FORGE targets 0.5, EvoEnv targets 0.3, SPADE targets [0.4, 0.6], and so on) and never revisits that target as models improve. The IRT and adaptive-testing literature treats this as a category error: it argues the "right" difficulty is not a property of the task alone but of the task-model pair, and that a fixed band chosen once will look easy to next year's models without the pool being regenerated. The two literatures have not converged; they solve adjacent but different problems. Pass-rate-band filtering at generation time is a cheap, effective way to avoid degenerate (always-solved or never-solved) RL training tasks. IRT-style per-item difficulty and discrimination parameters, computed once from a pool of model responses, are a cheap, effective way to keep a fixed benchmark discriminating between models over time without regenerating it, and Fluid Benchmarking's fifty-times reduction suggests the added cost of doing this is small relative to the benefit.

## 5. Diversity and coverage of environments

### 5.1 The classic result and its actual number

The original Procgen paper (arXiv 1912.01588, 2019-12-03) is the source of "diversity of environments matters more than count" as a load-bearing empirical claim, not just a slogan. Its central finding: agents "strongly overfit to small training sets in almost all cases," and "to close the generalization gap, agents need access to as many as 10,000 levels." It also reports an unusual, counter-intuitive pattern: "past a certain threshold, training performance improves as the training set grows," which "runs counter to trends found in supervised learning, where training performance commonly decreases with the size of the training set." Despite finding that 10,000 levels are needed to fully close the gap, Procgen's own practical recommendation for benchmark use is 500 training levels, described as "near the region where generalization begins to take effect," a pragmatic compromise well short of what the paper's own experiment shows is ideal, chosen for cost reasons. This nuance matters: even the canonical source of "diversity beats count" settled for much less diversity than its own data argued for.

### 5.2 LLM agent training environments

AgentGym (arXiv 2406.04151, 2024-06-06) names diverse environments as the first of three necessary ingredients for a generalist LLM agent ("diverse environments for agent exploration and learning," alongside a broad trajectory set and a scalable self-evolution method), but the reachable abstract does not give a quantitative cross-environment transfer number the way Procgen does; the diversity claim here is qualitative and architectural rather than measured.

### 5.3 OpenEnv hub scale

No official growth statistics (total environment count over time, category breakdown, coverage goals) were published by OpenEnv's maintainers in any page reached during this research. A proxy count via the Hugging Face model hub's "openenv" tag shows approximately 172 tagged results as of 2026-08-28, spanning reinforcement-learning environments (for example EVChargeEnv, support-triage-env), text-generation agent checkpoints, and at least one text-classification model (email-triage-openenv). This is an informal proxy, not an official metric, and almost certainly both undercounts genuine environments (anything not tagged) and overcounts (trained checkpoints tagged alongside actual environment definitions). Consistent with R22's earlier finding, OpenEnv's stated "auto-validation" mechanism to "measure environment quality and contribution to model learning" remains described as planned rather than implemented.

### 5.4 Formal coverage metrics: a genuine gap

No paper was found that proposes a general, formal metric for "state-space coverage," "tool coverage," or "policy coverage" of a generated benchmark or environment set, distinct from the proxy counts already used inside specific pipelines covered in R12/R25 (EvoEnv's novelty-embedding cache with a seed-representation floor, ScaleEnv's minimum-20-visible-tools rule). The field currently substitutes raw counts (number of domains, tools, tables) for a measured coverage fraction. This appears to be an open measurement problem rather than something missed in this search; see section 10.

## 6. Contamination and leakage

### 6.1 General contamination detection

A 2025 survey, "A Survey on Data Contamination for Large Language Models" (arXiv 2502.14425, 2025-02-20), organizes detection into white-box, gray-box, and black-box methods, and remediation into data-updating, data-rewriting, and prevention-based approaches. A concrete detection method, CDD/TED (arXiv 2402.15938, 2024-02-24, updated 2024-05-31), detects contamination via output-distribution shape and reports it "reveals ChatGPT exhibits contamination on HumanEval," alongside average relative improvements of 21.8% to 30.2% over competing detectors, though the paper's reachable abstract does not give a direct contamination-rate percentage for HumanEval itself. A more recent quantification framework, DCR (arXiv 2507.11405, 2025-07-15, updated 2025-09-22), detects contamination across four granularity levels and reports "accuracy adjusted using the DCR Factor to within 4% average error" across benchmarks tested, the most concrete precision number found in this literature.

### 6.2 Differential privacy epsilon in practice

Most academic DP-synthesis papers reachable in this pass state that a mechanism provides "differential privacy" without committing to a specific, generally-recommended epsilon value; the field treats epsilon as domain- and risk-dependent rather than universal. One concrete data point was found: a behavioral-health synthetic-data study (arXiv 2507.02971, 2025-06-30) tested epsilon from 1 to 100 and concluded "synthetic data sets with epsilon = 5 preserve adequate predictive utility while significantly mitigating privacy risks." A separate comparison paper notes, in the opposite direction, that "low levels of privacy (epsilon >= 100) could help some models generalize" but offers essentially no meaningful privacy protection at that level. Taken together, this suggests single-digit epsilon is the closest thing to a field-tested "usable with real protection" number, though it comes from one health-data study and should not be treated as universal.

### 6.3 K-anonymity, and the disagreement with synthetic data

See section 2.6 above for the direct academic dispute (arXiv 2407.07926 versus the earlier work it rebuts) over whether differentially-private synthetic data actually beats classical k-anonymization on privacy-utility trade-off, and whether PATE-GAN and PrivBayes's DP guarantees hold under adversarial testing. This is unresolved as a general claim; specific implementations should be independently re-tested rather than trusted on the strength of either paper alone.

### 6.4 PII in production-trace-derived environments: an under-documented practice

No paper or vendor page was found that documents a specific PII-scrubbing or de-identification methodology for turning real customer-support transcripts into a training or benchmark environment, beyond OlaBench being noted elsewhere as using "de-identified" data without published method detail (as already flagged, unresolved, in R22). This is a real gap in the public literature: building an environment from real customer traces, as we do, sits in a part of the field that essentially nobody has published a methodology for, as distinct from the well-trodden ground of anonymizing a static tabular dataset (section 2.6's k-anonymity and DP literature, which assumes a table of rows, not a multi-turn transcript with free text, tool calls, and entity references threaded through it).

### 6.5 Multi-table membership inference, restated for our shape

Section 2.6's MT-MIA finding (arXiv 2602.07126) deserves restating here specifically as a contamination/leakage concern for our environments: because our tables are linked by customer ID across orders, tickets, and account records, a privacy check performed table-by-table will systematically underestimate how identifiable a real customer is once all their linked rows are considered together. Any PII audit of a trace-derived environment should be user-level, not row-level.

## 7. Maintenance: versioning, regrading, and deprecation

### 7.1 MLPerf as the mature outside precedent

MLPerf, the longest-running industry ML benchmark suite, tracks comparability per benchmark, not per suite-wide release. Its public compatibility table uses a simple code: "X: Change in benchmark. Submission results can be compared across rounds when there has been no change in the benchmark," and "N/A" when a benchmark is absent from a given round (github.com/mlcommons/policies, MLPerf_Compatibility_Table.adoc, accessed 2026-08-28). It states explicit incompatibilities directly, for example "Multistream v0.5 to v1.1 is not compatible with v2.0 and newer," and separately notes "performance metrics for inference and power submissions are not comparable" across certain versions. No formal deprecation timeline (a stated "this version stops being valid on date X") was found; instead, comparability is tracked as a live, per-artifact fact in a table that gets updated every round. This is the most mature precedent for benchmark maintenance found in this research, and it is notably more granular than anything published by an LLM-agent-benchmark vendor: MLPerf does not say "v3 supersedes v2," it says "this specific benchmark's v2 and v3 numbers are/are not comparable," benchmark by benchmark.

### 7.2 What LLM-agent-environment maintenance looks like today

No formal, MLPerf-style deprecation or comparability policy was found published by any LLM-agent-environment or benchmark vendor. The practice observed elsewhere (tau2/tau3's versioned releases with a strict versus lenient replay flag, already covered in R22) is closer to periodic full-suite re-releases with task rewrites than to MLPerf's granular per-benchmark compatibility tracking. Fluid Benchmarking's adaptive item-reweighting approach (section 4.1) is itself a maintenance technique worth naming explicitly: instead of replacing a saturated benchmark outright, it continuously re-weights which items matter as models improve, which is a fundamentally different maintenance model than "ship a new version." Combined with "When AI Benchmarks Plateau"'s finding that curation quality, not held-out status, predicts resilience to saturation (section 4.2), the two best pieces of evidence gathered here both point toward the same practice: invest in expert review and item-level calibration up front, rather than relying on secrecy or periodic full replacement to keep a benchmark discriminating.

### 7.3 Fleet AI and Matrices: a confirmed negative result

Multiple additional URLs and search terms were tried for both Fleet AI and Matrices beyond what R22 already attempted. Fleet's own site states only its mission ("Fleet creates simulated worlds and real-world challenges to better understand and shape the behavior of artificial intelligences") with no technical detail on environment construction or maintenance reachable in this pass; its `/notes` page lists at least one team-focused post but no technical methodology content. "Matrices" as searched resolved to an unrelated data-analysis product, not the AI evaluation company referenced in the task; the correct company's technical content, if any, was not locatable without a working WebSearch. Both should be treated as a confirmed negative result rather than an oversight: there is currently no reachable primary-source statement from either company about how they build or maintain environments.

Most of the companies named in the task (Sierra, Halluminate, Surge, Mercor, Scale, Mechanize, OpenEnv/Meta, Anthropic, OpenAI) already have detailed, quoted coverage in R22 and R25. Two new industry-practice data points did emerge from this research and belong here rather than under a specific company:

First, the Gretel-to-NVIDIA consolidation (section 2.2): a standalone synthetic-data vendor's product and technical content have been absorbed into a much larger platform (NeMo Data Designer and NeMo Safe Synthesizer), and its original public technical claims about relational-synthesis fidelity are no longer independently reachable. This is worth tracking as a general risk for anyone citing a vendor's fidelity claims: the vendor, and the page making the claim, may not persist.

Second, MLPerf's compatibility-table discipline (section 7.1) is the most concrete, mature "how to version a benchmark" practice found anywhere in this research, and no LLM-agent-environment vendor has published anything as granular. If we want a durable answer to "which Verdict was computed against which Environment version," MLPerf's per-artifact compatibility table, not a single suite-wide version number, is the closest existing template.

## 9. What this means for us

1. Model referential integrity as more than foreign-key type matching. SDV's CAG constraint types (ForeignToPrimaryKeySubset, PrimaryToPrimaryKey) capture conditional relationships, for example "only premium accounts have perk rows," that a real customer database's business rules actually contain. Source: docs.sdv.dev. Our compiled DB's constraint layer should support conditional as well as unconditional foreign-key relationships.

2. Measure synthesized-row fidelity against real trace-observed distributions using a decomposed score (marginal, pairwise, cardinality, cross-table trend), not a single blended number, because a single score hides which dimension is weak. Source: SDMetrics's four-part Data Quality report. Dissent: none found; every vendor and academic source that reports a fidelity number decomposes it into at least marginal and joint components.

3. Treat vendor-versus-vendor fidelity comparisons (Mostly AI's self-published comparison against SDV) as unverified until reproduced on our own data, since there is no independent, MLPerf-style benchmark for relational-synthesizer fidelity the way there is for hardware. Source: section 2.3; general absence of an independent auditor in this space.

4. Run privacy checks at the user level, not the row level, for any environment built from real customer traces linked by customer ID across tables. Source: MT-MIA (arXiv 2602.07126), which found single-table, item-level membership-inference audits underestimate user-level leakage in multi-table synthetic data. This directly matches our schema shape (customers linked to orders, tickets, accounts).

5. If differential privacy is used on synthesized customer data at all, document the chosen epsilon and the specific metric used to validate it. Single-digit epsilon (around 5) is the closest thing to a field-tested "usable utility with real protection" number found (arXiv 2507.02971), though it is domain-specific, not universal. Whichever metric is used to validate the epsilon, remember the field's own warning that privacy metrics "embody the same assumptions" as the generator they assess (arXiv 2507.11324); validate with at least one simulation-based and one distance-based metric, not just one.

6. For tool implementation, pick a design pole deliberately, per tool, rather than defaulting to one approach everywhere. Where a real customer API is stable, cheap, and safe to call from a sandbox, prefer record-and-replay against real traffic (the WireMock/Hoverfly pattern) over full LLM simulation, since no LLM-simulated tool has been shown to match real traffic as closely as literal replay of it. Where the real API is unstable, rate-limited, unavailable in a sandbox, or third-party, use a cache-first, LLM-fallback virtual server (the StableToolBench/MirrorAPI pattern), and validate the fallback's fidelity directly against held-out real request and response pairs using response-similarity metrics (MirrorAPI's BLEU and cosine similarity approach), not merely by checking that agent pass rates look stable across runs. Source: section 3. Dissent: OSWorld and Windows Agent Arena reject simulation entirely in favor of the real system, at the cost of reproducibility and speed; this is the right choice only when the real system can be sandboxed safely and run fast enough for the evaluation loop, which will rarely be true for a real customer's production backend.

7. Calibrate difficulty at generation time with a fixed pass-rate band (as R12 and R25 already recommend for training data), but additionally compute IRT-style per-item difficulty and discrimination parameters once a pool of model responses exists, so tasks can be re-weighted as models improve without full regeneration. Source: Fluid Benchmarking's "fifty times fewer items" result (arXiv 2509.11106) suggests this is cheap relative to the benefit. Dissent: every RL-environment pipeline surveyed in R12/R25 uses only a fixed pass-rate band and never revisits it; the two approaches solve different problems (avoiding degenerate training tasks versus keeping a fixed benchmark discriminating over time) and are complementary, not competing, for a system meant to do both training-data generation and longitudinal model comparison.

8. Invest in expert curation and a two-reviewer audit (already planned per R22's tau3 precedent) as the primary anti-saturation mechanism, more so than keeping verifier logic secret. Source: "When AI Benchmarks Plateau" (arXiv 2602.16763) found "resilience to saturation is impacted by expert-curation, not by public test data." This does not argue against hiding verifier logic (section 6 and R12's leakage-grep practice remain correct for preventing shortcut exploitation), only that curation quality, not secrecy, is what has been shown to extend a benchmark's useful life.

9. Do not assume more environments or more tool count automatically means better transfer; track a held-out transfer metric explicitly. Source: Procgen's own recommendation of 500 training levels was a cost-driven compromise well short of the 10,000 its own experiment showed was needed to fully close the generalization gap (arXiv 1912.01588). If we scale the number of customer domains or synthesized variants, we should measure transfer to a held-out domain directly rather than assuming that domain count alone is a proxy for coverage, since even the paper that established "diversity matters" did not scale diversity as far as its own data recommended.

10. Version environment artifacts the MLPerf way: track compatibility per sub-artifact (schema version, tool implementation version, policy-compilation version) in an explicit, updatable table, rather than a single suite-wide release number. Source: MLPerf's compatibility table (section 7.1), which flags incompatibility at the level of an individual benchmark, not the whole suite. This matches and reinforces what R25 already proposed for a `RunnerVersion` record; the addition here is to extend the same discipline to the Builder's own output artifacts, so a stored Verdict can state exactly which schema, tool, and policy sub-versions it was computed against, the way an MLPerf submission states exactly which benchmark version produced a given number.
