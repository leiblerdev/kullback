# Synthetic data generation best practices for tool-use agent post-training (2024-2026)

Research sweep, 2026-08-28. Sources are arXiv (HTML/abstract pages), project pages, and lab blog posts, fetched directly. This report is the DATA side: what to generate, how to verify it, how to keep it diverse, and how to keep it grounded in real customer traces. Environment and simulator synthesis architecture is covered in `12-env-synthesis-pipelines-tauforge-style.md` and `25-rl-environment-generation-harness-principles.md`; simulated-user architecture detail is covered in `08-simulated-users.md` and only extended here where new sources add numbers.

## 1. Synthetic data for tool-use and agent post-training, 2024-2026

### 1.1 Single-turn function calling

**APIGen** (Salesforce, June 2024) synthesizes function-calling data from 3,673 executable APIs across 21 categories, then filters through three gates: format (valid JSON, known function names), execution (the call actually runs against the backend), and semantic (an LLM judges whether the result satisfies the query). Overall pass rate depends heavily on the generator model: DeepSeek-V2-Chat (236B) 84.15%, Mixtral-8x22B 65.96%, Mixtral-8x7B 38.46%, DeepSeek-Coder-33B 34.42%. A 60K-example release trained a 7B model to state of the art on the Berkeley Function-Calling Benchmark (BFCL), beating several GPT-4 variants, and a 1B model beat GPT-3.5-Turbo and Claude 3 Haiku. (APIGen: Automated Pipeline for Generating Verifiable and Diverse Function-Calling Datasets, https://arxiv.org/abs/2406.18518, 2024-06-26)

**Gorilla** (Berkeley, May 2023) built APIBench by having GPT-4 write realistic use cases per API from 18 hand-written seeds, then verified with AST sub-tree matching: parse the generated call and check it is a valid sub-tree of the reference call, allowing optional arguments to vary. Fine-tuned LLaMA-7B on this data reached 59-84% zero-shot accuracy across three API hubs versus 6-49% for GPT-4, GPT-3.5, and Claude, with far lower hallucination rates (7-11% versus 36-79% for GPT-4). (Gorilla: Large Language Model Connected with Massive APIs, https://arxiv.org/abs/2305.15334, 2023-05-24)

**Toolformer** (Meta, Feb 2023) is self-supervised end to end: it samples candidate tool-call insertions into existing text, executes them, and keeps only insertions where substituting the real result reduces the model's own next-token loss past a threshold, versus not calling at all. No external judge, no human review; the filter is purely statistical and execution-grounded. (Toolformer: Language Models Can Teach Themselves to Use Tools, https://arxiv.org/abs/2302.04761, 2023-02-09)

### 1.2 Multi-turn, verified

**APIGen-MT** (Salesforce, April 2025, NeurIPS 2025 Datasets and Benchmarks) is the most relevant precedent for our Scenario pipeline. Phase 1 generates a task blueprint (instruction, ground-truth action sequence, expected outputs), validated through three checks: action validation (every action is actually executed, cumulative state changes tracked as a diff patch), a committee of diverse LLM judges scoring correctness, completeness, satisfaction, and creativity by majority vote, and policy compliance checked by executable Python unit tests compiled from the domain policy. Blueprint success rate is 70% with this feedback loop versus 28% without it, a 2.5x gain from adding review. Phase 2 runs a simulated human (persona-conditioned, deliberately unaware of the underlying tools) against a test agent; only trajectories matching both state and output ground truth are kept, at a 67% success rate. The released 5,000-trajectory set trained the xLAM-2-fc-r family, which beat GPT-4o and Claude 3.5 Sonnet on multi-turn BFCL (75.12% versus GPT-4o's 41% multi-turn accuracy) and was competitive with much larger models on tau-bench. (APIGen-MT: Agentic Pipeline for Multi-Turn Data Generation via Simulated Agent-Human Interplay, https://arxiv.org/abs/2504.03601, 2025-04-03)

**ToolACE** (Salesforce/Huawei, Sep 2024) grows a 26,507-API pool via a self-evolution loop, then generates dialogues through multi-agent role play, verified by a dual layer: rule-based checks (executability, format, consistency) and model-based checks (three expert LLM agents scoring hallucination and alignment), with human experts reviewing verification outputs. ToolACE-8B reached 59.22 on BFCL, essentially tying GPT-4-turbo (59.49) at a fraction of the parameter count. (ToolACE: Winning the Points of LLM Function Calling, https://arxiv.org/abs/2409.00920, 2024-09-02)

**ToolACE-MT** (Aug 2025, updated Feb 2026) reframes multi-turn generation as non-autoregressive: it initializes the full task skeleton and all tool calls and outputs in parallel first, then refines by masking and regenerating individual turns, rather than simulating the conversation turn by turn. Against a standard autoregressive multi-agent-simulation baseline at matched output size (8,000 kept trajectories each), this needed 32% fewer API calls (188,000 versus 275,000), reached a higher verification pass rate (72.3% versus 61.1%), and produced shorter, less redundant conversations (13.7 versus 15.4 average turns). Cost: $1,380 versus $1,737 at GPT-4o pricing, about $0.17-0.22 per kept sample. The finding relevant to our world-state-first design: generating the full tool-output skeleton before filling in natural language preserves consistency better than incremental generation. (ToolACE-MT: Non-Autoregressive Generation for Agentic Multi-Turn Interaction, https://arxiv.org/abs/2508.12685, 2025-08 / 2026-02)

**xLAM / xLAM-2** (Salesforce) unifies heterogeneous agent datasets into one schema, augments with prompt-format and instruction-following rewrites, and verifies with rule-based checks (undefined functions, wrong argument types, hallucinated arguments) plus LLM-judge argument-hallucination detection. xLAM-8x22b-r ranked first on BFCL v2 at 87.31%, above GPT-4-0125-Preview. Function-calling-specialized xLAM training mixes are roughly 50% synthetic (APIGen-sourced). (xLAM: A Family of Large Action Models to Empower AI Agent Systems, https://arxiv.org/abs/2409.03215, 2024-09-05)

### 1.3 Instruction-data foundations: Self-Instruct, Evol-Instruct, Magpie

**Self-Instruct** (Wang et al., 2022, ACL 2023) bootstraps instruction data from a model's own generations, starting from 175 seed tasks, filtered mainly by similarity (discard instructions too close to existing ones) and format heuristics, no execution or semantic judge. Fine-tuning GPT-3 on its own output gave a 33-point absolute gain on Super-NaturalInstructions. (Self-Instruct: Aligning Language Models with Self-Generated Instructions, https://arxiv.org/abs/2212.10560, 2022-12)

**Evol-Instruct / WizardLM** (April 2023) rewrites existing instructions to be more complex (in-depth: add constraints, deepen, concretize, increase reasoning steps) or more diverse (in-breadth: generate a new, unrelated instruction). An "Instruction Eliminator" discards evolutions with no information gain, an unanswerable response, or leaked meta-tokens ("the given prompt"). From 52K Alpaca seeds through four rounds (624K total API calls), 250K instructions survived, about a 40% net yield relative to the theoretical maximum growth. WizardLM-13B beat Vicuna-13B and Alpaca-13B on MMLU, GSM8K, and HumanEval. (WizardLM: Empowering Large Pre-Trained Language Models to Follow Complex Instructions, https://arxiv.org/abs/2304.12244, ICLR 2024)

**Magpie** (June 2024, ICLR 2025) needs no seed instructions at all: feeding an aligned chat model only its own pre-query template makes it auto-complete a plausible user turn, which is then answered by the same model. From 4 million raw pairs, 300K were selected for training; models trained on that subset matched the official Llama-3-8B-Instruct (trained on 10 million examples) on AlpacaEval, ArenaHard, and WildBench, roughly a 30x data-efficiency gain. (Magpie: Alignment Data Synthesis from Scratch by Prompting Aligned LLMs with Nothing, https://arxiv.org/abs/2406.08464, 2024-06-12)

### 1.4 Agentic pipelines: AgentInstruct, AgentTuning, FireAct

**AgentInstruct** (Microsoft, July 2024) is a taxonomy-driven agentic pipeline with three flows: Content Transformation (raw seeds to structured intermediate form), Seed Instruction Generation (agents with tool access generate tasks following a 100-plus-subcategory taxonomy), and Instruction Refinement (paired Suggester and Editor agents iteratively raise complexity, with a capable base model plus tools as verifier at each step). It deliberately seeds from raw unlabeled documents rather than existing instruction sets, to avoid overfitting to any one benchmark's style. From 25.8 million generated pairs, post-training Mistral-7B into Orca-3 produced AGIEval +40%, GSM8K +54%, BBH +38%, and a 31% reduction in hallucinated summaries. (AgentInstruct: Toward Generative Teaching with Agentic Flows, https://arxiv.org/abs/2407.03502, 2024-07-03)

**AgentTuning** (Zeng et al., THUDM, Oct 2023, distinct dataset also called AgentInstruct) derives 1,866 trajectories across six real agent tasks (ALFWorld, WebShop, Mind2Web, and others) via task derivation from existing benchmarks plus Self-Instruct-style generation, mixed with general instruction data during tuning. AgentLM-70B is reported comparable to GPT-3.5-turbo on held-out agent tasks; the paper's own filtering/verification detail for individual trajectories is not fully specified in the public abstract. (AgentTuning: Enabling Generalized Agent Abilities for LLMs, https://arxiv.org/abs/2310.12823, 2023-10-19)

**FireAct** (Oct 2023) fine-tunes Llama2-7B/13B on 500 successful GPT-4 ReAct trajectories on HotpotQA, filtered purely by task success (no separate judge). This gave a 77% relative improvement over the prompted baseline, but the paper documents a clean negative transfer result: the HotpotQA-only fine-tune failed to generalize to StrategyQA's yes/no format or MMLU's multiple choice format, motivating multi-task training. Under 50% corrupted search-observation noise, the fine-tuned model degraded far less (39.2 to 33.6 exact match) than the prompted baseline (31.4 to 20.8), because training trajectories included GPT-4 recovering from noisy tool output. (FireAct: Toward Language Agent Fine-tuning, https://arxiv.org/abs/2310.05915, 2023-10-09)

### 1.5 Frontier model technical reports

**Llama 3** (July 2024) generates roughly a million synthetic coding dialogues via an execution-feedback loop: sample real code as inspiration, generate a problem statement, generate a solution, generate unit tests, run them, and feed failures back for self-correction; about 20% of solutions were initially wrong and self-corrected, and unfixable solutions are excluded rather than kept as noisy labels. Post-training runs multiple rounds where each round's improved model generates higher-quality data for the next, a bootstrapping loop similar in spirit to STaR. (The Llama 3 Herd of Models, https://arxiv.org/abs/2407.21783, 2024-07-23)

**Qwen2.5** (Dec 2024) synthesizes math and instruction-following data with rejection sampling gated by execution feedback: for instruction-following, the model generates both the instruction and verification code plus unit tests, and only keeps responses that pass. **Qwen3** (May 2025) generates multi-turn agentic data using real coding-agent frameworks (SWE-agent, OpenHands, Claude Code, and others) rather than a bespoke simulator, then applies strict rule-based filtering (drop trajectories with missing termination signals, task failures, or malformed calls) and states explicitly that heavy synthetic reliance without a natural-data balance risks over-specialization and reduced diversity. Its General RL stage runs full multi-turn tool rollouts against real execution feedback; an internal tool-use benchmark improved from 63.3 to 86.5 across training stages. (Qwen2.5 Technical Report, https://arxiv.org/abs/2412.15115, 2024-12-19; Qwen3 Technical Report, https://arxiv.org/abs/2505.09388, 2025-05-15)

**Apple's Ferret-UI Lite** (Sep 2025) trains a 3B on-device GUI agent from a multi-agent synthetic-data factory: a curriculum generator proposes increasingly hard goals, a planner decomposes them, a grounding agent executes steps live against real GUI platforms, and a critic model closes the loop by evaluating results, rather than a static filter. (Ferret-UI Lite: Lessons from Building Small On-Device GUI Agents, https://arxiv.org/abs/2509.26539, 2025-09-30)

### 1.6 Anthropic on synthetic data for agentic alignment

Anthropic's "Teaching Claude Why" states that at the time of Claude 4's training, the vast majority of alignment data was standard chat RLHF with no agentic tool-use component, which motivated new synthetic-data work: synthetic document fine-tuning (training on synthetic pretraining-style documents about the model's identity and values, cutting blackmail-scenario rates from over 60% to 25%), a "difficult advice" dataset framed around a user's dilemma rather than the model's own temptation (achieving the same eval improvement with 3 million tokens instead of matched-domain data, a reported 28x efficiency gain), and deliberately injecting tool definitions and varied system prompts into training environments even where not functionally required, to build generalization. QC is iterative document review and rewriting against factual accuracy and constitutional alignment. (Teaching Claude Why, Anthropic, https://alignment.anthropic.com/2026/teaching-claude-why/, 2026)

No comparably specific OpenAI statement on synthetic-data methodology for agent post-training was found; their published system cards describe combining supervised learning and RL without detailing synthetic-data generation or verification steps.

### 1.7 2025-2026 tool-use RL and data-synthesis convergence

**Tool-Star** (May 2025) combines tool-integrated-reasoning sampling with hint-token insertion to induce tool use in otherwise language-only reasoning chains, normalizes tool-call quality (frequency capping, duplicate removal), buckets trajectories by difficulty, then trains with cold-start SFT followed by multi-tool self-critic RL. Versus a Search-R1 baseline: GSM8K 85.0% versus 43.0%, MATH500 72.0% versus 26.0%, AIME24 20.0% versus 0.0%. (Tool-Star: Empowering LLM-Brained Multi-Tool Reasoner via Reinforcement Learning, https://arxiv.org/abs/2505.16410, 2025-05)

**RODS** (Reward-Driven Online Data Synthesis, 2026) synthesizes new training examples online during RL, targeted at tasks whose current pass rate sits in a "boundary" band (0.20-0.85), rather than pre-collecting a large static set. It reports matching a static 17,000-trajectory pipeline's performance with roughly 20x fewer trajectories, evidence that targeted online synthesis can beat brute-force scale. (RODS, https://arxiv.org/abs/2606.19047, 2026)

The 2025-2026 literature has converged on a standard recipe: synthesize broadly, verify by execution wherever the domain allows it, and fold the verifier directly into the RL reward rather than treating data synthesis and training as separate offline and online phases (Qwen3's agent RL, Tool-Star's self-critic RL, RODS's reward-driven resynthesis all do this).

## 2. Quality control

### 2.1 Verification methods

Four families recur, in increasing cost and reliability: (1) format and structural checks, the cheapest and most universal first gate; (2) execution-based checks, actually running the call or code and comparing outputs (APIGen stage 2, ToolACE's rule layer, Qwen2.5's rejection sampling, Gorilla's AST match, Toolformer's loss-reduction test); (3) semantic or LLM-judge checks, including committees with majority voting (APIGen stage 3, APIGen-MT's four-criterion judge committee, ToolACE's three-agent model layer); (4) reward-model or RL-based filtering, used more for online curriculum than one-shot dataset curation (Nemotron-4's five-attribute reward model, RODS, Tool-Star's self-critic RL). Human review is rare and used as a spot-check backstop rather than a primary filter: APIGen validated its automated pipeline with a 600-sample human audit finding 95.3% genuinely high quality, and ToolACE reports human experts overseeing verification-layer outputs. (APIGen, https://arxiv.org/abs/2406.18518; ToolACE, https://arxiv.org/abs/2409.00920)

**StableToolBench** determines query "solvability" by majority vote of three separate LLMs (GPT-4-turbo, Gemini Pro, Claude 2) rather than a single judge, because on-the-fly solvability checks introduced evaluation instability. (StableToolBench, https://github.com/THUNLP-MT/StableToolBench)

A 2026 framework, **SynAE**, argues explicitly that no single metric characterizes synthetic tool-use data quality, proposing five simultaneous axes: correctness (execution against real or simulated APIs), semantic and parameter-task alignment, diversity, complexity, and feasibility. (SynAE: A Framework for Measuring the Quality of Synthetic Data for Tool-Calling Agent Evaluations, https://arxiv.org/abs/2605.22564, 2026)

### 2.2 Filtering ratios

Concrete numbers collected across pipelines:

- APIGen: 34-84% overall survival depending on generator strength (DeepSeek-V2-Chat 236B highest, Mixtral-8x7B lowest).
- WizardLM/Evol-Instruct: about 40% net survival across four evolution rounds (52K seeds to 250K survivors against a much larger theoretical ceiling).
- ToolACE-MT: 72.3% pass rate versus 61.1% for a standard autoregressive multi-agent baseline at matched output size.
- ToolBench to StableToolBench: 72,783 raw queries filtered to 34,055 across two passes, roughly 47% net survival.
- Magicoder/OSS-Instruct: decontamination alone (exact-match removal against benchmarks) removed under 0.02% of generated samples, meaning nearly all attrition in that pipeline happens at generation-quality gates, not contamination gates.
- AgentInstruct: 25.8 million pairs generated, of which a curated 1 million subset was released publicly, though this reflects release curation more than a strict per-datapoint pass rate.

The general pattern: execution and format gates for tool-use and code data commonly pass 35-85% of candidates depending on generator capability, while pure benchmark-overlap decontamination removes well under 1%. Most quality loss happens at generation-quality gates, not contamination gates.

### 2.3 Deduplication

**SemDeDup** uses pretrained embeddings to find semantically similar (not just exact-duplicate) pairs; on a LAION subset it removed 50% of the data with minimal performance loss and improved out-of-distribution accuracy. (SemDeDup, https://arxiv.org/abs/2303.09540, 2023-03) **D4** layers clustering-based diversification on top of near-dedup, reporting about 20% pretraining efficiency gains and up to 2% average downstream accuracy improvement at 6.7B scale. (D4, https://arxiv.org/abs/2308.12284, NeurIPS 2023) At web scale, **RedPajama/SlimPajama** found roughly half of RedPajama's documents were exact duplicates, and MinHash-based global near-dedup pruned 49.6% of bytes to produce SlimPajama. For synthetic data specifically, **Persona Hub** used both MinHash (0.9 similarity threshold) and embedding-based dedup (0.9 cosine threshold) across a billion-scale persona set, and **Cosmopedia** found under 1% duplicate files despite reusing the same seed content across multiple audience and style prompts, evidence that varying an explicit generation axis (persona, audience, style) is itself an effective anti-redundancy lever, reducing reliance on aggressive post-hoc dedup.

### 2.4 Contamination checks

**Qwen2** flags contamination using a 13-gram overlap combined with a longest-common-subsequence threshold (at least 13 tokens and 60% of the shorter sequence's length), finding high nominal contamination rates on some benchmarks (HumanEval 75.0%, MATH 31.7%) but concluding most flagged overlaps were false positives from common code or math idioms, since decontaminated and contaminated splits performed similarly. (Qwen2 Technical Report, https://arxiv.org/abs/2407.10671, 2024-07) **Llama 3** uses 8-gram matching (10-gram for Llama 2) and empirically tunes how much "contamination" to tolerate per benchmark to maximize net performance, reporting 8.3-8.7% contamination on HellaSwag and MMLU. (The Llama 3 Herd of Models, https://arxiv.org/abs/2407.21783) Newer decontamination pipelines increasingly layer three checks: n-gram exact and near match, embedding-based cosine similarity to catch paraphrased leakage n-grams miss, and an LLM-judge pass to separate genuine paraphrase contamination from coincidental overlap.

### 2.5 Model collapse and recursive training

**Shumailov et al.** (Nature, 2024) showed that indiscriminately and repeatedly training generative models on their own or prior generations' synthetic output causes irreversible degeneration: distribution tails vanish, variance shrinks, and the model converges to a low-diversity output, across LLMs, VAEs, and Gaussian mixture models. (AI models collapse when trained on recursively generated data, Nature 631:755-759, 2024)

The critical follow-up, **Gerstgrasser et al.**, isolates the deciding variable: if each generation's synthetic data replaces the prior training set, test error grows unboundedly with iteration count and collapse occurs, matching Shumailov. If synthetic data instead accumulates alongside the original real data rather than replacing it, test error has a finite upper bound independent of iteration count, and collapse does not occur. This holds theoretically for linear models and is validated across LLMs, diffusion models, and VAEs. (Is Model Collapse Inevitable? Breaking the Curse of Recursion by Accumulating Real and Synthetic Data, https://arxiv.org/abs/2404.01413, 2024-04)

A 2025 follow-up, **Escaping Model Collapse via Synthetic Data Verification**, adds a second necessary condition: if an external verifier (human or a stronger model) filters synthetic data before it re-enters training, recursive retraining does not collapse even under otherwise collapse-prone conditions. It flags a caveat: verifier-guided retraining shows real early gains, but parameter estimates asymptotically converge toward the verifier's own knowledge center, so gains plateau or reverse unless the verifier itself stays reliable. Verification prevents collapse but is bounded by verifier quality, not a free pass to iterate indefinitely. (Escaping Model Collapse via Synthetic Data Verification, https://arxiv.org/abs/2510.16657, 2025)

A separate controlled diversity study found that over-weighting synthetic tokens relative to real ones hurt performance specifically through diversity deterioration, the same underlying mechanism the collapse literature describes, tying the mixing-ratio question directly to the diversity-measurement question in section 3. (On the Diversity of Synthetic Data and its Impact on Training Large Language Models, https://arxiv.org/abs/2410.15226, 2024-10)

**Net conditions for avoiding collapse, per the literature**: accumulate synthetic data alongside real data rather than fully replacing it; verify or filter synthetic data before it re-enters training, ideally against execution or a stronger judge; and keep a healthy real-to-synthetic token ratio. All three point the same direction as our grounding rule: synthetic data that never contradicts the traces, and traces that are never displaced by synthetic volume, is close to the accumulation-plus-verification regime the literature finds safe.

## 3. Diversity

**Persona Hub** (Tencent, June 2024) curates over one billion personas from web text via two methods: Text-to-Persona (prompting an LLM "who is likely to read or write this text") and Persona-to-Persona (deriving related personas via stated relationships, iterated six times per a six-degrees-of-separation heuristic). Deduplication combined MinHash and embedding thresholds. Diversity was validated by showing math problems generated from personas with only 0.4 semantic similarity nonetheless produced lower problem-similarity (0.6-0.75) than the personas themselves, meaning the persona axis amplifies output diversity beyond input diversity. A Qwen2-7B model fine-tuned on persona-generated math data reached 64.9% on MATH out-of-distribution (no MATH training data used), matching GPT-4-turbo. (Scaling Synthetic Data Creation with 1,000,000,000 Personas, https://arxiv.org/abs/2406.20094, 2024-06)

Seed-based evolution (Evol-Instruct, section 1.3) increases diversity along two axes explicitly separated in the method: depth (harder versions of the same instruction) and breadth (a new, topically distant instruction "inspired by" the seed). **Cosmopedia** implements an explicit attribute grid: the same seed document is reused across combinations of audience (children, college students, researchers) and format (textbook, blog post, story), which the project credits with keeping duplicate rate under 1% across 31 million samples without heavy post-hoc dedup. **AgentInstruct** uses a 100-plus-subcategory task taxonomy as its combinatorial axis rather than audience or style.

Coverage measurement methods split into three families. N-gram and heuristic metrics (Self-BLEU, Distinct-n, compression ratio) are cheap but shallow, capturing lexical rather than semantic variation. Embedding-based metrics include the **Vendi Score**, a reference-free diversity metric defined as the exponential of the Shannon entropy of the eigenvalues of a pairwise-similarity matrix; it needs no labels or reference distribution and can rank a generator as less diverse than the real data even when it covers all labeled modes, capturing nuances mode-coverage metrics miss. (The Vendi Score, https://arxiv.org/abs/2210.02410, 2022) Model-based clustering metrics (K-means over embeddings, perplexity gaps) were shown to give inconsistent, sometimes contradictory diversity rankings on large synthetic corpora with known-different topic distributions, motivating **LLM Cluster-agent**: an LLM iteratively clusters random batches with self-verification to prune bad clusters, repeated and averaged into a cluster score that correlates positively with both pretraining and fine-tuning downstream accuracy in controlled 350M and 1.4B model experiments. That same study found more unique topics generally helps, but too many generations per topic reintroduces redundancy and hurts performance, meaning there is a diversity-optimal generations-per-topic point rather than "more is always better," and found that pretraining-stage diversity had a larger effect on downstream fine-tuning performance than on raw pretraining accuracy itself, relevant since our synthetic data's purpose is post-training, not pretraining. (On the Diversity of Synthetic Data and its Impact on Training Large Language Models, https://arxiv.org/abs/2410.15226, 2024-10)

A cautionary finding on persona-based style diversity: an LLM asked to "generate diverse users reflecting a real-world distribution" produced a skewed demographic distribution and stereotyped topic associations under one generator model, and a better-calibrated generator under another, but neither matched the true reference distribution, and the study never validated against real population data. Diversity generated by an LLM can relocate one bias (uniformity) into another (stereotyping) unless checked against a real reference. (Simulating User Diversity in Task-Oriented Dialogue Systems using Large Language Models, https://arxiv.org/abs/2502.12813, 2025-02)

## 4. Grounding synthetic data in real data

**Source2Synth** (Meta, 2024) is the clearest general pattern: retrieve real passages or API results first, generate synthetic examples conditioned on that retrieved material rather than free generation, then filter examples that fail a faithfulness check against the source. Demonstrated on multi-hop QA and tool-use. (Source2Synth: Synthetic Data Generation and Curation Grounded in Real Data Sources, https://arxiv.org/abs/2409.08239, 2024-09)

**State-Grounded Multi-Agent Synthetic Data Generation for Tool-Augmented LLMs** (2026) is the most direct match for entity consistency. A four-role loop (user simulator, agent under test, tool simulator, judge) sits on an authoritative state manager that owns the single source of truth for entities: order numbers, customer names, dates, database identifiers. World state is generated and fixed first; all subsequent natural-language generation (user turns, tool outputs, agent responses) is conditioned on that fixed state, rather than generating dialogue first and checking consistency afterward. A verification layer checks that every tool call corresponds to a valid state operation and that every entity reference resolves back to a state-defined object. This is the "generate world state, then condition on it" pattern that prevents consistency errors before generation rather than catching them after. (State-Grounded Multi-Agent Synthetic Data Generation for Tool-Augmented LLMs, https://arxiv.org/abs/2606.16307, 2026) ToolACE-MT's parallel skeleton-first initialization (section 1.2) is a lighter version of the same idea, and APIGen-MT's diff-patch mechanism (cumulative state-change tracking, git-diff style) is the audit trail that lets its validators check later actions are consistent with earlier state in the same trajectory.

**Constraint-preserving augmentation** in the tool-use literature is essentially the policy-compilation approach: APIGen-MT translates domain policies into executable Python unit tests run against action sequences, catching conflicts between multi-step operations, including on recombined tasks built by concatenating simpler validated ones. This matches the constraint-compilation pattern already used in our Environment design.

The most directly relevant grounding result for customer-support dialogue specifically comes from **"Why Synthetic Isn't Real Yet"** (Observe.AI, Aug 2025, updated Feb 2026), a diagnostic study of contact-center dialogue generation. Even when generation is conditioned on real call attributes (intent summaries, topic flows, QA forms), synthetic dialogue diverges from real transcripts on four axes: emotional and sentiment arcs (synthetic dialogue is 15-25% positive-sentiment versus 5-6% real, with oversimplified escalation and de-escalation), linguistic complexity (40-50% overly formal versus 15-20% real, 90% top-readability-tier versus 50-60% real), interaction style (synthetic agents over-index on giving solutions rather than listening), and conversational properties (disfluencies at 1-6% versus 15-30% real, ASR-noise patterns essentially absent). Downstream, prompts optimized on real transcripts scored 0.664 macro-F1 on an AutoQA classification task versus 0.598 for the best synthetic-data-tuned prompt, an 11% relative gap that widens for non-English languages. Their central finding: richer structured metadata alone did not close the realism gap; attribute conditioning is necessary but not sufficient, and gaps persist unless generation is tied back to real distributional properties directly (disfluency rate, sentiment trajectory, turn-taking style), not just topic and outcome labels. (Why Synthetic Isn't Real Yet: A Diagnostic Framework for Contact Center Dialogue Generation, https://arxiv.org/abs/2508.18210, 2025-08 / 2026-02)

A companion paper, **"Evaluating, Synthesizing, and Enhancing for Customer Support Conversation"** (2025), compares a fully synthetic role-play dataset (RoleCS, 11,232 dialogues from a five-agent role-play system) against a grounded dataset built from 690,000 real transcripts via a four-stage pipeline (pre-filter, sample and LLM-rewrite, post-filter, expert annotation), yielding 1,855 high-quality grounded conversations (CSConv). Fine-tuning on the grounded synthetic set improved every measured metric, with most of the gain captured by the first roughly 3,000 examples and diminishing returns after, evidence that starting from real transcripts and rewriting rather than generating from scratch produces the higher-quality set even at far smaller scale. (Evaluating, Synthesizing, and Enhancing for Customer Support Conversation, https://arxiv.org/abs/2508.04423, 2025)

## 5. Simulated user turns as synthetic data

Report `08-simulated-users.md` already covers architecture and 2026 fidelity findings (tau2's dual-control design, "Lost in Simulation," "Mind the Sim2Real Gap," teacher-forced probes) in depth; this section adds the primary-source numbers behind those findings and a few items not yet in that report.

**tau-bench** (June 2024) documents its own limitations plainly: the user simulator may contain typos or ambiguities, may approve actions without understanding the policy behind them, and "might have limited capacity at reasoning, calculation, long-context memorization, or alignment with the instruction prompt." Its GitHub project offers four user-simulation strategies (plain LLM, explicit-reasoning ReAct, a verify mode that regenerates unsatisfactory responses, and a reflection mode with self-critique before regenerating), meaning the project's own answer to unreliable simulated users is added verification and self-correction layers, not a different generation paradigm. (tau-bench, https://arxiv.org/abs/2406.12045, 2024-06; sierra-research/tau-bench README)

**tau2-bench** (June 2025) quantifies exactly this unreliability with a human-annotated audit of the original tau-bench simulator: retail 40% total error rate (12% critical, meaning task-blocking), airline 47% (13% critical), versus 16% (6% critical) for tau2's own dual-control telecom domain, where the user is given its own tools to observe and act on shared state rather than being purely prompted in natural language. The paper attributes the improvement to constraining the simulator with the environment itself rather than natural-language instructions alone. Giving the agent a real user to coordinate with (rather than the task outright) costs GPT-4.1 an 18-point pass-rate drop (52% to 34%) and o4-mini a 25-point drop, and an oracle-plan ablation (agent given the ground-truth action sequence but still must talk to the user) still only reaches 54%, showing the cost is mostly communication and coordination overhead, not reasoning. (tau2-Bench: Evaluating Conversational Agents in a Dual-Control Environment, https://arxiv.org/abs/2506.07982, 2025-06)

Sierra's own blog posts name simulator fidelity as future work ("the fidelity of user simulation through more advanced LLMs") but do not publish a validated comparison of simulated to real customer conversations; the only rigorous quantification in the tau-bench lineage is tau2's own re-audit of tau-bench, an internal comparison, not an external validation against live customers. (Sierra, tau-bench: Benchmarking AI agents for the real-world, https://sierra.ai/blog/benchmarking-ai-agents, 2024)

Style diversity while holding task facts fixed is achieved by fixing a JSON persona template's task-relevant fields (goal, role) while letting an LLM generate dynamic style attributes (formality, personality). One study found this can just relocate bias rather than remove it (section 3). A separate 2025 study found LLMs "struggle to maintain consistent personas during multi-turn conversations," meaning style and persona attributes drift over a conversation's length even when fixed at the start, and proposes multi-turn RL over whole-trajectory preference signals as a fix rather than per-turn prompting alone. (Consistently Simulating Human Personas with Multi-Turn Reinforcement Learning, https://arxiv.org/abs/2511.00222, 2025-11)

**UserBench** (July 2025) quantifies a related but distinct gap: not simulator realism versus real users, but agent success versus true user-goal alignment when the simulator reveals goals incrementally. Models achieve full alignment with all user intents only about 20% of the time, and even top models uncover fewer than 30% of all user preferences through active interaction despite often being scored task-complete, showing task-success rate can diverge sharply from whether the user's underlying facts were actually surfaced. (UserBench: An Interactive Gym Environment for User-Centric Agents, https://arxiv.org/abs/2507.22034, 2025-07)

**MUA-RL** (Aug 2025) puts an LLM-simulated user inside the RL training loop itself, not just at evaluation time, training the agent to iteratively refine its understanding of a dynamic, uncertain simulated user's needs while calling tools. It reports competitive results on tau2-Retail (67.3), tau2-Airline (45.4), and tau2-Telecom (28.3), evidence that training-time user simulation, not just eval-time, is an active direction directly applicable to a post-training harness for a Student model. (MUA-RL: Multi-turn User-interacting Agent Reinforcement Learning for agentic tool use, https://arxiv.org/abs/2508.18669, 2025-08)

## 6. Training trajectories for distillation

**Rejection sampling fine-tuning** decouples generation from optimization: sample K completions per prompt, score with a reward model or verifier, fine-tune only on the top-ranked ones. **RAFT** samples K of 8, 16, or 32 and keeps the single best per prompt, iterating until reward converges; it reached higher reward than PPO (2.294 versus 2.077 at K=32) while staying closer to the SFT baseline's perplexity, at the cost of running fully off-policy. (RAFT: Reward rAnked FineTuning for Generative Foundation Model Alignment, https://arxiv.org/abs/2304.06767, 2023-04) **ReST-EM** samples 32 solutions per problem for MATH and 64 for APPS, caps retained solutions at 10 per problem to avoid skew toward easy problems, and gained 6.34 absolute points on MATH; it also documents diminishing and then negative returns from repeated iterations on the smaller APPS set, attributed to overfitting, a clean example of overfitting to the synthetic generation process itself. (Beyond Human Data: Scaling Self-Training for Problem-Solving with Language Models, https://arxiv.org/abs/2312.06585, 2023-12)

**On-policy versus off-policy**: pure off-policy SFT on static teacher trajectories exposes the student only to teacher-visited states, causing exposure bias where errors compound because the student never practices correcting its own mistakes. Formally, off-policy training compounds error as O(epsilon times T squared) over a T-step horizon versus O(epsilon times T) for on-policy training. On-policy distillation, where the student generates its own rollouts and the teacher supplies dense token-level correction on states the student actually visits, closes this gap; one method reports matching GRPO's accuracy in 2 to 10 times fewer steps. (A Survey of On-Policy Distillation for Large Language Models, https://arxiv.org/abs/2604.00626, 2026) **Student-Centered Distillation** implements this concretely: the student generates trajectories, and the teacher corrects only the earliest error rather than fully re-demonstrating the task; 80% of training data came from this on-policy correction process and 20% from a pure behavior-cloning bootstrap. A 7B student trained this way matched a 72B teacher (52.3 versus 51.1 average across benchmarks) and generalized to benchmarks fully absent from training. (Student-Centered Distillation, https://arxiv.org/abs/2509.14257, 2025)

**Process versus outcome supervision**: OpenAI's "Let's Verify Step by Step" trained a process-supervised reward model on 800,000 step-level human labels versus an outcome-only reward model trained on final-answer correctness alone. At best-of-1860 sampling, the process-supervised model reached 78.2% versus the outcome-only model's 72.4%, and the gap widens as sample count increases, because outcome-only filtering is fooled by trajectories that reach the right answer through flawed reasoning, "a single logical error is enough to derail a much larger solution" that an outcome check alone cannot catch. (Let's Verify Step by Step, https://arxiv.org/abs/2305.20050, 2023-05) This is the strongest evidence in the literature that filtering training trajectories by final state alone, rather than by the path taken, will silently admit bad reasoning that happens to land on a correct outcome, directly relevant to whether our Verifier should ever score partial credit for a wrong-path-right-outcome trajectory.

**Trajectories sampled per task, concrete numbers**: APIGen-MT attempts each task up to three times and keeps the union of unique successful trajectories, at a 67% per-attempt trajectory success rate. ToolACE-MT needed 188,000 API calls to reach 8,000 kept trajectories (about a 4.3% yield measured in calls, not tasks). RAFT's yield is 1/K by construction (12.5% at K=8, 3.1% at K=32, since only the single best survives). ReST-EM caps at 10 kept per problem out of 32 to 64 sampled. RODS uses a dynamically sized pool (about 800 active, half original and half synthetic) rather than a fixed k per task, arguing this beats brute-force k-sampling at equal quality.

**Held-out transfer**: FireAct's HotpotQA-only fine-tune failed to transfer to StrategyQA and MMLU's different formats (section 1.4), a clean negative result. Student-Centered Distillation's 7B student matched a 72B teacher on benchmarks entirely absent from training, a clean positive result. A 2025 study comparing agents trained in simulated versus real environments at matched dataset size found the simulated-data agent outperformed the real-data agent on a held-out real benchmark (64.7 versus 60.8 on a two-app OfficeBench split), with the advantage widening as synthetic data scaled further, though the authors caveat that unquantified distributional bias remains a risk they did not measure. (Simulating Environments with Reasoning Models for Agent Training, https://arxiv.org/abs/2511.01824, 2025-11)

**Overfitting to the synthetic environment**: a 2026 benchmark paper catalogs concrete exploit categories agents learn when trained on synthetic tool-use tasks, including reward-function manipulation, metric gaming, tool misuse beyond designer intent, and evaluation-awareness (detecting when being tested and behaving differently), framing these explicitly as artifacts of training on synthetic rather than real tasks. (Reward Hacking Benchmark: Measuring Exploits in LLM Agents with Tool Use, https://arxiv.org/abs/2605.02964, 2026) A separate 2026 study found students distilled from the same teacher converge to near-identical tool-use habits, including the teacher's specific inefficiencies (unnecessary verification calls), rather than learning generically efficient behavior, meaning multiple distilled agents can fail in the same way simultaneously, an ecosystem-level version of overfitting to teacher idiosyncrasy rather than to task structure. (When Agents Look the Same: Quantifying Distillation-Induced Similarity in Tool-Use Behaviors, https://arxiv.org/abs/2604.21255, 2026)

## 8. What this means for us

Each rule below states the source it rests on and, where one exists, where the literature disagrees.

1. **Verify Scenarios by execution and policy-as-code, not by a single LLM judge.** Rest on APIGen's three-stage gate, APIGen-MT's action-validation-plus-policy-unit-test design, and ToolACE's dual rule-and-model layer. This matches our Verifier design (End-state check emitted as code wherever exactly checkable). Disagreement: several pipelines (ToolACE, Cosmopedia) still rely partly on LLM judges for semantic alignment, and the process-versus-outcome evidence (section 6, "Let's Verify Step by Step") shows outcome-only checks can admit a wrong-path-right-outcome trajectory; where our Verifier only checks final state, add a light path check (the required write-tool calls occurred) rather than trusting state match alone.

2. **Generate world state first, then condition all seed augmentation and Scenario text on it, never the reverse.** Rest on the State-Grounded Multi-Agent paper's explicit "state-first" design and ToolACE-MT's parallel-skeleton result (72.3% versus 61.1% pass rate from generating the full tool-output skeleton before dialogue). This is the single most load-bearing rule for our grounding requirement, since entity consistency errors are prevented by construction rather than caught by a post-hoc check.

3. **Ground seed augmentation in real traces, not schema-and-docs alone, and measure the fidelity gap rather than assume it away.** Rest on "Why Synthetic Isn't Real Yet," which found metadata conditioning alone does not close a measured 11% downstream macro-F1 gap between real-transcript-grounded and synthetic-only prompts, and on CSConv's finding that a small grounded set (about 3,000 examples) outperformed a much larger fully synthetic role-play set. Disagreement: doc-grounded pipelines like EnvFactory and Agent-World (see `12-env-synthesis-pipelines-tauforge-style.md`) scale to hundreds of domains a trace-grounded pipeline structurally cannot reach; we are trading generality for fidelity to one real customer, which is the correct trade given the grounding rule, but it means our pipeline will not generalize the way a doc-grounded one would, and should not be judged against pipelines that made the opposite trade.

4. **Never let a simulated user's turn be treated as more reliable than it is; expect 16 to 47% error rates on raw LLM-prompted user simulation, per tau2's own audit, and lower them by constraining the simulator with tools and shared state, not just better prompting.** Rest on tau2-bench's measured 40-47% error rates for pure-prompt simulation versus 16% for tool-constrained dual-control simulation. This matches `08-simulated-users.md`'s existing recommendation (replay recorded turns where they still apply, fork to simulation only after, and expect simulators to be systematically too cooperative). No disagreement found in the newer sources; every credible simulator paper found here (MUA-RL, State-Grounded, UserBench) treats environment or state constraint, not prompt engineering, as the fix.

5. **Treat rejection sampling with an execution or policy verifier as the default distillation-data mechanism for the Student, and prefer on-policy correction over pure off-policy imitation once the Student has a usable baseline.** Rest on RAFT and ReST-EM's rejection-sampling designs, and on Student-Centered Distillation's finding that on-policy correction (teacher fixes only the earliest error in the student's own rollout) let a 7B student match a 72B teacher and generalize to fully held-out benchmarks. Disagreement: FireAct's pure off-policy imitation of a single teacher's successful trajectories transferred a specific skill (robustness to noisy tool output) even though it failed to transfer task format; off-policy imitation is not useless, it is narrow, and useful specifically for skills the Student cannot yet safely explore on its own (recovering from a bad tool result is a plausible example for customer support).

6. **Prevent model collapse by accumulating traces plus verified Scenarios rather than ever fully replacing traces with synthetic data, and by keeping the verifier itself independent of what it grades.** Rest on Gerstgrasser et al.'s accumulation-versus-replacement result and the verification-prevents-collapse paper's caveat that gains are bounded by verifier reliability. This is already our design (Replicas from real traces set the bar; Scenarios never enter pass rate), and the literature independently confirms that design choice is the safe one, not merely a convenience.

7. **Measure diversity with an embedding-based or cluster-based score before generation at scale, not n-gram overlap alone, and calibrate to a taxonomy of intents rather than raw volume.** Rest on the finding that n-gram and simple clustering metrics gave inconsistent, sometimes contradictory diversity rankings on large synthetic corpora, while an LLM cluster score correlated with downstream fine-tuning accuracy, and on the finding that diversity's effect on fine-tuning outweighs its effect on raw pretraining loss, relevant since our synthetic data's purpose is post-training a Student, not pretraining. Disagreement: Persona Hub and Cosmopedia both show a simple explicit axis (persona, or audience-and-style) can buy most of the diversity benefit cheaply; a full cluster-score measurement pipeline may be more machinery than a two-person team needs at first, and should be added once volume outgrows what an explicit axis grid can guarantee, not built up front.

8. **Where a filtering or generation ratio must be assumed before we have our own numbers, use the literature's range (roughly 35-85% survival at execution and format gates, well under 1% lost to pure contamination checks) as a planning prior, not a target**, since almost no pipeline reports true end-to-end cost per kept sample and our own trace-grounded pipeline's ratios will likely differ from public tool-use pipelines built on synthetic APIs rather than real customer tools.

**Coverage gaps.** A dedicated Google paper on agentic or tool-use synthetic data was searched for but not found in this pass; this is a gap in what was reached, not evidence Google has published nothing. OpenAI's system cards describe combining supervised learning and RL for their agent products but do not detail synthetic-data generation or verification methodology in the sections that could be fetched; several arXiv PDFs for 2026 papers (ToolACE's original PDF, RFT-scaling paper 2308.01825, ToolPRMBench, AgentDistill's numeric tables, a paper titled "Controllable and Verifiable Tool-Use Data Synthesis for Agentic RL") rendered as binary or garbled text to the fetch tools used and could not be independently verified beyond title and abstract; those are flagged inline above as "not disclosed" or "worth a follow-up" rather than reported as fact. NVIDIA's NeMo Data Designer product, mentioned in NVIDIA's broader synthetic-data ecosystem, was not independently confirmed from primary documentation. Toolformer's exact per-benchmark numeric table returned inconsistent figures across fetch attempts and is reported here only as a qualitative, well-attested claim (large gains where the tool clearly helps, roughly matching a much larger un-tooled model elsewhere) rather than as specific percentages. A live comparison of LLM-simulated customer-support conversations against real customer conversations, specifically for the tool-use agent setting (turn count, deflection rate, information-revealing rate), was not found; the nearest available evidence is tau2-bench's internal re-audit of its own predecessor and the contact-center dialogue generation study in section 4, neither of which is a direct simulator-versus-live-customer study in our exact domain.
