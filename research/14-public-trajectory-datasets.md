## Part 1: Source-by-source

### 1. tau2-bench (Sierra), and tau-bench v1
- URL: https://github.com/sierra-research/tau2-bench, paper https://arxiv.org/abs/2506.07982, v1 paper https://arxiv.org/abs/2406.12045
- Format (from `src/tau2/data_model/simulation.py` and `message.py`): a `SimulationRun` with `id`, `task_id`, `timestamp`, `start_time`, `end_time`, `duration`, `termination_reason`, `agent_cost`, `user_cost`, `agent_usage`, `reward_info`, `messages` (half-duplex) or `ticks` (full-duplex/voice), `trial`, `seed`. Messages: `UserMessage`/`AssistantMessage` carry `role`, `content`, `tool_calls`, `cost`, `usage`, `timestamp`, `generation_time_seconds`, `turn_idx`; `ToolCall` has `id`, `name`, `arguments`, `requestor` ("user" or "assistant", because in the telecom dual-control domain the simulated user also has tools); `ToolMessage` has `id`, `role: "tool"`, `content`, `requestor`, `error: bool`, `turn_idx`, `timestamp`. `RewardInfo` has `reward`, `db_check`, `env_assertions`, `action_checks`, `nl_assertions`, `communicate_checks`, `reward_basis`, `reward_breakdown`. `TerminationReason` enum: `USER_STOP`, `AGENT_STOP`, `MAX_STEPS`, `TIMEOUT`, `TOO_MANY_ERRORS`, `AGENT_ERROR`, `USER_ERROR`, `INFRASTRUCTURE_ERROR`, `CONTEXT_WINDOW_EXCEEDED`, `UNEXPECTED_ERROR`. (https://raw.githubusercontent.com/sierra-research/tau2-bench/main/src/tau2/data_model/simulation.py, https://raw.githubusercontent.com/sierra-research/tau2-bench/main/src/tau2/data_model/message.py)
- Example step shape: user message ("I want to cancel order X") -> assistant `tool_calls:[{name:"get_order_details", arguments:{order_id}}]` -> `ToolMessage{content: <json>, error:false}` -> assistant text asking for confirmation -> user "yes" -> assistant `cancel_order` call -> ToolMessage -> final assistant message. Sierra results are written to `data/simulations/` and browsed with `tau2 view` (https://github.com/sierra-research/tau2-bench).
- Stats: retail 115 tasks, airline 50, telecom 114 (2,285 generated programmatically); GPT-4.1 pass^1 74% retail, 56% airline, 34% telecom; dropping the user (no-user mode) vs dual control changes success by 18 points (GPT-4.1) and 25 points (o4-mini); user-simulator error rates 16% telecom (6% critical), 40% retail (12% critical), 47% airline (13% critical). (https://arxiv.org/html/2506.07982). v1: grading compares end-of-conversation DB state to annotated goal state, pass^8 under 25% in retail for GPT-4o (https://arxiv.org/abs/2406.12045).
- Third-party dumps of real tau2 trajectories exist, e.g. `AgentSuite/tau2-bench-trajectories` (30 models x 278 tasks, one JSONL per model; fields `model_path`, `user_model_path`, `benchmark_name`, `task_name`, `sampling_params`, `user_sampling_params`, `messages`, `eval_result`, `meta`) at https://huggingface.co/datasets/AgentSuite/tau2-bench-trajectories.
- Grader sees: final DB state hash + required action set + NL assertions on the dialogue + "communicate" checks (was info X told to the user).

### 2. AppWorld
- URL: https://github.com/StonyBrookNLP/appworld, paper https://arxiv.org/abs/2407.18901
- Format: the agent acts by executing Python (`world.execute(code)`) in a stateful IPython shell that calls `apis.{app}.{api}(**params)`. Outputs per task are written to `experiments/outputs/{experiment}/{task_id}/` with `checkpoints/` (state snapshots via `save_state`/`load_state`), `dbs/` (per-app JSONL deltas vs base DB, e.g. `spotify.jsonl`), `evaluation/report.md`, `logs/environment_io.md` (every execute call I/O, parseable with `parse_environment_io_log`) and `logs/api_calls.jsonl` (every API/HTTP call, parseable with `parse_api_calls_log`), `version/`. Task object exposes `instruction`, `supervisor` (name, email, phone), `app_descriptions`, `api_docs` (YAML/function-calling/OpenAPI), and on train/dev `ground_truth` (solution code, tests, `num_apis`, `num_apps`, `num_solution_code_lines`). (https://raw.githubusercontent.com/StonyBrookNLP/appworld/main/README.md)
- Example step: instruction "pay my share of the roommates' electricity bill via Venmo" -> code `apis.venmo.show_transactions(...)` -> observation is the Python stdout/JSON -> next code cell.
- Stats: 9 apps, 457 APIs, 100+ DB tables, ~100 simulated people, 750 tasks; GPT-4o ~49% normal / 30% challenge. Evaluation is state-based unit tests with collateral-damage checks; tests are typed `no_op_pass` / `no_op_fail`, metrics TGC and SGC. (https://arxiv.org/abs/2407.18901, https://github.com/StonyBrookNLP/appworld)
- Grader sees: full DB state diff (this is the only source here that ships pre-state, post-state deltas, and the API call log side by side).

### 3. SWE-agent `.traj` files, SWE-smith trajectories
- URL: https://swe-agent.com/latest/usage/trajectories/, https://huggingface.co/datasets/SWE-bench/SWE-smith-trajectories, paper https://arxiv.org/abs/2504.21798
- Format (.traj): top-level `trajectory` (list of steps), `history` (messages shown to the LM), `info` (`exit_status`, `submission` = patch, `model_stats`), `replay_config`. Per step: `action`, `observation`, `response` (raw LM output), `thought`, `state` (env vars captured after execution), `execution_time`, `query` (exact messages sent at that step). (https://swe-agent.com/latest/usage/trajectories/)
- HF release: `messages`, `instance_id`, `resolved`, `model`, `traj_id`, `patch`; 76,002 rows, generated with SWE-agent + Claude 3.7 Sonnet; the system prompt is "You are a helpful assistant that can interact with a computer to solve tasks"; 5,017 of them were used to fine-tune SWE-agent-LM-32B (40.2% SWE-bench Verified). (https://huggingface.co/datasets/SWE-bench/SWE-smith-trajectories)
- Example step: thought "Let me look at the failing test" -> `action: "str_replace_editor view /repo/tests/test_x.py"` -> observation: file contents with line numbers -> next step edits.
- Stats published: 50k instances from 128 repos (https://arxiv.org/abs/2504.21798). Per-step timing (`execution_time`) is present, which is rare.
- Grader sees: the `submission` patch applied in a fresh container, then test results (`eval_logs` in the nebius mirror).

### 4. SWE-Gym / OpenHands trajectories
- URL: https://huggingface.co/datasets/SWE-Gym/OpenHands-SFT-Trajectories, https://huggingface.co/datasets/SWE-Gym/OpenHands-Sampled-Trajectories, paper https://arxiv.org/html/2412.21139; sibling sets `OpenHands-Verifier-Trajectories`, `MoatlessTools-Sampled-Trajectories` (https://huggingface.co/api/datasets?author=SWE-Gym)
- Format: `instance_id`, `run_id` (encodes model, max iterations and temperature, e.g. `gpt-4o-2024-08-06_maxiter_30_N_v2.1-no-hint-train-t04-run_1`), `resolved: bool`, `messages` (7 to 101 entries), `tools` (3 tool definitions: bash execution etc.), `test_result` dict with `empty_generation`, `error_eval`, `failed_apply_patch`, `test_timeout`. SFT set: 491 successful rows, 13 to 101 messages each. (cards above)
- Example step: assistant tool call `execute_bash{"command":"grep -rn 'def parse' src/"}` -> tool message with stdout -> assistant `str_replace_editor` edit -> tool message "The file ... has been edited".
- Stats: 491 successful vs 5,557 unsuccessful sampled trajectories; successful avg 39.9 messages (about 19 agent turns), 18,578 tokens (2,560 to 81,245); unsuccessful avg 39.2 messages, 17,218 tokens but range up to 167,834 (failures include very long spirals). (https://arxiv.org/html/2412.21139)
- Also: `nebius/SWE-agent-trajectories` mirrors the same shape: `instance_id`, `model_name`, `target` (success bool), `trajectory` (steps with `role`, `text`, `system_prompt`, `mask`, `cutoff_date`), `exit_status`, `generated_patch`, `eval_logs` (https://datasets-server.huggingface.co/rows?dataset=nebius/SWE-agent-trajectories&config=default&split=train&offset=0&length=1).
- Grader sees: patch + test run only. Note the OpenHands runtime event model (id/timestamp/source/cause) could not be fetched (404 on both org names), so I do not describe it.

### 5. Terminal-Bench 2.0 / Harbor (ATIF)
- URL: https://harborframework.com/docs/agents/trajectory-format, https://github.com/laude-institute/harbor
- Format: Agent Trajectory Interchange Format, `schema_version: "ATIF-v1.7"`. Top level: `session_id` (run-scoped), `agent{name, version, model_name, tool_definitions, extra}`, `steps[]`, `final_metrics`, `trajectory_id`, `subagent_trajectories`. Step: `step_id` (from 1), `timestamp` (ISO 8601), `source` ("user"/"agent"/"system"), `model_name`, `message`, `reasoning_content`, `tool_calls[{tool_call_id, function_name, arguments, extra}]`, `observation{results[{source_call_id, content, subagent_trajectory_ref}]}`, `metrics{prompt_tokens, completion_tokens, cached_tokens, cost_usd, logprobs, completion_token_ids}`, `llm_call_count`. This is the only format in this survey with an explicit sub-agent reference and an explicit mapping from observation to the tool call that produced it. (https://harborframework.com/docs/agents/trajectory-format)
- Public dumps: `yoonholee/terminalbench-trajectories`: 52,104 trajectories, 89 tasks, 109 agent/model combos, per-step `src`, `msg`, `tools:[{fn, cmd}]`, `obs` (truncated to 5,000 chars); median 21 steps, mean 47.1 steps, 39.6% pass overall (https://huggingface.co/datasets/yoonholee/terminalbench-trajectories). `harithoppil/terminal-bench-2-trajectories`: 3,723 trajectories with `task_name`, `model`, `agent`, `prompt`, `response` (whole trajectory as one text blob, up to 223k chars), `reward`, `elapsed_seconds` (https://huggingface.co/datasets/harithoppil/terminal-bench-2-trajectories).
- Example step: `{"src":"agent","msg":"Checking file structure...","tools":[{"fn":"Bash","cmd":"ls -la"}],"obs":"total 42\ndrwxr-xr-x ..."}` (yoonholee card).
- Grader sees: container state via a test script run after the agent finishes (reward 0/1); no per-step state.

### 6. AgentDojo
- URL: https://github.com/ethz-spylab/agentdojo, paper https://arxiv.org/abs/2406.13352, results explorer https://agentdojo.spylab.ai/results/
- Format (`benchmark.py` `TaskResults`): `suite_name`, `pipeline_name`, `user_task_id`, `injection_task_id`, `attack_type`, `injections: dict[str,str]`, `messages: list[ChatMessage]`, `error`, `utility: bool`, `security: bool`, `duration: float`. Messages (`types.py`): `ChatUserMessage{role, content[]}`, `ChatAssistantMessage{role, content[] (text/thinking/redacted_thinking blocks), tool_calls[]}`, `ChatToolResultMessage{role:"tool", tool_call, content[], tool_call_id, error: str|None}`, `ChatSystemMessage`. (https://raw.githubusercontent.com/ethz-spylab/agentdojo/main/src/agentdojo/benchmark.py, https://raw.githubusercontent.com/ethz-spylab/agentdojo/main/src/agentdojo/types.py)
- Example step: user "Summarize my unread emails" -> assistant `get_unread_emails()` -> tool result containing an injected instruction -> assistant (if hijacked) `send_money(...)`.
- Stats: 97 user tasks, 629 security test cases; utility and security are booleans computed by suite-level environment state checks; on context-length or server errors utility=False, security=True; for DoS attacks security is the inverse of utility. (https://arxiv.org/abs/2406.13352, benchmark.py)
- Grader sees: post-episode environment object (in-memory Pydantic state) compared by task-specific check functions, plus the message list. Full runtime traces are browsable in Invariant Explorer (https://agentdojo.spylab.ai/results/).

### 7. WebArena (and VisualWebArena, same harness)
- URL: https://github.com/web-arena-x/webarena, paper https://arxiv.org/abs/2307.13854
- Format (`run.py`): a `trajectory` list alternating `state_info{observation, info}` and `action{action_type, element_id, raw_prediction ...}`; rendered `<result_dir>/<id>.html` with optional screenshots; optional Playwright trace `traces/{task_id}.zip`; `action_history` strings; score 0/1. Observation is the accessibility tree (`obs["text"]`) or a screenshot. Actions are ID-based (`click [id]`). (https://raw.githubusercontent.com/web-arena-x/webarena/main/run.py, https://raw.githubusercontent.com/web-arena-x/webarena/main/README.md)
- Example step: obs = accessibility tree of the shop admin page -> LM raw output "Let me open orders. ```click [1234]```" -> action `{action_type: click, element_id: "1234"}` -> new accessibility tree.
- Stats: 812 tasks; evaluators `string_match`, `url_match`, `program_html`; environment must be reset after the full run because tasks mutate the sites (README).
- Grader sees: final answer string, final URL, or a program that reads the live page/DB. Not the intermediate page states unless the Playwright trace was enabled.

### 8. ToolBench / StableToolBench
- URL: https://github.com/OpenBMB/ToolBench, https://github.com/THUNLP-MT/StableToolBench
- Format: instance = `query`, `query_id`, `api_list` (category, tool, api), `answer_generation` (DFSDT tree), `train_messages` (ChatML-ish dialogue), `answer` with intermediate steps, `final_answer`, `function_calls` with params and results. (https://raw.githubusercontent.com/OpenBMB/ToolBench/master/README.md)
- Example: query -> plan -> pick `weather.get_forecast` -> observe JSON -> refine -> "Finish" with final answer.
- Stats: 3,451 tools, 16,464 APIs, 126,486 instances, 469,585 real API calls at annotation time, 4.0 reasoning traces per instance on average. StableToolBench replaced flaky live RapidAPI calls with a cache + GPT-4-simulated fallback and a trained "MirrorAPI" that mimics 7k+ APIs; metrics SoPR, SoWR, FAC. (both READMEs)
- Lesson for a replica builder: the original benchmark decayed because tool outputs were live and non-deterministic; the fix was to record and replay responses.

### 9. xLAM function-calling-60k and APIGen-MT-5k (Salesforce)
- URL: https://huggingface.co/datasets/Salesforce/xlam-function-calling-60k, https://huggingface.co/datasets/Salesforce/APIGen-MT-5k, paper https://arxiv.org/abs/2504.03601
- Format 60k: `query`, `tools[]` (name, description, typed parameters), `answers[]` (tool name + arguments); single-shot, may contain several calls in one answer; 3,673 executable APIs over 21 categories; verified by format check, execution, semantic check; >95% human-judged correct.
- Format APIGen-MT: ShareGPT-style `conversations[{from: human|function_call|observation|gpt, value}]`, `system` (domain policy), `tools`; 5,000 rows, up to 56 turns, retail and airline domains from tau-bench; produced by blueprint generation then simulated human/agent interplay; 99% of 200 sampled trajectories judged correct.
- Example step (per card): `{"from":"human","value":"..."}`, `{"from":"function_call","value":"{\"name\":..., \"arguments\":...}"}`, `{"from":"observation","value":"<tool output>"}`, `{"from":"gpt","value":"..."}`. (The datasets-server row fetch returned HTTP 500, so I could not quote a real row.)
- Grader sees: nothing at inference; these are SFT data. The generation pipeline verified with state checks and policy checks before including a row.

### 10. Toucan-1.5M (MCP-grounded)
- URL: https://huggingface.co/datasets/Agent-Ark/Toucan-1.5M, paper https://arxiv.org/html/2510.01179
- Format: `uuid`, `messages` (chat with tool declarations), `question`, `target_tools`, `question_quality_assessment`, `response_quality_assessment`, `metadata` (original MCP server info, annotations). Subsets: single-turn-original, irrelevant (server-shuffled, tool should not be called), single-turn-diversify, multi-turn. Tool responses come from real MCP execution, not simulation.
- Stats: 1.5M trajectories, 495 servers (filtered from 2,800), 2,000+ tools; 567,262 multi-turn instances (about 37%); curated SFT subset 119.3K = 28.3K original + 40K irrelevance + 15.8K diversified + 35.2K multi-turn; rule-based filter drops rows with connection failures, missing tool calls, response failures, or file-system paths; covers single, parallel and sequential tool calls, and most tasks expose more tools than the ones needed. (paper HTML)
- Example step: system (tool JSON schemas) -> user question -> assistant parallel calls to two MCP tools -> two tool results -> assistant answer. (Row fetch returned HTTP 500; structure taken from the card.)

### 11. Nemotron-Agentic-v1 (NVIDIA)
- URL: https://huggingface.co/datasets/nvidia/Nemotron-Agentic-v1
- Format: `uuid`, `messages` (role, content, tool_calls, reasoning), `tools`, `reasoning`, `license`, `used_in`. Two splits (config `default`): `interactive_agent` 19,028 rows (user, agent, and a simulated tool-execution environment) and `tool_calling` 316,094 rows; total 335,122, ~5.5 GB JSONL. Tool outputs are synthetic, produced by a simulated "tool execution environment"; an LLM judge filtered trajectories. (https://datasets-server.huggingface.co/splits?dataset=nvidia/Nemotron-Agentic-v1, card)
- Example step (from first-rows): user "I need to cancel order ORD1058" -> assistant `cancel_order{"order_id":"ORD1058","reason":"user_request"}` -> tool `{"refund_amount":18.99,"loyalty_impact":0}` -> assistant "Order cancelled. $18.99 refund processed." with reasoning "User explicitly requested cancellation within 15-minute window, qualifying for full refund per policy." Policy text enforces "one tool call at a time" and "explicit verbal confirmation" for order changes. (https://datasets-server.huggingface.co/first-rows?dataset=nvidia/Nemotron-Agentic-v1&config=default&split=interactive_agent)

### 12. BFCL v3/v4 multi-turn
- URL: https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html, data https://github.com/ShishirPatil/gorilla/tree/main/berkeley-function-call-leaderboard/bfcl_eval/data
- Format: each entry `id` (e.g. `multi_turn_base_0`), `question` (list of turns, each a list of `{role:"user", content}`), `initial_config` (serialized starting state of stateful Python classes such as `GorillaFileSystem`, `TwitterAPI`, `VehicleControlAPI`), `path` (callable functions), `involved_classes`; ground truth per turn in `possible_answer/`. Files: `BFCL_v4_multi_turn_base/long_context/miss_func/miss_param.json`. (raw file fetch; directory listing)
- Example: turn 1 "Move 'final_report.pdf' within document directory to 'temp'... make sure to create the directory" -> agent calls `cd`, `mkdir`, `mv` on the file-system class -> turn 2 grep for budget section -> etc.
- Stats: 1,000 entries: 200 base + 200 missing-parameter (agent must ask) + 200 missing-function + 200 long-context + 200 composite; 20-step limit per turn before forced termination. Evaluation per turn: state-based (compare backend object state after the turn) AND response-based (ground-truth call sequence must be a subset of what the model executed, tolerating exploration and recovery). Entry passes only if all turns pass both. (blog)
- Grader sees: in-memory object state after each turn plus the executed call list.

### 14. GAIA
- URL: https://huggingface.co/datasets/gaia-benchmark/GAIA
- Format: `task_id`, `Question`, `Level` (1 to 3), `Final answer`, `file_name`, `file_path`, `Annotator Metadata{Steps, Number of steps, Tools, Number of tools}`. 450+ questions. ### 15. TheAgentCompany
- URL: https://arxiv.org/html/2412.14161 (OpenHands-based runs, code/data/results released)
- Stats: 175 tasks; best agent (Gemini 2.5 Pro) 30.3% full completion, 39.3% partial score, about 27 steps and more than $4 per task; step counts across models 14.6 to 39.9 LLM calls; cost under $1 to over $6 per task. Grading is checkpoint-based: partial score 0.5*Result/Total + 0.5*S_full. Failure modes: lack of social skills (agent "prematurely considers the task accomplished" after a colleague reply), browsing failures on popups and professional UIs, and shortcut faking (renaming another user to the target name). Interruptions come from simulated colleagues over chat (NPC turns inside the trajectory).

### 16. MCPMark
- URL: https://github.com/eval-sys/mcpmark, paper https://arxiv.org/html/2509.24002
- Format: results in `./results/{exp_name}/{model}__{mcp}/run-*/` containing the task instruction, initial environment state, execution trajectory (agent actions + tool responses), final environment state, `verify.py` output, and metrics (turns, tool calls, tokens, cost) in JSON/CSV.
- Stats: 127 tasks over Notion, GitHub, Filesystem, PostgreSQL, Playwright; average 16.2 turns and 17.4 tool calls per task; per service turns roughly Filesystem 10 to 20, Notion 13 to 34, GitHub 10 to 27, Playwright 16 to 31, Postgres 8 to 30; gpt-5-medium 52.56% pass@1 / 33.86% pass^4, Claude Sonnet 4 28.15% / 12.60%; >50% of failures are "implicit" (agent finishes but verification fails), the rest explicit: context overflow, turn-limit, abandonment, premature stop, malformed tool call; task instructions average 288.6 words, verifiers 209.8 lines. README (2026) reports gpt-5.5 at 92.9% on the Verified set.
- Grader sees: real service state (Notion pages, GitHub repo, DB rows) inspected by a per-task Python verifier from a curated initial state.

### 17. MCP-Universe
- URL: https://github.com/SalesforceAIResearch/MCP-Universe, paper https://arxiv.org/abs/2508.14704
- Format: trace records via `MemoryCollector` / `FileCollector` / `SQLiteCollector`, results map `task_trace_ids`; evaluators are declarative (`json`, `get`, `len`, `foreach`, comparison ops) in task JSON, in three families: format, static, dynamic (fetches live ground truth at grading time).
- Stats: 6 domains, 11 MCP servers; GPT-5 43.72%, Grok-4 33.33%, Claude 4 Sonnet 29.44%; named failure drivers: context growth with step count and unfamiliar tools. Cursor did no better than plain ReAct.

### 18. MCP-Atlas (Scale AI, 2026)
- URL: https://arxiv.org/html/2602.00933
- Format: task = natural-language goal + context, allow-listed tool set, reference trajectory, atomic claim list; grading is a claim-level rubric grounded in tool outputs (1.0 / 0.5 / 0.0 per claim, pass at >=0.75 coverage).
- Stats: 1,000 tasks, 36 real MCP servers, 220 tools; 15.2 tools exposed per task (6 to 37), 4.1 required (2 to 8), 11.1 distractors; reference trajectory mean 9.8 tool calls; 4.7 claims per task; top pass rate 82.2%; 11-category failure taxonomy: tool-call family (malformed parameters, wrong tool, no tool use, failed error recovery) = 36.7%, cognitive family (task misunderstanding, faulty synthesis, response misparsing, early termination, hallucinated facts, logical errors, constraint violations) = 63.3%.

### 19. EnterpriseOps-Gym (2026)
- URL: https://arxiv.org/abs/2603.13594 (found via arXiv API; related: StarHarness 2608.24804, AgentMercury 2608.20634 which synthesizes ~5,000 verifiable business environments)
- Format/statistics: containerized sandbox with 164 DB tables and 512 tools across 8 industries; 1,150 expert tasks; best model (Claude Opus 4.5) 37.4%; oracle guidance adds 14 to 35 points; best refusal rate on infeasible requests 53.9%, and agents often execute harmful actions instead of refusing. The abstract does not publish per-step statistics.

### 20. Analyses of trajectory failures (cross-cutting)
- TRAIL (Patronus): 148 traces in OpenTelemetry/OpenInference span format (118 GAIA, 30 SWE-bench), 1,987 spans, 575 erroneous spans, 841 errors; annotations are per span: span id, category, evidence, description, impact Low/Medium/High; taxonomy reasoning / system execution / planning-coordination; output-generation errors (formatting, instruction non-compliance) are ~42% of all errors; traces often exceed model context; best judge model 11% accuracy. https://huggingface.co/datasets/PatronusAI/TRAIL, https://arxiv.org/abs/2505.08638
- AgentErrorTaxonomy / AgentErrorBench / AgentDebug: 200 annotated failing trajectories (100 ALFWorld, 50 WebShop, 50 GAIA); five modules (memory, reflection, planning, action, system: step-limit exhaustion, tool execution error, LLM limit, environment error); "most failures cluster in mid-trajectory steps (6 to 15)", memory and reflection dominate; kappa 0.55; root-cause feedback yields up to 26% relative success gains. https://arxiv.org/html/2509.25370
- MAST (Why do multi-agent LLM systems fail): 1,600+ annotated traces across 7 frameworks, 14 failure modes in three groups (system design, inter-agent misalignment, task verification), kappa 0.88. https://arxiv.org/abs/2503.13657
- Step-criticality: Critical Step Optimization identifies "decision points where alternate actions demonstrably flip task outcomes" (https://arxiv.org/abs/2602.03412); ELPO locates "the first irrecoverable step via binary-search rollout trees" (https://arxiv.org/abs/2602.09598). Error-recovery data synthesis for GUI agents: https://arxiv.org/abs/2605.29447, OpenMobile policy-switching to capture recovery data: https://arxiv.org/abs/2604.15093.
- LHAW: 285 underspecified variants of TheAgentCompany, SWE-Bench Pro and MCP-Atlas tasks, classifying missing information as outcome-critical, divergent, or benign (https://arxiv.org/abs/2602.10525). Useful when deciding which missing fields in a customer trace actually matter.

## Part 2: Synthesis

### (a) Common denominator across formats
Every source reduces to an ordered list of messages with a `role` in {system, user, assistant, tool}, an assistant `tool_calls[]` each with `name`/`function_name`, `arguments` (dict or JSON string) and usually an `id`, and a tool result with `content` plus (in the better ones) a back-reference (`tool_call_id` in AgentDojo, `source_call_id` in ATIF, `id` in tau2) and a boolean/string `error` (tau2, AgentDojo). A run-level wrapper adds `task_id`/`instance_id`, model identity, a success flag (`resolved`, `reward`, `utility`, `target`), and sometimes cost and duration (tau2, ATIF, TheAgentCompany, MCPMark). The tool schemas appear as a `tools` field in SFT-style datasets (xLAM, Toucan, Nemotron, OpenHands) and ATIF (`agent.tool_definitions`), but not in most benchmark logs. Timestamps per step exist only in tau2 (`timestamp`, `generation_time_seconds`), ATIF (ISO 8601), SWE-agent (`execution_time`), and OpenTelemetry-based TRAIL.

### (b) What is systematically missing that a replica environment needs
- Pre/post state: only AppWorld (`dbs/*.jsonl` deltas, checkpoints), MCPMark (initial and final state saved per run), BFCL (`initial_config` per entry), and tau/tau2 (DB check at end) carry state. Chat-style dumps (SWE-Gym, SWE-smith, Toucan, Nemotron, APIGen-MT, tau2 HF mirrors) contain no state at all; state has to be reconstructed by replaying tool outputs.
- Side effects: no format tags a tool call as read vs write. BFCL's blog notes state-based eval exists precisely because write/delete effects are invisible in the response (https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html); AppWorld's collateral-damage tests exist for the same reason.
- Tool schemas: absent from tau2 runs, SWE-agent `.traj`, WebArena, ToolBench answer files, Terminal-Bench dumps (`tools:[{fn, cmd}]` only). You will usually need to recover the schema from the system prompt or from the union of observed argument keys.
- IDs and linkage: tool-call to result linkage is explicit in ATIF, AgentDojo, tau2; positional (next message) everywhere else. Entity IDs inside tool outputs (order IDs, file paths) are the only join keys available to reconstruct a database.
- Timestamps and latency: missing in almost all SFT datasets; present in tau2, ATIF, SWE-agent, TRAIL spans.
- Non-determinism markers: none. ToolBench's decay and StableToolBench's cache/MirrorAPI are the evidence that live tool responses drift; MCP-Universe added "dynamic evaluators" for time-sensitive ground truth. A replica must record which tool outputs were live (time, randomness, external data) versus deterministic functions of state.
- User intent and hidden user state: tau2 has a user simulator with its own tools and observable state (dual control), APIGen-MT has a "blueprint" with ground-truth actions, BFCL has the per-turn intended calls. Production traces will have none of this; only the surface utterance.
- Truncation: Terminal-Bench dumps truncate observations at 5,000 chars; `harithoppil` stores the whole trajectory as one 223k-char text field; SWE-Gym failures reach 167k tokens. Expect observation content to be lossy in customer traces too.
- Termination reason: tau2's `TerminationReason` enum and MCPMark's explicit-failure list (context overflow, turn limit, abandoned, premature stop, malformed call) are the only places where "why the episode ended" is a first-class field.
- Sub-agents: only ATIF (`subagent_trajectories`, `subagent_trajectory_ref`) and MAST/TRAIL multi-agent traces model them.

### (c) Recurring trajectory shapes and rough frequencies
Frequencies are only published sporadically, so these are ranges inferred from the numbers above, each tied to its source.
- Single-shot tool call (one assistant turn, one or more calls, done): the dominant shape in xLAM-60k (all rows), Toucan single-turn subsets (about 63% of 1.5M are single-turn: https://arxiv.org/html/2510.01179), and Nemotron `tool_calling` (316k of 335k rows).
- Read-then-write chain (lookup, confirm, mutate): the canonical tau/tau2, APIGen-MT and Nemotron interactive shape; tau2 policies force a confirmation turn before writes, Nemotron's policy text mandates "explicit verbal confirmation" and "one tool call at a time". Length: up to 56 turns in APIGen-MT; MCPMark averages 16.2 turns / 17.4 calls; MCP-Atlas reference paths average 9.8 calls.
- Long exploratory loops with retries (coding and terminal): median 21 / mean 47 steps on Terminal-Bench; about 19 agent turns for successful SWE-Gym runs, with failed runs spiralling to 167k tokens; TheAgentCompany 14.6 to 39.9 LLM calls per task. Explicit retry-rate numbers are not published; proxies are MCPMark's ">50% implicit failures", MCP-Atlas "failed error recovery" as one of four tool-call failure modes, and AgentErrorBench's finding that failures cluster at steps 6 to 15.
- Clarification / missing-information turns: BFCL reserves 200 of 1,000 entries for missing parameters and 200 for missing functions; Toucan's 40K "irrelevance" rows train not-calling; EnterpriseOps-Gym reports agents refuse infeasible requests only 53.9% of the time at best. In tau2, the "user" can also fail: 16 to 47% user-simulator error rate depending on domain.
- Parallel fan-out: Toucan explicitly includes parallel calls (share not given), xLAM answers can contain several calls per query, ATIF models multiple `tool_calls` per step with per-call `source_call_id`. Nemotron and tau-style policies forbid it. No source publishes a parallel-call percentage; treat it as agent-scaffold dependent.
- Sub-agent delegation: present only in ATIF and in MAST/TRAIL multi-agent traces; no frequency published.
- User interruption mid-episode: structural in tau2 (every episode is multi-turn), TheAgentCompany (simulated colleagues), BFCL (multi-turn questions), Toucan multi-turn (about 37%), Nemotron interactive (19k rows). Zero in SWE/terminal/web datasets, which are single-instruction.

### (d) What a grader can actually see at the end, per source
- Final DB/object state: tau-bench, tau2 (`db_check` plus action set plus NL and communicate checks), AppWorld (state-based unit tests plus collateral-damage checks), BFCL multi-turn (state per turn plus call-subset check), AgentDojo (environment state checks for utility and security), MCPMark (`verify.py` against real service state), EnterpriseOps-Gym (state sandbox).
- Artifact only: SWE-agent, SWE-Gym, SWE-smith, Terminal-Bench (patch or container tests after the run).
- Final message / answer string only: GAIA, MCP-Universe static evaluators, WebArena `string_match` and `url_match` (with `program_html` reaching into live pages), MCP-Atlas (claims verified against tool outputs in the trace), ToolBench/StableToolBench (LLM-judged pass and win rates on the final answer, FAC).
- Checkpoints along the way: TheAgentCompany (partial credit per checkpoint), Mind2Web (per-step element and action match against a human demo).
- Nothing at all (pure SFT data with generation-time verification only): xLAM-60k, APIGen-MT-5k, Toucan, Nemotron-Agentic.

Practical takeaway for building the replica from customer traces: model the trace as ATIF-shaped steps (that is the most complete public schema), then add the three things no public log reliably carries: a per-call read/write side-effect flag, a pre/post state snapshot keyed on the entity IDs found in tool outputs (AppWorld's `dbs/*.jsonl` delta style), and a determinism flag per tool so replay can distinguish cached outputs from live ones (the StableToolBench lesson).
