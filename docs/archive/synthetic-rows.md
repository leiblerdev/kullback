# Synthetic rows: what the Starting state is missing and how others fill it

Written 2026-08-29 after the first live retail build, from a research pass over the benchmark seed-data methods and the tabular synthesis literature (full notes in the session scratchpad, `research_synthetic_rows.md`). Decision D40 already says synthetic rows for reads are generated by observing the real rows in the traces, tagged, and reported "assisted" when read. This file records what exists, what the retail numbers say, and the practices the sources agree and disagree on, so the design grill can decide the how.

## 1. Where retail stands

Real tau2 retail seed against the Starting state mined from 456 traces:

| table | real seed | mined | share |
|---|---:|---:|---:|
| users | 500 | 53 | 10.6% |
| orders | 1000 | 158 | 15.8% |
| products | 50 | 35 | 70% |
| items (real: `products[id].variants`) | 591 | 9 | 1.5% |

Field shape on the rows we do have matches the real one (user keys identical). What is missing is breadth, and one table that is not a table: we mined `items` as a top-level table where the real db nests variants under products. That shape difference is the `schema_shape` cause in the fidelity split (`get_item_details`, 9 calls). The nesting was in the traces after all (every `get_product_details` result carries `variants` keyed by `item_id`), and since D106 the miner records `items -> products.variants` as the table's home, so the 591 real variants are the count a generator has to reach inside products, not in a table of their own.

`compile_env.add_synthetic_rows` exists and is the whole of D40 as built: for an id the traces referenced but never showed, it writes a row made of the modal value per column from the observed rows, with the id set. Retail produced 0 such rows, because every id the traces referenced was also shown. It never generates rows for ids the traces never mention, which is the 90% of users and 98% of items above. So today an off-path read of a real but untouched user returns "not found", and a Run that wanders there is marked assisted for a row that does not exist rather than for a synthetic one.

## 2. How the benchmarks built their seeds

- tau-bench and tau2: schema by hand; per field, decide whether an LLM is needed (names, addresses, product names) or code (ids, prices, dates); the LLM produces seed values for free text and a program composes rows. Their own notes: "code-based database construction is more reliable than GPT-based construction". Ground-truth actions are built from the db first and the user scenario written afterwards to lead to them.
- AppWorld: about 106 people with a relationship graph, 370K rows, populated by calling the same validated APIs the agent uses at eval time (placing an order writes order, cart, inventory and email rows through the API's own invariants). ChatGPT only for free text, with a human review pass. Correctness enforced by 1,780 unit tests rather than by generation-time constraints. Per-task diffs over one shared base db.
- CRMArena-Pro: the outlier. LLM generates structural content too (29K to 55K records, 21 latent variables), and a validation pipeline (dedup, format checks, LLM consistency checks, 90% expert "realistic" rating) catches what it got wrong.
- EnterpriseOps-Gym (164 tables, mean FK degree 1.7) and STATE-Bench (450 task-local sandboxes) do not publish their generation method.
- APIGen-MT, EnvFactory, Envs-FORGE, Agent-World: fix deterministic, checkable content programmatically first, verify it, then layer natural language on top. Westworld and TauForge could not be verified as real systems.

## 3. Practices the sources converge on

1. Fit marginals and pairwise correlations from the seed rather than hand-specifying them. A few hundred rows is inside the regime copula methods (SDV) and in-context LLM generation with curation (CLLM, FairTabGen, 200 to 1,000 rows) report as workable. GANs, diffusion and fine-tuned LLM generators need more data and collapse minority categories.
2. Ids and enumerations are generated by code from the mined format and vocabulary, never by an LLM. tau-bench says so; IRG treats FK matching as a graph optimization so no key dangles; "When Tables Leak" (2512.08875) shows LLM-generated digit strings memorize and leak seed values. Concretely: mine prefix, length, character set and sequential-or-random from the real ids and draw new ids disjoint from the observed set.
3. Closed vocabularies stay closed: statuses, tiers, types are sampled from the observed set at observed frequencies, because tool and policy code branches on the exact values.
4. Generate related rows as one bundle, not table by table: user, then addresses, payment methods, an order referencing them, its line items, with totals computed as the sum of items and timestamps in causal order. Table-by-table generation is where dangling keys and totals that do not add up come from. IRG's staging (degree, null indicator, aggregate stats, row values, FK matching) is a usable template.
5. Where the harness has a callable tool layer, prefer creating synthetic activity by calling the tools (AppWorld) over inserting rows, since a tool cannot behave differently on a row it validated and wrote itself.
6. Test the result: FK closure (zero orphans, IRG reports 100% as achievable), id uniqueness over the union of real and synthetic, KS per numeric column and total variation per categorical column against the seed (SDMetrics computes both; both are marginal, so spot-check one or two known correlations), distance-to-closest-record as a duplication filter, and tool-behavior parity: replay recorded calls with synthetic ids substituted and require the same result schema and the same success or error branch. None of the reviewed work has that last test, because none of it mines someone else's world.

## 4. Failure modes reported

- Judges near chance on synthetic worlds: Holistic Agent Leaderboard (2510.11977) measures LLM judges at 0.65 AUROC on tau2 trajectories and 0.54 on AppWorld API traces, with false-success 3% to 76% by domain. Deterministic state assertions are the safer grader once synthetic rows are in play (consistent with D25).
- Mode collapse on rare states (a "partially refunded" order vanishes) for GAN generators; Faker-style generators have the opposite problem, no mode from the customer's data at all.
- Referential integrity breaks often enough in naive multi-table synthesis that IRG reports "100% valid schema" as its differentiator.
- DCR alone gives false confidence about privacy ("The DCR Delusion", 2505.01524). For our concern, not handing back exact recorded rows as unseen, DCR as a duplication check is adequate; for PII it is necessary, not sufficient.
- Held-out has to hold end to end: changing the simulated user between two evaluations moves scores 5 to 15 points, so unseen rows with a seen user simulator are not a held-out test.

## 5. Approaches ranked by fit to a few hundred mined rows with tool parity required

1. Tool-driven generation (AppWorld pattern). Input: our own generated tools plus a per-table count and value distribution from the mined marginals. Output: rows written by the same code path a real transaction takes, derived fields right by construction. Risk: only as complete as the tool layer; a mined table no write tool touches (products, in retail) still needs a direct generator; the heaviest to stand up.
2. Programmatic composition with an LLM for free text only (tau-bench pattern). Input: per-field class (checked: ids, statuses, keys, amounts, dates; free: names, street lines, descriptions), mined marginals per checked field, mined id-format spec. Output: checked fields by code, free text by an LLM or Faker. Risk: a field misclassified as free text that policy actually branches on; cross-table correlations exist only where coded.
3. IRG-style constrained multi-table generation. Input: the mined schema with PK and FK declared, per-table samples. Output: a full database with FK closure by construction. Risk: knows nothing of tool behavior, so it must be paired with the parity test; row-count targets get sacrificed to FK integrity; evidence at a few hundred rows total is indirect.
4. SDV with HMA as a baseline or a second opinion on fidelity. Input: tables in SDV metadata with relationships. Output: fitted marginals, FK values drawn from existing keys. Risk: SDV's own docs cap it at about 5 tables and one level of depth; it will perturb a checked field unless constrained.

Our `EntitySchema` already carries a per-column class (`exempt | hard | semantic`, proposed by rule with evidence, verified per column) that is close to the checked-versus-free split option 2 needs.

## 6. Where sources disagree

- Whether an LLM may generate structural fields: tau-bench and AppWorld say no by construction; CRMArena-Pro says yes with post-hoc validation. The majority and the leak evidence sit with the first.
- Whether DCR is a sufficient privacy check: industry material says yes; 2505.01524 says no.
- Whether a few hundred rows is enough: classic generators say no; the low-data in-context methods say yes with curation.
- Whether synthetic rows should count as environment at all: D40 and D49 say a Run that reads one is assisted and stays out of the counted Verdicts; every benchmark above counts its synthetic world as the world, because there the synthetic world is the whole world. The difference is that ours stands in for a customer's real one.

## 7. What was built (2026-08-29, D107)

`builder/synth.py` is option 2 of section 5 with the LLM left out: checked fields by code, free
text by recombining the observed vocabulary, and the cross-table structure from mined rules. The
founder's reference for this was "tau forge"; it could not be found under that name, and the
closest documented method is tau-bench's own appendix B.2, which is what section 2 describes.

Run it with `harness build --grow users=500 --grow orders=1000 --grow-seed 0`. A homed table
(retail's items) grows with its parent. The build writes `synthetic.json` with what was added, the
rules per table and the checks, and every grown id is tagged on the schema so both the Simulated
user and a tool read of one mark the Run assisted.

Retail, grown from the mined Starting state to the real seed's counts:

| table | observed | added | real seed | checks |
|---|---:|---:|---:|---|
| users | 53 | 447 | 500 | ids unique, keys closed, no twins |
| orders | 158 | 842 | 1000 | every order under a synthetic user that lists it back; line totals equal the sum; payment method is one of that user's |
| products | 35 | 15 | 50 | names repeat (no free-text source) |
| items (under products.variants) | 448 | 178 | 591 | keyed by their own item id |

Against the real seed (which the generator never saw): items per order 3.02 vs 2.98, fulfillments
per order 0.53 vs 0.58, payment methods per user 1.46 vs 1.39, orders per user 1.88 vs 2.0,
variants per product 11.9 vs 11.8; users' city and state within 0.25 and 0.18 total variation;
gift card balances at 0.25 KS. Order line options sit further out (up to 0.57 on `connectivity`)
because only the observed products' option vocabularies exist to draw from.

Known limits, each a candidate for the next pass: zip is redrawn independently of city; product
names and any other free text repeat; a numeric option seen fewer than ten times with distinct
values is not told apart from an identity by evidence alone (the rule errs toward category);
popularity of unseen items is one smoothing count. The tool-parity replay of practice 6 (recorded
calls with synthetic ids substituted) is not built; `scripts/env_fidelity.py` is where it belongs.

### The same rules on airline and telecom (2026-08-29)

The overfit check D106 set, run the same day on the cross-domain corpora under `data/work/`
(200 airline traces, 456 telecom traces), with the code unchanged apart from three rules the run
itself forced, each structural: an id with no run shape in common (airline's `OWZ5XL`) is drawn
per position from the characters seen at that position; a digit run is drawn inside its observed
range per length, so a day stays a day and a birth year a birth year (before this, `dob` came out
as `6865-68-15`), with the range widened only when a sequential id exhausts it; and a list named
after a table (`reservations`, `bill_ids`) is a foreign key to it even when most of the rows it
names were never shown, which is the normal case for a corpus that samples the world.

| domain | observed | grown to | rules found | checks |
|---|---|---|---|---|
| airline | 34 users, 117 reservations, 134 flights | 500 / 2000 / 300 in 2.5 s | users.reservations is a key list with a back reference from reservations.user_id; reservation flights repeat the flight's origin and destination; payment ids come from the user's payment methods; email and user id from the name | pass; reservations per user 4.04 vs 4.0 real, flights per reservation 2.53 vs 2.5 |
| telecom | 1 customer, 1 device, 1 plan, 3 lines, 4 bills | 5 / 5 / 5 / 15 / 20 | bill.total_due is the sum of its line items; customer.bill_ids and line_ids are key lists | fails the id-shape check with a warning: `customers` was grown from one observed row, so its id pattern (`^C10{2}1$`) is a literal and no rule has evidence |

Telecom is the honest limit and a finding of its own: 456 traces that reuse one customer show
one customer, and no generator can grow a distribution it has one sample of. The checks say so
in `synthetic.json` (`warnings`) rather than pretending; the tables below ten observed rows are
copies with new digits.
