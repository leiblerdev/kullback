# Phase 1: the move

Landed 2026-09-02, the first phase of `rebuild-phases.md` (D129, D130). No behavior changed. The distribution, the package and the command are now `kullback`, the package sits at the repository root with no `src/`, `src/harness/{builder,runner,shared}` is split into the six subpackages of D121 and D123 plus the three frontends, the dependency direction is an import-linter contract that `uv run lint-imports` checks, and the tests moved to mirror the packages (1,451 collected before and after). The one artifact that changes on purpose is `runner_version.json`.

## What moved where

`shared/` is gone; nothing imports it. `shared/provider.py` and `shared/pricing.py` became `kullback/ai/`, the provider layer, which imports nothing of ours. `shared/records.py`, `shared/canon.py`, `shared/confinement.py` and `shared/budget.py` went into `kullback/runner/` beside `loop.py`, `route.py`, `verdict.py`, `validate.py`, `atom_context.py`, `boundary.py`, `gate_support.py`, `replay.py`, `regrade.py`, `state.py`, `judge.py` and `scorecard.py`, which stayed. `runner/pipeline.py`, `shared/parallel.py` and `shared/search.py` went into `kullback/builder/`, where everything that was already under `builder/` stayed, `verifier.py` included until phase 3. `shared/report.py` is `kullback/report.py`, `cli.py` is `kullback/cli.py`, and `tui.py` is `kullback/tui/__init__.py`. `kullback/agent/`, `kullback/gates/` and `kullback/examiner/` exist with a docstring each saying which phase fills them, and `tests/agent/`, `tests/gates/` and `tests/examiner/` the same, so phases 2, 3 and 5 add files rather than directories. `scripts/` imports from the new paths and puts the repository root, not `src/`, on `sys.path`.

Records and canon are in `runner/` because they define what the Runner grades: a Verdict is computed over `Run` events under the canonicalizer's rules, and a package that grades by a record it does not own would need the record to sit in a fourth place. The cost is that `builder/verifier.py`, which D91 keeps out of the Runner's internals, now reads two modules whose import path starts with `kullback.runner`. The boundary scan and the two tests that used to say "no `harness.runner` in the source" now name the modules verifier.py and report.py may read (`records`, `canon`) and refuse every other `runner/` module, which is the same rule stated against the new paths.

Confinement is in `runner/` rather than in `gates/` because it is a primitive two callers share: `verdict.py`'s atom gate and `validate.py`'s constraint gate both call `confine` on model-written source, and phase 3 moves the gate over tool bodies into `gates/` on top of it. Had the primitive gone to `gates/` now, `runner/` would import `gates/`, which is the wrong direction.

`pipeline.py` is in `builder/` because `build.py` is its only caller and phase 4 turns it into the Builder's DAG scheduler. It was in `runner/` only because the first build brief put it there, and it was the one file under `runner/` that the D89 scan had to keep from importing the Builder while serving the Builder. The scan's tests that planted a dynamic import in `pipeline.py` now plant it in `loop.py`, a file that stays under the scanned surface. `parallel.py` and `search.py` moved for the same reason: `build.py` is the only caller of both.

`tui/` is a package rather than a module because later phases split it: the screen today is one file that reads the build's files, and the frontends of D129 consume an event stream, so the file will grow pieces (the stream reader, the board, the banner) that are easier to review as separate modules under one directory.

`Usage`, the token count a model call returns, is the one record no longer defined in `records.py`. `provider.py` constructs it on every reply and `records.py` embeds it in `Cost`, so it has to sit where both can import it, and the only such place under the contract is `ai`. It sits in its own module, `kullback/ai/usage.py`, rather than in `provider.py`, because `verdict.py` must have no import path to a provider (D76, checked by walking the import graph): a module holding one pydantic class and no client keeps that true. It carries `Record`'s config by hand (aliases both ways, unknown keys refused), `records.py` re-exports it, and `ALL_RECORDS` still lists it so the round-trip test and the pipeline cache treat it like any other record.

## The contract

`pyproject.toml` carries three import-linter contracts under `[tool.importlinter]` with `root_package = "kullback"`, written for all six packages now so phases 2 and 3 do not edit the file. The first is a layers contract: `builder` and `examiner` are the top layer and independent of each other; `gates` is below them; `agent` and `runner` are below `gates` and independent of each other; `ai` is the bottom. A layer may import anything below it and nothing above or beside it, so `ai` imports nothing of ours, `agent` and `runner` import only `ai`, `builder` and `examiner` import `agent`, `gates`, `runner` and `ai` and never each other. The second contract forbids `gates` from importing `agent`: a gate is code over the Runner's work and never reaches into the agent core (D122). The third forbids every one of the six packages from importing `cli`, `tui` or `report`, so the frontends are imported by nothing but themselves. Three contracts, all kept, over 46 files and 106 dependencies at the time of writing.

## RunnerVersion

`runner_version()` in `runner/boundary.py` used to hash three files by name, `loop.py`, `route.py` and `verdict.py`, and marked a missing one as `"missing"`. It now hashes every `.py` file under `kullback/runner/`, keyed by the path relative to `runner/` in sorted order, plus the routing config, and `RUNNER_FILES` is gone from both `boundary.py` and `cli.py` (D121: the Runner's hash is a package). A file moving into or out of the package moves the version the same way a changed line always did. Every `runner_version.json` frozen before this phase is therefore stale: its `file_hashes` list three names where the new formula lists seventeen (sixteen since phase 3 moved `scorecard.py` out of the package), and its `runner_version` no longer matches what `validate.runner_version` computes, so `kullback freeze-runner` must be run again in every workdir before its next `verdict` or `regrade`. That is the only artifact this phase changes.

## The byte-identical check

The offline build the tests run (the `build` fixture of `tests/test_e2e.py` and the full `build.build()` of `tests/builder/test_build.py`, over `tests/fixtures/tau2_retail_small.json` with `RecordedModel` and `TestModel`) was run once from the last `harness` commit and once from this tree, into two directories, and compared with `diff -r`. `bodies.json`, `constraints.json`, `intents/`, `gates.json`, `environment.json`, `schema.json`, `tool_sigs.json`, every Run under `runs/`, every Verdict and every stage cache entry are byte-identical, with the following provisos, all checked rather than assumed.

`ingest_version` is the sha256 of `ingest.py`'s own bytes (D66 keys re-derivation on the ingest code hash), and the import lines in that file changed, so the raw comparison moves `ingest_version`, and through `Trace.hash` the names of the trace files and the order `load_traces` reads them in, which is sorted by file name. The same comparison run without the pin was measured too, so the cascade is known rather than guessed: `bodies.json`, `constraints.json`, `intents/`, `gates.json` and the Tasks are still byte-identical, but `schema.json` (each column's capped `samples` list is filled in trace order), `tool_sigs.json` (`first_seen` and `last_seen`), `user_facts.json` (the same facts in another order), `schema_version`, `tools_version` and therefore `env_id` in `environment.json`, the sidecar and every Run all move. None of that is the moved code doing something different; it is the pipeline being order-dependent on a trace order that the ingest hash decides, and the ingest hash changing because the file's bytes changed, which is what D66 asks for. Pinning `INGEST_VERSION` to one value on both sides makes the whole cascade disappear and is how the comparison above was made. On an existing workdir the next build re-derives its traces under the new version, exactly as after any edit to `ingest.py`. Two files carry wall-clock noise (`wall_ms` in `budget.json`, and the nonce in each tool sandbox's `out.json`); running the old tree twice against itself shows the same noise. Stage cache entries under `cache/` and regraded Verdicts under `verdicts/` are named by keys that include the stage function's module name and the canon module's identity, so their file names moved while their contents did not.

## What the next phases build on

Phase 2 adds the provider-neutral stream to `ai/` and fills `kullback/agent/` and `tests/agent/`; the contract already lets `agent` import `ai` and nothing else, so the phase is files, not configuration. Phase 3 moves the D79 suite out of `builder/verifier.py`, the check list out of `runner/validate.py` and the confinement gate over tool bodies into `kullback/gates/`, which the contract already lets import `runner` and `ai`; `verifier.py`'s allowance to read `records` and `canon` in the boundary scan is what it keeps until then. The `mutants/` directory is mutmut's own copy of the tree and is gitignored; it still holds the `src/harness` layout and is rebuilt from `source_paths = ["kullback/"]` on the next `uv run mutmut run`. Two names keep the old word on purpose: the environment variable `HARNESS_ALLOW_MODEL_REQUESTS` and the price cache under `~/.cache/harness/`, both user-facing settings whose rename would be a behavior change outside this phase.
