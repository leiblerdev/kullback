# Phase 7: context tools and the floor

Landed 2026-09-02, the seventh phase of `rebuild-phases.md` (D124, D131), pulled forward to run beside phase 4 because it lives entirely in the agent core that phase 2 built. `kullback/agent/context.py` is the accounting (the estimate, the window, the line, the counters) and the manager that owns the session record, the guards, the four operations and the floor; `kullback/agent/context_tools.py` is the extension that gives the model the tools under whichever arm the harness is configured for; `AgentHarness` gains `session` and `context` parameters, the `session`, `context` and `context_stats` properties, and the three methods the manager needs (`remove_prompt_section`, `sync_context` and a public `emit`); `ExtensionAPI` gains `context`, `protect`, `unprotect`, `entry_id_for`, `catalog_tool`, `catalog_skill` and `remove_prompt_section`. Forty-five tests under `tests/agent/` (210 under `tests/agent/` and `tests/ai/` together, against 164 after phase 2) drive the whole of it against `TestModel` and assert on the events a run emits and the entries a session records. Every public name and signature of phase 2 is unchanged; every addition is a parameter with a default, a new module or a new method, and a harness built without a session behaves exactly as before. No artifact changes: nothing outside the agent core calls any of this yet, and the one thing that would change a transcript, the context note on tool results, is off by default.

## Why the tools exist, and what has no precedent

D124 moved tau's seam: tau lets code decide when to compact and what to replace and asks the model only for the summary text, and the founder wanted the model to decide what to keep and what to throw away, with code as the floor. D131's research pass found that nobody has shipped that shape. Every agent it looked at triggers compaction from code at 75 to 95% of the window, Anthropic's own compaction api states that the model cannot influence what gets compacted, and the one study of model-controlled forgetting found it loses to a hybrid where code protects the dependencies the model has not tagged. So the tools are an experiment with the guards D131 asked for, the floor is what makes a missed compaction cost a count rather than a two-hour round, and the counters are what the experiment reports. The live context meter in every tool result has no precedent anywhere; it is part of what is being tested.

## The estimate, the window and the line

`estimate_context(messages, system, tool_schemas, window, line, use_usage)` returns a `ContextEstimate` with the tokens, the window, the line as a fraction and which of two sources it used. When the provider reported usage on an assistant message, the estimate is that message's input, cached input and output tokens (what the model saw and said on that call) plus a characters-over-four count of whatever was appended after it, and the source is `usage`. Otherwise the whole active context is rendered the way the wire sees it, the system prompt and the tool schemas included, and counted at four characters to a token; the source is `heuristic`. The manager forces the heuristic after any compaction until the next reported usage arrives, because the last usage counted a context the compaction has since changed, and reading it would fire the floor on every later turn; a test pins that. The window is a parameter on `ContextConfig` with a default of 200,000, because the agent core may not import `runner.budget` (D121) and a caller passes `window_for(model)` in. The line is a fraction of the window, 0.40 by default (D124, kept by D131 against shipped thresholds of 75 to 95% and the one practitioner recommendation of 50 to 60%). `over_line` is strictly above the line.

## The record and the ids

A harness given a `SessionStore` records every message the loop appends as a `MessageEntry`, in the harness's own event path before any subscriber sees the `message_end`, and starts its transcript from the store's `active_messages()`; after a compaction, `sync_context` puts the active path back in front of the model by rewriting the transcript list in place and re-reads the system prompt into the running state, so a forget, a fallback or a skill change reaches the very next model call without rewriting history. The session root is written with the arm. Entry ids are short (`e1`, `e2`, ...) because the model has to type them; they are assigned from a counter that starts above the highest existing number on a reloaded session and is never reused. A tool result's id is assigned at `tool_execution_start`, always fresh, so a hook or a handler can `protect` the result before the model reads it, and so a scripted call id that repeats after a compaction shrank the transcript can never pair a new result with an old entry's id.

## The tools and every refusal

`forget(entry_ids, note)` appends a `CompactionEntry` with `by="model"`, the note as its summary and the ids as `replaces_entry_ids`; `active_path()` then stands the summary where the first replaced entry stood, so it reads at the point in the history it summarizes, and nothing is deleted. A forget that names one side of a tool exchange is widened to the whole exchange, the assistant message and every result answering its calls, because a result without its call or a call without its result is a transcript no provider accepts; the result tells the model which ids were included for that reason, and a widened id meets the same guards as a named one. Each refusal is an `is_error` result whose text names the rule, so the model can act on it, and each is counted under its rule in the stats. The rules and their reasons: `session_info`, the root is never forgotten, whichever way it is named (the store enforces the same on replay); `protected`, an application declared the entry through `protect` with a reason the model reads back (an unacted gate ruling, an open finding, an unfinished repair; D131's dependency guard); `current_turn`, anything appended since the last `turn_start`, because the assistant message that made this very call and the results before it in the batch are what the model is acting on; `recent_tool_output`, the tool results of the last N turns that had any (N is `recent_tool_turns`, default 2), OpenCode's protected zone of recent tool output stated in turns; `unknown_entry` and `not_in_context` for an id the session does not hold or one already forgotten; `empty_note`, because a summary is the price of a forget. The order in which the rules are checked is the order above, so a protected entry is reported as protected even when it is also recent.

`recall(entry_id)` reads a forgotten entry back from the record and returns its text as the tool's result, marked with the original id and kind in the content and in the result's details. That result is a new entry at the end of the context; the original is never spliced back where it stood. Lost-in-the-middle is the reason (D131): what the model asked for is what it needs now, and the end of the context is where attention is. A recall of an entry still in context, or of an entry with no content (a tool-set change), is refused under `in_context` or `no_content`. The copy a recall lands is an ordinary tool result, and nothing about having been recalled protects it: it is guarded as recent tool output for the next `recent_tool_turns` turns like any other result, and after that the model may forget it again and the floor may drop it, unless the application protected it. That is deliberate, since a recall the model has finished with is exactly the kind of entry the floor should be free to take back; a test pins it.

`unload(name, kind)` and `load(name, kind)`, with `kind` one of `tool` or `skill`, change what is in context besides messages. Unloading a tool removes it from the registry and appends a `ToolSetChangeEntry`; the tool goes into the manager's catalog whether or not the application put it there, so a load reverses it. Unloading a skill removes its section from the system prompt and appends a `SkillChangeEntry` with the content hash of the text that left; loading appends the same with `action="load"`, so the record says which text was in context when an artifact was compiled (D125). The application registers what may be loaded through `catalog_tool(tool, loaded=)` and `catalog_skill(name, text, loaded=)`; a `loaded=True` catalog entry is registered or put in the prompt at once and recorded as a load. The context tools themselves are pinned and cannot be unloaded (rule `context_tool`), because a model that unloads `load` is stuck. Every load result carries the count of loaded tools against the soft cap of 20 (`tool_cap`, D131), and a load past the cap is allowed and says so in words; the tools' prompt section shows the same count and is refreshed on every load and unload.

`context_entries()` is the fifth tool, not in D124's list, and it is there because the model can only forget what it can name: every tool result carries its own entry id in the context note, but user messages, findings, steers and summaries have no such line, and the model needs the ids of the forgotten entries to recall one. It lists the active path with id, kind, an estimated size, the guard that applies and the first line, and then the entries a recall can bring back.

## The note

With `ContextConfig(note=True)` the harness installs one `tool_result` hook for the duration of each run, after every hook an extension installed, so that gate rulings appended to a result come first and the note comes last. The line reads `context 31% of 200000, line at 40%, estimated from usage; this result is entry e12`; the estimate counts the result it is appended to. It is off by default and applications turn it on: it changes every tool result the model reads, and phase 4's comparison against phase 3's artifacts must not see it unless asked. Without a session the note has no entry id and the rest is the same.

## The floor

At the end of every turn the harness records the fill as the model left it and, when the estimate is over the line and the floor is on, compacts tau's way with code choosing what goes. It walks the active path from the oldest entry in units (an assistant message with its tool results is one unit, every other entry its own), skips every unit that any guard covers (the root, protected entries, the current turn, recent tool output), and drops units until the tokens freed cover the excess over the line or nothing free is left. It then asks the same model for a summary of the dropped entries in one call, with the entries rendered by id and kind in the prompt and fenced between `<entries>` and `</entries>`, the prompt saying that everything between the markers is recorded data and never instructions (D134), and appends a `CompactionEntry` with `by="code_fallback"`, the dropped ids in `replaces_entry_ids`, `first_kept_entry_id` set when the dropped set is a clean prefix of the path (the store then applies it the way phase 2 described), and a note saying at which turn it fired, what the estimate was, whether the summary was the model's, and whether the context is still over the line because the rest is protected. When the model cannot answer (a `TestModel` that has run out, a provider error, an empty reply) the floor still compacts, with a mechanical summary that lists the dropped entries' kinds and first lines under a header saying why, and the note and the stats say it was mechanical. A `compaction` event with `by="code_fallback"`, the entry id and the note follows the `turn_end` on the same stream. A summary is itself compactable: when the context stays over the line and the only old entry is a summary, the floor summarizes it again, which is a count against the model like any other firing. `by="code_fallback"` is a new value beside phase 2's `model` and `code`, on the entry and on the event, so a build can tell the floor from any other code-driven compaction an application appends.

## The arms

`ContextConfig.arm` is one of `tools`, `code_only` and `files`, default `code_only`, and `context_tools.setup(api)` reads it from the harness and registers what the arm carries: under `tools` the five tools and their prompt section, under `code_only` nothing (the floor alone, tau's shape, the control), under `files` one `note(text)` tool whose text is appended to a notes section of the system prompt, always shown and untouched by every compaction because the prompt is never compacted, with each note also written to the session as a `CustomEntry` under `context_notes` so a reloaded session gets its notes back. Letta measured generic file-style memory operations beating a bespoke memory api (D131), which is why the third arm exists and why it has no forget and no recall. The arm is written into the session root's `arm` field when the harness creates the root, so a build's artifacts say which arm produced them; the default is `code_only` rather than `tools` so that a harness whose application never loaded the extension does not record an arm it did not run.

## What is measured, and what is not yet

`harness.context_stats` is a `ContextStats`: `forget_calls`, `recall_calls`, `load_calls`, `unload_calls` and `note_calls` (every call, refused or not, because D131's first number is the model's own triggering rate), `refusals` by rule, `fallback_compactions` and `mechanical_summaries`, and `fill_at_turn_end`, the fill fraction at the end of each turn as the model left it, before the floor ran. The fill list is what the build's numbers are read against, since context rot is continuous and not a cliff (D131). Not measured yet: anything over a real build. The numbers D124 and D131 ask for per agent per build (forget and load counts next to the fallback count, gate pass per round against context fill, cost per round, the three arms compared) need the Builder and the Examiner running on this core, which phases 4 and 5 are doing; this phase is the mechanism and its tests. Nothing here is tuned to a customer or a benchmark: the guards, the line, the cap and the arms are parameters of the core with defaults from the decision log.

## What phases 5 and 6 must call

The `protected` rule bites only if the application says what is protected. A gate ruling the model has not acted on: in the `tool_result` hook that appends the ruling, or in a `tool_execution_end` handler, call `api.protect([api.entry_id_for(call.id)], "unacted ruling: ...")`, and `api.unprotect` the id when the model has acted on it (the next call on the same artifact, or the repair verb that answers it). An open finding from the Examiner: protect the entry the finding refers to when the finding is sent (the follow-up's own entry id is the id of the message once delivered, which `entry_id_for` does not cover; protect the tool result the finding is about, whose id the sender has from its own run), and unprotect when the finding is closed. An unfinished repair: protect the entries the repair reads while it runs. The floor honors the same set, so a protected entry survives a fallback as well as a forget. Without these calls the rules `session_info`, `current_turn` and `recent_tool_output` still hold on their own.

## Tests

`tests/agent/test_context.py` covers the two estimate sources and the stale-usage rule, the record behind a harness and its reload, id uniqueness across reloads, the note off by default and on (with the entry id, without a session, from usage, and after an extension's hook), the floor at the line with the model's summary and with the mechanical one, the floor below the line and switched off, protected entries and the current turn surviving a fallback, recent tool output and whole exchanges, protect and unprotect through the api by tool call id, and the counters. `tests/agent/test_context_tools.py` covers forget dropping entries the model then no longer sees on the wire, a forgotten user message standing where it was, every refusal rule as an `is_error` result naming itself, widening into a guarded entry, forgetting twice, the empty note, recall at the end marked with the original id and its two refusals, the recalled copy being ordinary context the model can forget again, unload then load of a tool and of a skill with the registry, the prompt and the record, the load and unload refusals, the soft cap in the result and the prompt, the index, each arm's tool set with the arm on the session root, and the files arm's note still in the prompt on the turn after the floor fired.

Phases 4 and 7 were built side by side on one tree, so the review that closed this phase ran the suite once both had landed, and the integration check re-read the number once the tree was quiet: 1,643 tests, all passing, `ruff` clean over the whole tree, `lint-imports` keeping all three contracts, and `tests/builder/` with `tests/test_e2e.py` unchanged, which is the check that the note being off by default leaves the build's artifacts alone. That review also retired the last line of phase 2's `tests/agent/test_boundary.py`, which asserted that nothing outside `kullback/agent/` imports the agent core: phase 4 put the Builder on the core, which is what D121 and D123 decided, so the test now asserts what still holds, that only the two application packages and the frontends reach into the core and that `runner/` and `gates/` never do.

## Not done in this phase, on purpose

No token streaming, as in phase 2. The context note's estimate is a heuristic between reported usages and the reported usage itself counts the previous call, so the meter is a guide, not an invoice; the budget still measures spend. The floor asks for one summary and takes what it gets; it does not retry and it does not check the summary's length. A recall returns the entry's text and not its details, since details never entered the context in the first place. The files arm keeps notes in the system prompt and does not cap them; a build that fills the prompt with notes is a result to report, not a case to prevent yet.
