# Phase 5: the Examiner, and the rounds the two agents take turns in

Landed 2026-09-02, the fifth phase of `rebuild-phases.md` (D123, D124, D126, D127, D128, D130, D133). `derive_verifier` left the Builder for `kullback/examiner/`, the probe pool, the loosening gate, the false-rejection number, the refuse verb and the trusted ruling landed in `kullback/gates/`, and `kullback build` now runs rounds: a Builder beat, then an Examiner beat, then `round_end` with the counts the gates report, until the loop is done, stalled or at the ceiling. The verifiers artifact and `task_status.json` the fixture produces are the same bytes as before the phase; `gates.json` and `pipeline/state.json` changed on purpose, and the section on the byte-identical check says how. The first half of this note is the Examiner's side (what moved, the plan and its store, the seven tools, the probe skill, the six gates); the second is the round driver's (`kullback/rounds.py`, the CLI, the TUI, the report).

## What moved, and what stayed in the Builder

`builder/verifier.py` is `examiner/derive.py` and `builder/reference.py` is `examiner/reference.py`, both moved whole: `derive_verifier`, `export_tau2_actions`, the D111 confirmation, the residue judge, the constraint rates and the demotion keep their signatures, and the one edit is that `_helpers_src()` now reads `HELPERS_SRC` from `gates/verifier_suite.py`, where the transcript helpers a compiled Hard predicate calls moved byte for byte so the derivation and the policy compiler read one text without either importing the other (`builder/policy.py` re-exports the name). The body of the old `derive_verifier` stage left `build.py` for `examiner/stage.py` with its helpers (`final_constraints`, `no_reference_status`, `derive_for`, `suite_for`, `verifier_for`, `request_text`, `seed_ids`); `derive_all(ctx, inputs)` is the stage's `run` over an `ExamContext` of three members (`workdir`, `seed_runs` through the anchor, `record_gate` through the ledger), which is all the stage ever used of the pipeline's context, so the same bytes land in `verifiers/`, `task_status.json`, `references.json` and `constraints_check.json`, and `scorecard.json` is rewritten last so it reads as it did when the stage ran inside the pipeline. `inputs_from(store)` is the seam: it keeps `DERIVE_INPUTS` (tasks, sigs, constraints, canon rules, replays, re-rolls, Intents, user rules, traces, assisted tools) and raises on any `FORBIDDEN_INPUTS` name (bodies, db, schema, environment, overlays, synthetic rows, policy text, lessons), so a store that could show the Examiner a tool body never reaches it (D123). The Intent record and `apply_intent` moved into `runner/records.py` (`builder/intent.py` re-exports them) and `GateLedger` into `gates/ledger.py` (`builder/pipeline.py` re-exports it), so both agents record rulings through one class with one lock. What stayed: the replay, intent and rerolls stages, `plan.models` with the loophole probe and the reference judge wrapped as before so `budget.json` keeps its stage names, and the two Environment-executing halves of the old stage as public factories, `build.probe_runner(plan)` and `build.reroll_runner(plan)`, the Runner as a callable the Examiner is handed and never looks inside (D120).

The derivation is pinned by a content hash as well as by the moved tests: `tests/examiner/test_derive.py` holds the hash of `derive_verifier` over `tests/gates/verifier_fixtures.py`'s Runs computed on main at a40812c before the move (`DERIVATION_HASH_ON_MAIN`), because no Task of the small fixture has a confirmed Reference and `verifiers/` is empty on both sides of the snapshot; every test of the old `test_verifier.py` and `test_reference.py` runs unchanged against the new modules.

## The Examiner's plan, its store and the seven tools

`ExaminerPlan` (`examiner/plan.py`) is what one session is given: the Builder's store filtered through `inputs_from`, the Environment id, the probe, judge and re-roll models, the two Runner callables, the probe limit, the anchor, the round and the round's `allowance_remaining`. `load_state` reads back everything the Examiner and the derivation left on disk and builds `store`, the mapping `gates_over` binds a registered gate's artifacts to: `verifiers` (`verifiers/*.json`), `task_status`, `probes` (`probes/<task>/pool.json`, a `ProbePool` per Task), `history` (`examiner/history/<task>.json`, a `VerifierHistory` of every version attempted, accepted or rejected, named by content hash), `refusals` and `findings` (`examiner/refusals.json`, `examiner/findings.json`), `rerolls` (the Builder's rows merged with `examiner/rerolls.json`, the Examiner's own re-rolls, so the legitimate pool grows across rounds, D133), `replays`, `canon_rules`, `sigs` and `task_runs` (every replay and re-roll Run of each Task loaded off disk). All of it persists across builds of the same workdir: a probe stays in its pool (D127) and the history is what makes loosening one-directional over time.

The tools (`examiner/tools.py`) are `AgentTool`s with pydantic arguments and results, and every result carries `produced`, the artifact names the `tool_result` hook runs the bound gates over. `read(kind, id)` is the whole read surface: a Task, a Trace, an Intent, a Run (a replay, a re-roll or a probe), a Verifier, a pool, the task status, the `gates.json` rows, the re-roll and replay rows, the References, as JSON text. `derive(target)` runs `derive_all` for every Task or one, emits `StageStart` and `StageEnd` for `derive_verifier` so the screen still shows the stage line, records the `compile_policy` and `derive_verifier` rulings through the ledger as the pipeline stage did, and appends an accepted `derive` row to each Task's history when the derived hash is new. `probe(task_id, bug_class, note, events, termination_reason, base_run_id)` is a hand-written Run (the Reference's events edited per bug class) scored by `check_run` against the current version and appended to the pool whichever way it scored; it is refused before writing when `probe_admission_gate` says the Task closed. `repair(task_id, reason, drop, add)` builds a candidate from the current atoms, runs the whole D79 suite through `stage.suite_for` (the References, the wrong Run, the alternative path, the Intent text, the user rules, the loophole probe under the probe limit), `probe_pool_gate` over the candidate and `loosening_gate` over the history with the candidate appended as an unaccepted row, and accepts only when all three pass; an accepted candidate replaces `verifiers/<task>.json` and the status row, a rejected one stays in the history with `rejected_by`. `refuse(task_id, reason)` is admitted only when `refuse_gate` finds no finished frontier Run, and an admitted refusal is written to `examiner/refusals.json` and `task_status[task]["refused"]`. `reroll(task_id, count)` buys more frontier Runs through the Builder's callable under the prefix `reroll-r<round>`, refuses when no callable was handed over or the allowance is spent, sets `plan.ceiling_reached` on a `BudgetExceeded`, and lands the rows in `examiner/rerolls.json`. `finding(...)` files a `Finding` for the Builder with a suggested verb and returns the record in `details`. No tool decides a ruling; each calls a registered gate and reports what it said.

`examiner/skills.py` holds the probe skill, catalogued and loaded from the start (D125): the fuzzing paper's eight bug classes (loose answer extraction, missing final-answer markers, numeric-tolerance abuse, schema-only validation, extra-field acceptance, visible-test overfitting, stdout spoofing, missing timeouts), each with one sentence on the edit to the Reference's events that writes it as a Run of this Environment, and the rule that a probe stays in the pool forever. `examiner/extension.py` is built the way the Builder's is, from shapes that live once: `DriverModel`, `drive_tool` and the `refuse_paths` hook factory in `kullback/agent`, `Ruling`, `ruling_line`, `rulings_over` and the protected-path rule (`PROTECTED_PATH`, `names_protected_path`) in `kullback/gates`, `write_json`, `read_json` and `rules_of` in `kullback/runner`. Its own part is the seven tools, three prompt sections (what the Examiner is, its rules, the Tasks of this build), two `tool_call` hooks (`examiner_reads_only_its_surface`, which raises on any argument naming `bodies.json`, `env`, `sandbox`, `environment.json`, `db.json`, `schema.json`, `overlays`, `tools` or a path under `kullback/gates` or `kullback/runner`; and `repair_guard`, which protects the newest read of the Task while a repair runs) and the `gate_rulings` `tool_result` hook, which runs the gates bound to what the tool produced, appends the rulings, protects a result carrying a failed ruling as an unacted ruling until the next derive, repair, probe or refuse on the same Task lands, and protects the entry a finding is about until the driver closes it (D124, D131). `examiner/agent.py` is the session driver on the Builder's pattern: `examiner_harness`, `run_examiner`, the core's `drive_tool` under the Examiner driver's call id, and `ExaminerError` when a model never called derive.

## The six gates, and the records they rule over

Every rule of the phase is a pure function in `kullback/gates` registered in `GATES` with its artifact bindings (D122): 40 specs over 50 ruling names, from phase 4's 34 over 44, the six new names being the six gates below. `probes.py`: `probe_pool_gate` rescores every probe ever written for a Task against its current version and fails per probe that scores a pass, naming the probe, its bug class and the version hash (D127, monotone); `probe_admission_gate` closes a Task after `PROBE_STOP` (3) consecutive probes written against the current version that it already rejected, an accepted repair starting a new tail (D133). `loosening.py`: `legitimate_runs` is the confirmed replays plus every re-roll row whose termination is a success termination, built by code from the Runner's records and never from a model; `loosening_gate` compares the newest attempt in a Task's history against the last accepted version before it and fails per Run newly passed that is not in that pool, a first version having nothing to loosen from; `false_rejection` and `false_rejection_gate` measure, per Task, the fraction of held-out legitimate Runs (not among the Verifier's seeds) the required atoms reject, `None` when nothing is held out, and fail only for a Verifier that rejects every held-out frontier Run. The Hard atoms are left out of that scoring on purpose: a frontier Run that broke the policy is rightly rejected, and counting it would let a Verifier's Hard atoms look like a false rejection the Examiner should repair away. `trust.py`: `refuse_gate` admits a refusal only when `finished_runs` is empty (the solvability judge of D128 as code) and `trusted_gate` calls a Verifier trusted when it passed the D79 suite, rejects every probe in its pool, is the last accepted version of its history and its Task is not refused, with the false-rejection number per Task in its metrics. `round_end.py`: `round_counts`, `done`, `stalled` and `exit_for`, the driver's section below. The records are in `runner/records.py`: `Probe`, `ProbePool`, `VerifierVersion`, `VerifierHistory`, `Refusal`, `Finding`, `RoundRecord`, and `Intent` with `IntentSpan` and `apply_intent` moved in; `Verifier.verifier_version` now counts attempts per Task and the content hash names a version everywhere.

## One stream, four beats, one agent at a time

`rounds.run_rounds(workdir, model, ...)` is what `kullback build` calls. It builds one `BuildPlan`, one Builder harness over it (the phase 4 extension, driven by code or by `agent_model`) and one `Loop`, and runs `Loop.round(n)` from 1 until a round ends with an exit. A round is `RoundStart`, a Builder beat, an Examiner beat, the counts, `RoundEnd`; a beat is `BeatStart(agent, round)`, the agent's work, `BeatEnd(agent, round, spend)`. All four are typed events of the agent core's union (`agent/events.py` gained `BeatStart` and `BeatEnd`, and `RoundEnd` gained `exit`), and every subscriber the caller hands the driver is attached to both harnesses before any event, so a screen or a test sees one stream in the order things happened: the Builder's stage events sit between its `BeatStart` and `BeatEnd`, the Examiner's between its own, and nothing of one agent's is emitted inside the other's beat. The same events reach the dict stream the TUI reads (`{"kind": "round", ...}`, `{"kind": "beat", ...}`), and the Examiner's stage events are mapped to the `{"kind": "stage", ...}` dicts the pipeline already emits so a screen that knew the Builder's stages needs nothing new to show the Examiner's.

D128 is enforced in the driver, not asked of the model: `builder_beat` raises `RuntimeError("the Examiner is still running; one agent at a time (D128)")` before it emits anything when the Examiner harness is mid-run, and `examiner_beat` does the same the other way round. A test calls one beat from inside a subscriber of the other harness's run and reads the refusal. The Examiner's harness is opened on the first Examiner beat, with the plan's `ExaminerPlan` over the Builder's store, and kept across rounds; each round sets `plan.round`, refreshes the plan's inputs from the Builder's current store, and hands the plan the round's allowance before the beat starts.

What the Examiner is handed is the Builder's store filtered through `examiner.stage.DERIVE_INPUTS`: the Tasks, traces, Intents, replay and re-roll rows, the canon rules, the tool signatures and the References. `bodies`, `db`, `schema` and `environment` are never in it, and `ExaminerPlan` refuses a store that names them (D123: the Examiner never reads tool bodies or the Environment, and the Builder never writes a Verifier or a probe). The Runner the Examiner's probe and re-roll tools use is a callable the Builder built over its own store (`build.probe_runner`, `build.reroll_runner`), so the Examiner runs Runs without seeing what runs them.

## Two drivers, and what `--agent` changes

Without `--agent` the driver issues the tool calls itself through each harness's hooks and registry, with no model turn, the way phase 4's Builder driver does. The Builder beat is `build(target)`; the Examiner beat is `derive(target="all")`. The harness's model is a `DriverModel` whose `query` raises, so a model turn on that path is a bug that shows. This is the path the CLI takes by default and the reason the fixture's artifacts are the same bytes through the loop as through `build.build()`.

With `--agent` (which needs `--model`) the one model drives both sessions. On round 1 the Builder is prompted with the same words phase 4 used and the Examiner with one message asking it to call `derive` with target `all`, read the rulings, then probe, repair, refuse or send a finding as they tell it; on later rounds each is steered with a one-line round message and continued, so the transcript is one session per agent across rounds, written to `builder/session.jsonl` and `examiner/session.jsonl` in the workdir. A model-driven Builder that ends its beat without a build result, or with an error result, fails the round with `BuildError`, the way a model-driven session in phase 4 did.

## The findings, drained into the Builder as follow-ups

The Examiner files what is wrong on the Builder's side with its `finding` tool (an assisted tool, a fidelity gap, a Reference the re-rolls disagree with, an Environment fault), and the record is a `Finding` in `runner/records.py` with a `suggested` verb (`compile_tool`, `replay`, `reroll` or `none`). The driver collects every `Finding` off the Examiner's `ToolExecutionEnd` events and holds it as pending until the next Builder beat. There the code driver acts on it by calling the Builder tool it names (`compile_tool(name=...)` or `replay(task=...)` or `reroll(task=...)`) before the build of the target; the model driver delivers it as a follow-up, one user message per finding with the Finding record in the message's `details` and a short text naming it, after a steer that says the findings follow. The record travels as data and never enters the model's context (D123); the text does. Once delivered, the finding is closed through `ExaminerPlan.close_findings`, which also releases the Examiner's session entry the finding protected (D124, D131), and the round's counts list the ids that were sent.

## The counts, and where every number comes from

`round_end` is computed by `gates.round_end.round_counts` over the Examiner's store after its beat: fidelity, tasks, tasks with a Reference, trusted (and the ids), refused (and the reasons), assisted runs, probes passing, false rejection per Task, and the unfinished Tasks. The driver adds only the three numbers no gate can know: the fallback compactions per agent this round (the phase 7 counter, read off each harness's context stats as a delta), the spend per agent this round (the budget ledger's total, read before and after each beat) and the finding ids sent. The `trusted` ruling the counts rest on is recorded in `gates.json` through the Examiner's ledger; a ruling with an equal row already in the file is not recorded twice, so the Builder's `replay_reference` row keeps its place and the file's order is the reference order with the new rows appended. The counts are on the `RoundEnd` event, in `rounds.json` (one `RoundRecord` per round, the exit on the last) and in the dict the driver returns, and a test checks they are the same three ways.

## The three exits, `stall_rounds` and the allowance

`gates.round_end.exit_for` decides, in this order: `ceiling` when the Builder's last result carries a stop (the pipeline's `BudgetStop`), when the Examiner's plan says it reached the ceiling, or when the allowance was exhausted two rounds in a row; `done` when the state holds after the round (no Task unfinished and no probe passing); `stalled` when the last `stall_rounds + 1` rounds moved none of the gate counts in either direction. `stall_rounds` defaults to 1, so two rounds that moved nothing end the loop; `--stall-rounds 2` waits one more, which is the experiment D126 keeps open. On the fixture no Task has a confirmed Reference, so the loop is `done` after round 1, and the stalled and ceiling exits are pinned at the `Loop` level on hand-made rounds.

The allowance is per agent and per round (D126). `--allowance-usd` sets it; without it, round 1 runs unbounded and each later round's allowance is what that agent spent in round 1 (a round-1 spend of zero means no allowance). The Examiner's plan reads `allowance_remaining` before each beat and its re-roll tool refuses at or below zero; a model-driven agent whose spend crosses the allowance mid-beat is steered once, after the tool batch, with "Your allowance for this round is spent: finish with what you have (D123)", and not stopped. A round in which either agent reached its allowance counts as exhausted; two in a row is the ceiling exit.

## The CLI, the TUI and the report

`kullback build` gained `--stall-rounds` and `--allowance-usd`, calls `rounds.run_rounds` with `agent_model` set to the model only under `--agent`, prints one line per round as each ends (`round N: fidelity a/b tasks, trusted c, refused d, assisted runs e, probes passing f, compactions builder g examiner h, spend $x.xxxx`), then `exit: done|stalled|ceiling after N round(s)`, then the result as JSON. The result is the Builder's dict (status, workdir, env_id, gates, tasks, target, rulings, tool_result) plus `rounds`, `exit`, `trusted`, `refused` and `examiner` (its last rulings and its last tool result).

The TUI's board shows `round N, <agent> beat` above the stages while a beat runs, a table with one row per finished round (round, fidelity, trusted, refused, probes passing, spend, exit) once a round has ended, and `/status` reads `rounds.json` beside `pipeline/state.json`. `/build` goes through `rounds.run_rounds`, the entry the CLI uses.

The report gained a `## Rounds` section after `## Environment` with the same table plus assisted runs, and three headline lines when rounds exist: how many Tasks have a trusted Verifier with the false-rejection number per Task beside it (D133, off the last `trusted` ruling in `gates.json`), how many Tasks were refused and why, and, on a stalled exit, which Tasks need a person. Each Task's block says whether its Verifier is trusted (and if not, why) and the share of held-out frontier Runs its required atoms rejected. A `rounds.json` that is not a list of `RoundRecord` is named under the records the report could not read.

## The byte-identical check

The integrated tree runs the fixture through `rounds.run_rounds(model=Bodies(), max_attempts=0)` with `INGEST_VERSION` pinned, and every file of the result is compared by content hash against the phase 4 snapshot made through `run_builder`. 260 files are the same bytes, `task_status.json`, the (empty) verifiers, `references.json`, `constraints_check.json`, `scorecard.json`, `replays.json`, `tasks.json`, `bodies.json`, `environment.json` and the 18 files under `runs/`, `tasks/`, `intents/` and `user_rules/` among them. The differences are the permitted ones: `budget.json` differs only in `wall_ms` (the total's and each stage's); the seven sandbox `out.json` files carry their nonces; `pipeline/state.json` is the new shape; `gates.json` has the reference rows in the reference order with one new row, `trusted`, appended (the probe, loosening, false-rejection and refuse rulings write nothing on a fixture with no confirmed Reference); ten `cache/` entries are renamed with equal contents because the stage code that keys them changed, and the `derive_verifier` entry is gone because the stage is not the Builder's; the model cache has the same 174 entries with seven under different names; and `builder/session.jsonl`, `examiner/session.jsonl` and `rounds.json` are new. `rounds.json` on the fixture holds one round, `exit: done`, fidelity 2 of 3 Tasks, no Task with a Reference. Two things the comparison taught: the replay rows embed the absolute path of the workdir, so a build made under another directory shows `replays.json` and the replay and re-roll cache entries as differing by that prefix alone (the close re-ran the snapshot under the reference's own directory and they are equal by hash); and a cache entry's name carries the stage's source, so the deduplication pass that moved `read_json`, `write_json` and `rules_of` into `runner/` kept their alias names inside `build.py`'s stage bodies on purpose, since renaming them would have moved every cache entry once more. `tests/test_rounds.py` pins both halves of the claim in code: the `task_status.json` the code-driven rounds leave has the sha256 recorded before the phase (`e6ec7ca50f375163805c0651745c411d39d45bfa8dfe9a2e59ba5bcea335cd73`), and the Examiner's round-end rulings are appended after the Builder's rows without moving any (the Builder's rows minus `compile_policy` a strict prefix, the tail `compile_policy`, `derive_verifier`, `trusted`, the `compile_policy` row equal to the Builder's since `GateLedger.record` replaces a same-named row the way the pre-phase stage did, and `replay_reference` once). The suite at the close, 2026-09-03: 1,815 collected, 1811 passed, 4 skipped (the raw-data and vendor skips) in 161 seconds, `ruff` clean, the three import contracts kept, and the comparison re-run through `snapshot_driver_phase5.py` and `phase5_compare.py` with the verdict above: 260 files equal by hash, verifiers and `task_status.json` byte-identical, nothing outside the permitted list.

## Not done in this phase, on purpose

No repair verb on the Builder: a finding whose answer is a recompile or a rewrite waits for phase 6, and the code driver acts on a finding only through the three tools the Builder already has (`compile_tool`, `replay`, `reroll`). No concurrent agents: D128's turn-taking is enforced by the two `RuntimeError`s, and the signal that would reopen it (the Examiner idle for most of the Builder's beat) is not measured. The false-rejection number is reported and never acted on, and its gate fails only the single-path Verifier, because D133 says no paper names the threshold. The Examiner's own re-rolls go through the Builder's callable, so a Task the Builder never built an Environment for (a narrowed target) gets no probe and no re-roll rather than a Runner of the Examiner's own. `seed_ids` exists twice, in `build.py` and in `examiner/stage.py`, because the Builder's catches the pipeline's error and the Examiner's context never raises, and folding them would import the pipeline into the Examiner. The fixture confirms no Reference, so the probe, loosening, refuse and false-rejection rulings are exercised by the hand-built worlds in the tests and write no row on the snapshot; the first live build with a confirmed Reference is where those four gates first appear in a `gates.json`. Phase 4's two recorded gaps stand: the `artifacts.py` five are still registered beside `tool_runs.py`, and `compile_tools` still overwrites `gates.json`.

## What phase 6 builds on, and what stays open

The repair verbs, the ratchet and the lesson attach to the Builder beat: a finding's `suggested` verb is already the code driver's action, and the model driver already delivers findings as follow-ups, so the verbs land as tools and hooks without touching the loop. The allowance's size in dollars (D126) and `stall_rounds` 1 against 2 are experiments the driver exposes as flags and does not decide. The fallback-compaction count per agent per round is on every `round_end` now, which is the number the phase 7 experiment (D124) waits for; nothing reads it yet beyond the CLI line.
