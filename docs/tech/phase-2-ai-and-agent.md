# Phase 2: `ai` and `agent`

Landed 2026-09-02, the second phase of `rebuild-phases.md` (D120 to D124, D128, D130, D131). `ai/` gains a provider-neutral stream over today's `Model.query`, and `kullback/agent/` is filled: messages, tools, typed events, the stateless loop, the harness, the session tree and the extension api, with 64 tests (56 under `tests/agent/`, 8 for the stream under `tests/ai/`) that assert on the events a run emits. Nothing outside `kullback/agent/` and `kullback/ai/stream.py` imports any of it, and a test says so by walking the package's imports; `MemoModel`, `RecordedModel` and `TestModel` are untouched and their tests pass as they were. No artifact changes, because no build goes through the new code yet. The shape follows huggingface/tau's `tau_agent`, read the same day, with pydantic models where tau has dataclasses and with the pieces later phases need (stage, round, compaction and custom-message events; tool-set, skill and compaction entries) carried as types now so those phases add emitters rather than vocabulary.

## Where the messages live

The transcript's four types, `UserMessage`, `AssistantMessage`, `ToolResultMessage` and `ToolCall`, with the `Message` union discriminated on `role`, are defined in `kullback/ai/messages.py` and re-exported by `kullback/agent/messages.py`. The brief left the choice open between that and a stream generic over whatever message type the caller passes. The stream assembles an `AssistantMessage` from a `ModelReply` and reads the transcript it is asked to continue, and `ai` may not import `agent` (D121), so the types either sit in `ai` or become a type parameter on every stream event for exactly one concrete type. One module and a re-export is the smaller shape, and it keeps `ai` what phase 1 made it: it owns `Usage` already, and a message is the same kind of thing, the record of what crossed the wire. Everything above `ai` reads them from `kullback.agent.messages`.

`to_wire` in the same module turns the typed transcript into the dict list `Model.query` takes, the system prompt first as a system message, so the adapters, the memo cache and the recorded model see exactly the shape they saw before. Two things never reach the wire. `details`, on a user message or a tool result, is dropped: it is where a structured record rides next to the text the model reads (a gate ruling, a Run, the Examiner's `gates.json`, D123), and the whole point of the field is that it does not cost context. An assistant message that ended in error with neither text nor tool calls is left out too; it stays in the transcript as the record of what happened, but no provider accepts an empty assistant turn and it would poison the next request.

## The stream

`kullback/ai/stream.py` is tau's `AssistantMessageEvent` shape: `start`, then text and tool-call blocks each opened, filled by deltas and closed (`text_start`, `text_delta`, `text_end`, `toolcall_start`, `toolcall_delta`, `toolcall_end`), then `done` with the assembled message and one of four stop reasons (`stop`, `tool_use`, `length`, `error`), or `error` carrying an assistant message with `stop_reason="error"`. Every event before `done` carries the partial message as assembled so far, so a consumer can render without keeping its own copy. The provider's own words for why it stopped (`end_turn`, `tool_calls`, `max_tokens`, and so on) are folded onto the four in one table, and when the word is unknown the reply's shape decides: tool calls mean `tool_use`, otherwise `stop`.

In this phase every provider still answers whole, so `stream(model, messages, tools, system, config)` calls `Model.query` once, in a worker thread so the event loop is not held by the network wait, and then emits the assembled events at once: one delta per text block, one delta per tool call. That is enough for the loop, the harness and every test, and it is what keeps the three offline models working through the stream unchanged, since each is a plain `Model.query` and the thread is where it is called. A token stream is a later change to this one file; the loop and the events already read the stream and never the reply. A provider exception becomes an `error` event rather than escaping, so the loop can record it in the transcript and end the run cleanly; a cancellation of the awaiting task does escape, because that is the caller stopping the run. A tool call the provider did not name (scripted replies rarely do) gets an id from its position and the transcript length, deterministic so the memo cache keys the same request the same way twice.

## Tools

`AgentTool` is generic over an args model and a result model: a name, a description, the two pydantic classes and an async executor from one to the other. The JSON schema the provider sees is `args_model.model_json_schema()`, so the schema and the validation cannot disagree. `run(arguments)` validates the arguments before the executor runs and a failure is a `ToolResult` with `is_error` set, in words the model can act on (`invalid arguments for add: a: Input should be a valid integer`), never an exception out of the loop; the executor's own exception is an error result the same way, since a tool is an isolation boundary; and the result is validated against the result model before it enters the transcript, so a tool that returns the wrong shape is recorded as an error result rather than crashing the run. What the model reads is the validated result as JSON, unless the tool gives a `render` function, in which case the model reads its short account and the full result stays in `details`; that is how a tool whose result is large (a Run) stays out of the context without being lost. `ToolRegistry` holds tools by name, refuses a duplicate, and renders their schemas in the provider-neutral shape (`name`, `description`, `input_schema`) both adapters already accept; `remove` is there for phase 7's `unload`.

## Events

`kullback/agent/events.py` is the typed union, discriminated on `type`: `agent_start`, `agent_end` (with the messages the run appended), `turn_start`, `turn_end` (the assistant message and its tool results), `message_start`, `message_update` (one stream event with the partial), `message_end`, `tool_execution_start`, `tool_execution_update`, `tool_execution_end`, `stage_start`, `stage_end` (name and counts, for phase 4's scheduler), `round_start`, `round_end` (counts as a dict, all from gates and none from a model, filled in phase 5), `error`, `compaction` (phase 7, with whether the model or the code did it), and `custom_message` (content enters the context, details does not). Every state change in a run is one of these, and that is the rule that makes the rest work: a frontend, a session store or a test reads the stream and never the loop's internals, and two agents can take turns on one stream (D128) because the stream is the whole story.

## The loop

`run_agent_loop(state, model, tools, hooks, emit, prompts)` is a stateless async function. It holds nothing between calls; everything it reads and writes is on the `LoopState` it is handed (the transcript as a list mutated in place, the system prompt, the two queues, the cancel flag, the model config, an optional turn cap), and everything it does it emits. The transcript is the source of truth: `agent_end` reports the messages the run appended, but the list on the state is the record, and a second run over the same list continues where the first stopped.

A turn is one assistant message through the stream (`message_start` with the first partial, a `message_update` per stream event, `message_end` with the final message), then its tool calls executed sequentially in the order the model asked, each as `tool_execution_start`, the tool, `tool_execution_end`, and the result appended as a `ToolResultMessage` with its own message events; then `turn_end`. Sequential rather than parallel because the tools this core will carry write one workdir and one budget (D118's parallelism is inside a stage, not between tools), and because the transcript's order is then the execution order, which is what a replay wants.

The two queues differ by when they are read, and that timing is the design. After each tool batch the steering queue is drained whole and its messages are appended as user messages before the next assistant turn: a steer reaches the model at the earliest point where a message can be inserted without separating a call from its result. A ceiling hit is a steer (D123). When the model stops without tool calls, the follow-up queue is drained one message at a time and each starts another turn with its own tool loop; a follow-up is delivered only when the run would otherwise end, which is what the Examiner's findings want (D123) and what a scheduler's next target will want in phase 4. A steer interrupts; a follow-up waits. The same holds for messages queued before a run starts: a steer goes in with the prompt, a follow-up is held for the end.

Hooks are lists on a `Hooks` object, applied in registration order, sync or async. A `tool_call` hook sees the call and may return rewritten arguments (the tool runs on them; `tool_execution_start` still shows what the model asked), return `None` to leave them, or raise; a raise blocks the call and the model reads an `is_error` result naming the hook and its message (`add blocked by no_writes: gates/ is read-only`). That is fail-safe by construction, a hook that crashes blocks rather than lets through, and it is why the D122 write block on `gates/` and `runner/` will be one raising hook in phase 4. A `tool_result` hook sees the call and the `ToolResult` and may return a rewritten one, which is how a gate's ruling reaches the model appended to the result it is about to read, with the structured ruling in `details` (D123); a `tool_result` hook that raises fails that result, keeping the tool's `details`, and the run continues, on the same reasoning. A call to a tool the registry does not hold is an error result too. Cancellation is a flag on the state: the loop reads it before each model call and before each tool, so a cancelled run ends with an error assistant message and the rest of its batch marked not run, and nothing is half-written.

## The harness

`AgentHarness` is the one stateful object. It owns the transcript between runs, the `ToolRegistry`, the hooks, the system prompt's named sections, the two queues and the subscribers. `prompt(text)` and `continue_()` return an async iterator of events for the caller while every event is also pushed to the subscribers, in the same order, through one queue; a subscriber that raises stops the run, which is the right default for a session store that could not write. `steer`, `follow_up` and `send_message(content, details, deliver_as)` queue whether or not a run is on, and `send_message` emits `custom_message` at queue time so the stream shows both moments, the sending and the delivery. `cancel()` sets the running state's flag. One run at a time: a second `prompt` while one runs is refused, tau's rule and the discipline turn-taking gives two harnesses on one workdir for free (D128). Before each run the harness answers any tool call the transcript left dangling (a cancel between a call and its result) with an interrupted error result, through the events, so the transcript stays valid on the wire without rewriting history.

## The session tree

`kullback/agent/session/` is an append-only JSONL store. Every line is an entry with `id`, `parent_id`, `timestamp` and a `type`: `session_info` (the root), `message`, `tool_set_change` (names loaded and unloaded, since tool schemas are context too), `skill_change` (name, load or unload or edit, and the content hash that says which text was in context, D125), `compaction` (summary, `replaces_entry_ids`, `first_kept_entry_id`, and whether the model or the code wrote it, D124), `custom` (application data under a namespace), and `leaf`, the pointer. `append` hangs an entry under the current leaf and makes it the leaf; `branch(entry_id)` writes a leaf line pointing at an earlier entry, so the next append forks from there and the old branch stays on disk; `load` replays the file and refuses a duplicate id, a missing parent or a leaf that points nowhere. `active_path()` is the root-to-leaf walk with compactions applied: the entries a compaction replaces drop out and the compaction stands where the first of them stood, so the summary reads at the point in the history it summarizes, and `active_messages()` is that path as messages with the summary as a marked user message. What a compaction replaces is its `replaces_entry_ids`, the list the model chose in a `forget` (D124), plus everything on the path before `first_kept_entry_id` when that is set, which is how the code fallback compacts, tau's way, by a prefix; the root `session_info` is never replaced whichever way it was named. Nothing is ever deleted, which is what makes a wrong forget cost one recall: `get(entry_id)` reads a replaced entry back from the record.

## Extensions

An extension is a `setup(api)` callable. `ExtensionAPI` offers `register_tool`, `add_prompt_section(name, text, position)`, `on(event_type, handler)` returning the unsubscribe, `tool_call` and `tool_result` to install hooks, and `send_message`. The system prompt is the sections joined in order with a blank line between; a section with the same name replaces in place, a position inserts, no position appends. `load_extensions(harness, setups)` runs them in order against one api. The Builder and the Examiner are extensions on this api (D123, ADR-0007), each with its own harness, session and prompt; a customer workdir may carry skills, which are text, and never an extension, which is code.

## The fake provider

There is no `kullback/ai/fake.py`. `TestModel` scripts replies in order, takes tool calls, records every call it saw, and refuses to answer when it has run out, which is everything the loop's tests need, and every test in `tests/agent/` runs on it. Adding a second scripted model at the stream level would have been a copy with a different name.

## Not done in this phase, on purpose

Token streaming: the stream emits assembled events, and a real delta stream is a change to `stream.py` only. The context tools (`forget`, `recall`, `load`, `unload`) and the 40% line with its code fallback (D124, D131): the entries and the `compaction` event exist and `active_path` applies them, but nothing appends a compaction yet and no context estimate is computed. `tool_execution_update` is declared and never emitted, since no tool reports progress yet. Timing on the assistant message (tau records time to first output) is not carried; the budget already measures wall clock per stage. Parallel tool execution is not offered and will not be unless a tool that is safe to run beside another appears.

## What phase 4 builds on

The Builder becomes an extension: its stages become `AgentTool`s with pydantic args and results (`recluster`, `grow`, `compile_tool`, `replay`, `reroll`, `build`), `builder/pipeline.py` emits `stage_start` and `stage_end` around each, the gates of phase 3 run inside `tool_result` hooks and append their ruling to the result, one raising `tool_call` hook blocks any write into `gates/` or `runner/`, and the run is one `build(target)` call through the harness with the repair verbs off (phase 4 landed with code issuing that call, so `kullback build` takes no model turn and stays deterministic, and kept `harness.prompt` for the `--agent` path). The comparison against phase 3's artifacts is that phase's test. Phase 5 gives the Examiner its own harness and session on the same core, with its findings reaching the Builder as follow-ups and the ceiling as a steer. Phase 7 puts the context tools on `SessionStore` and starts emitting `compaction`.
