# Phase 4: the Builder as an extension, targets over the DAG

Landed 2026-09-02, the fourth phase of `rebuild-phases.md` (D120, D122, D123, D128). No artifact changed. `builder/pipeline.py` is now a scheduler over a declared graph, the Builder's stages are tools of the agent core with pydantic arguments, the gates rule inside a `tool_result` hook, a raising `tool_call` hook refuses any write into `kullback/gates` or `kullback/runner`, and `kullback build` runs one Builder session that issues `build(target="environment")` without a model turn. The twelve rulings the build recorded outside the registry after phase 3 are registered, so the set of rulings written to disk by code the registry does not know is empty. The build over the fixture produces the same bytes as before the phase, under the permitted differences and one renamed stage, whether it goes through `build.build()` or through the Builder's tool; that comparison is the phase's test.

## The graph is declared once and the scheduler decides the order

`build.py` used to hold two hand-ordered lists, the fresh build's and the iterated build's, and the pipeline walked whichever it was given from top to bottom. It now holds one declaration, `stages(plan, ...)`, of the fifteen stages with what each reads and writes: ingest (when there are files), mine, cluster, canon_rules, starting_state, compile_tools, compile_policy, judge_lessons, intent, vocabulary, user_rules, build_environment, replay_reference, rerolls and derive_verifier. The list is in the order a reader meets the stages, not the order they run. `Pipeline._deps` reads the order off the declaration: a stage depends on the producer of every artifact it reads, and every stage that is not upstream of the anchor's source also depends on the stage that produces it, so that the anchor is drawn from the Tasks the moment they land (D81) and no Builder stage seeds its Runs before it exists. A topological sort over those edges is the schedule; `run(targets=...)` takes the closure of the targets over the same edges, so a target is resolved by its stale inputs first and its current ones come from the cache without the caller ordering anything (D120). A target is a stage name or an artifact name, and a name that is neither is refused with a `GraphError` before anything runs.

At `workers=1` the scheduler takes the first ready stage in topological order each time, which is the order the old lists implied, and that is why the artifacts are the same bytes: the cache key of a stage is its code, its inputs, its paths and the anchor, none of which the scheduling touches. Above one worker the ready stages run on a `ThreadPoolExecutor` and the scheduler waits on the first to finish, applies its outcome on its own thread (the store, the state, the anchor, the events) and starts whatever became ready; the outcomes are applied in the order they complete, but everything a stage writes goes through the store or through `GateLedger`, which locks and replays the rulings in stage order, so `gates.json` and `pipeline/state.json` are the same at two workers as at one, and a test says so. A `BudgetStop` (D86) raised on a worker thread ends the run as before: the stage is `stopped`, nothing downstream starts, the stages already in flight finish. The `workers` count the CLI already had for items inside a stage now also bounds the stages side by side, which is D118 at the stage level; the budget ledger has one lock, so a ceiling is still one number.

Each stage emits the agent core's typed `StageStart(name)` when it starts and `StageEnd(name, counts)` when it ends, with `status`, `cached`, `attempts`, `rulings`, `elapsed_ms` and `produced` in the counts, through the `emit` callable the pipeline is given; a callback that raises is swallowed so a listener can never fail a build. The dict events the TUI reads are still emitted on `on_event` unchanged, and the TUI's board also accepts the typed events, converting them to the dicts it already knew. The state file gained nothing: `statuses`, `attempts`, `gates`, `log`, `failed_stage`, `stopped` and the mermaid graph are written as before, the mermaid now from one fifteen-node graph rather than two lists.

## The stages as tools, and what a result exposes

`builder/tools.py` gives the harness six `AgentTool`s over one `BuildPlan`: `build(target)` in the general form, and `recluster()`, `grow(table, count)`, `compile_tool(name)`, `replay(task)` and `reroll(task)` as the verbs a session reaches for by name, with a pydantic model each so the schema the model sees and the validation cannot disagree, and `count >= 1` refused by the model rather than by the stage. Every one of them calls `build.execute(plan, target, **narrowing)` on a worker thread so the event loop stays free: `recluster` targets `cluster`, `grow` targets `starting_state` with the table's count overriding the plan's growth targets (D107), `compile_tool` targets `compile_tools` narrowed to the named tool and merges its body and its build record into `bodies.json` and `tool_builds.json` so every other tool keeps its body, `replay` targets `replay_reference` narrowed to one Task and merges into `replays.json`, `reroll` targets `rerolls` narrowed to one Task (D112). There is no repair verb: the Builder does not edit code (D122), and the prompt says so in as many words.

A result is `BuildResult`: a one-line summary, the target, the pipeline's status, `passed` (complete and every ruling passed), the rulings as `Ruling(stage, passed, failures)`, one `StageReport` per stage that was considered, the artifacts produced, the failed stage and the stop record when there is one, and a `payload` with the workdir, the environment id, the Task ids and the names of the rulings recorded. What the model reads is `render(result)`: the summary, one line naming the stages that ran with `cached` where the cache served them, one line of ruling names with pass or fail and the first failure of a failed one, then the failed stage or the stop. Everything else reaches the transcript's `details` and never enters the context, which is D123's point: a Run or a set of bodies is data, not prose.

## The two hooks

`builder/extension.py` is the `setup(api)` the harness loads. It registers the six tools with the harness's `emit` as their event sink, so the pipeline's stage events reach the harness's stream in order (each event is handed to the loop from the build's thread and waited for, so the stream carries them in the order the stages emitted them rather than in the order the loop got round to them; a subscriber that raises still cannot stop a build, because the exception travels back to `Pipeline._emit_typed`, which drops it), adds three prompt sections (what the Builder is, what it may and may not do, the target vocabulary of this plan's graph, computed from the declaration so it is never stale), and installs the two hooks.

The `tool_result` hook runs after a tool returns with what it produced in `details`. For every produced artifact it looks up `gates_over(artifact)`, the registered gates bound to that artifact, runs each once over the plan's store (a gate over two artifacts runs when both are there) and appends a `gate rulings:` line to the content the model reads and the rulings as records to `details["gate_rulings"]`. It writes nothing: the stages already recorded the same rulings in `gates.json` and `state.json` on their way, so the hook reports what the registry says about the artifacts and the on-disk record stays the stage's. A test compares the hook's rulings to what is on disk, ruling by ruling, and documents the one gap: compile_tools overwrites `gates.json` with its per-tool sandbox rulings, so the cluster ruling recorded before it is dropped from the file (it was before this phase too) while the hook still reports it.

The `tool_call` hook walks a call's arguments through dicts and lists and raises `PermissionError` on the first string that names a path segment `gates/` or `runner/`, bare or under `kullback/`, at the start of a value or after a separator (`gates.json`, `runs/` and `runner_version.json` do not match). A relative path, an absolute one and one with `..` in the middle all name the same segment and are all refused. The package directory named with nothing after it (`rm -r kullback/gates`) is refused too, which the segment rule alone would miss for want of a trailing separator; that second form asks for the `kullback/` prefix, so a bare word `gates` or `runner` as an argument value stays an ordinary string. The loop turns the raise into `write_file blocked by no_agent_writes_gates_or_runner: ...` with `is_error` set and the tool never runs. This is D122 in code: the gates and the Runner are packages no agent writes, and a rule the prompt states can be argued with while a hook cannot. The test registers a dummy `write_file` tool beside the Builder's and shows the blocked paths blocked and `kullback/builder/x.py`, `gates.json` and the workdir's own files allowed, on the loop's path and on the driver's, which agree. `builder/memory.py`'s read-only list names `kullback/gates/` and `kullback/runner/` for the same reason, so no lesson may propose editing them either.

## Driven by code or by a model, and why the CLI stays deterministic

`builder/agent.py` holds `run_builder(workdir, model, target, agent_model=None, ...)`. It builds one `BuildPlan`, one harness with the Builder extension over it and the subscribers attached before any event, and then takes one of two paths. Without an agent model the driver issues `build(target)` itself through the harness's hooks and registry, in the order the loop keeps (every `tool_call` hook, the tool, every `tool_result` hook, then a `ToolExecutionEnd` on the stream), with no model turn: the harness's model is a `DriverModel` whose `query` raises, so a model turn in that path is a bug that shows. That is what `kullback build` does, and it is why the workdir the CLI leaves is byte-identical to `build.build()`'s: the same plan, the same stages, the same gates, the same bytes, plus the events. The line the CLI prints gained three keys on the dict `build.build()` returned, `target`, `rulings` and `tool_result`, which is what a caller needs to see that the build went through the tool and what the gates said about it. With an agent model (`kullback build --agent`, which needs `--model`) the harness is sent one message asking for `build(target)` and the model drives; a scripted `TestModel` in the tests takes that path, and the artifacts it leaves are compared to the driver's file by file. `--target` picks the stage or artifact; the default is the whole build. The loop's own execution of a tool call is not public, so the driver applies the hooks the way the loop does and a test pins that they agree; if the core grows a public `execute(call)` the driver should call it.

The reason for a code driver rather than a model that always drives is D128 and the sentence in the phase plan: the Builder runs with one message and repair verbs off. A model that chooses the target adds nothing to a build that has one target, costs a turn, and makes the artifacts depend on what the model said. The model-driven path exists so phases 5 and 6, where the Examiner's findings reach the Builder as follow-ups and there are verbs to choose between, run on the same harness, the same tools and the same hooks the CLI already exercises.

## Which rulings are registered, and what sits outside

Phase 3 pinned twelve `stage` values the build wrote to `gates.json` or `state.json` from code outside the registry: `cluster`, `parses`, `executes_on_s0`, `deterministic`, `non_trivial`, `replay_fidelity`, `refuses_unknown`, `compile_tools`, `intent`, `vocabulary`, `rerolls` and `derive_verifier` (with `tau2_export` recorded by the exporter). All of them are now registered. The six sandbox rulings live in `kullback/gates/tool_runs.py` as pure functions over the sandbox's results (`body_parses_gate`, `body_executes_gate`, `body_deterministic_gate`, `body_non_trivial_gate`, `body_replay_fidelity_gate`, `body_refuses_unknown_gate`), with the row comparison, the id patterns and the crash classification beside them, and `builder/sandbox.py` keeps thin wrappers that run the sandbox and hand the results (or the sandbox's error) to the gate; the metrics and failure strings are the ones the file had. The stage rulings live in `kullback/gates/stages.py` (`cluster_gate`, `compile_tools_gate`, `intent_gate`, `rerolls_gate`, `tau2_export_gate`, `vocabulary_gate`, `task_verifiers_gate`), each a function over the artifact it rules on, and `build.py` records what they return. `GateSpec` gained `artifacts`, the names of the artifacts a gate is bound to in the build's own vocabulary (`tasks`, `bodies`, `intents`, ...), which is what `gates_over` and the hook read; the registry holds 34 specs over 44 ruling names, and two tests pin the outside set to empty. One reads the Builder's source, every module of it, for a ruling written with the `gate` helpers or with `GateResult(stage=...)` by hand, and the other reads what a whole driver build actually left in `gates.json` and `pipeline/state.json` and asks the same question of the names on disk, so a ruling written in a shape the scan does not know still has to be a registered gate's.

Two things sit outside the registry by shape rather than by omission. The compile-tools stage still overwrites `gates.json` with its per-tool rulings, dropping the mine and cluster rulings recorded before it, which is the file's pre-existing semantics and not this phase's to change; and a fresh build's mine and cluster stages run once more on the next targeted or iterated run, because the anchor is part of every cache key and those two run before it is chosen, which is also the shape the pipeline had. Both are noted in the tests that meet them.

## The compile-tools rulings still live in two places, and which one is the real one

The cross-package review found `gates/artifacts.py` holding a second set of the five compile-tools
rulings: `parses_gate`, `executes_gate`, `deterministic_gate`, `non_trivial_gate` and the
`compile_tools_gates` that sequences them over an `evidence` dict. They read the same five things as
`gates/tool_runs.py`'s `body_parses_gate`, `body_executes_gate`, `body_deterministic_gate`,
`body_non_trivial_gate` and `body_replay_fidelity_gate`, which are the ones a build actually runs:
`builder/sandbox.py` wraps those, the sandbox hands them its results, and the rulings they return are
what reaches `gates.json`. Nothing calls the `artifacts.py` five except the `compile_tools` registry
row and six tests, so they are registered but never exercised by a build.

The choice, recorded so nobody has to make it twice: `tool_runs.py` is the home. The `artifacts.py`
five, the `compile_tools` and `compile_tools.replay_fidelity` registry rows, and the six tests in
`tests/gates/test_artifacts.py` that cover them come out; `compile_tools.bodies` stays, because
`compile_tools_gate` is a real ruling over the bodies artifact, and `fidelity.replay_fidelity_gate`
stays either way since `scorecard.py` calls it. The deletion is not in this pass: it moves the
registry's spec and ruling counts, which two tests and the paragraph above pin by number, and the
integration pass that found it was not the place to renumber them. It is a small, self-contained
edit once someone is already in `gates/__init__.py`.

## The byte-identical check

`snapshot_build.py` (under the scratchpad) runs the full build over `tests/fixtures/tau2_retail_small.json` with the scripted bodies and the ingest version pinned, before the phase and after it, and `diff -r` compares the workdirs. The run after the phase went through `build.build()`, which now builds a `BuildPlan` and calls `execute`, which runs the new scheduler with `anchor_from="tasks"` at one worker; a second run went through `run_builder`'s driver path. Against the before snapshot both differ only in the permitted places: `runner_version.json`, `budget.json` in `wall_ms` alone, the nonces in the sandbox's `out.json`, and the names of some cache entries (the key includes the stage's code, so a stage whose function moved is renamed while one that did not keeps its name; the contents of every entry are identical stage for stage). In `runner_version.json` the Runner's own hash is unchanged and only `gates_version` moved, because `tool_runs.py` and `stages.py` are two new files in the package that hash is over, which is the point of hashing the gates apart from the Runner (D122). One difference is not on that list and is the phase's: the stage that assembles the Environment was called `environment`, the same word as its artifact, and a target vocabulary in which a stage and an artifact share a name is ambiguous, so the stage is `build_environment` and the artifact is still `environment`. `pipeline/state.json` therefore has `build_environment` where `statuses` and `attempts` had `environment`, and its mermaid text is drawn from one graph; its `gates`, `log`, `failed_stage` and `stopped` are byte-equal. `gates.json`, `replays.json`, `bodies.json`, `tool_builds.json`, `tasks.json` and every other artifact are identical.

## Tests

`tests/builder/test_scheduler.py` (11 tests) covers the order from reads and writes whatever the declared order, two independent stages overlapping at two workers (a barrier both must reach) and not at one, the same artifacts and cache names at one and two workers, a target running only itself and what is upstream, a stale input rebuilt before the target with a current one served from the cache, the typed events in order with their counts, an emit that raises not failing the build, the ledger's order at two threads, `write_gates` then `record`, the anchor drawn when the Tasks land with every Builder stage waiting, and a `BudgetStop` at two workers. `tests/builder/test_extension.py` (34 tests, parametrized) covers the driver's build and its events, the short content and the payload in details, the hook's rulings against `gates.json` and `state.json`, the blocked and allowed paths on both paths, the six tools and three sections and no repair verb, invalid arguments, a cached target, `compile_tool` keeping every other body, `replay` over one Task, the model-driven session (the tools it was offered, the system prompt, the rulings in its second call's messages) and its artifacts against the driver's, the `BuildError` cases and the driver model's refusal. `tests/gates/test_package.py` pins the artifact bindings to names the declaration produces and the outside set to empty over the Builder's source, and `test_extension.py` pins the same over the ruling names a whole build left on disk; `tests/test_cli.py` and `tests/test_tui.py` follow the entry point to `run_builder` and the `--agent` refusal without `--model`. This phase took the tree from phase 3's 1,544 tests to 1,633, and with phase 7 landed beside it and both reviews' tests added the suite is 1,643, green, with `ruff` and `lint-imports` clean.

One test outside this phase's files failed by design while it was being built: `tests/agent/test_boundary.py::test_nothing_outside_agent_imports_the_new_code`, phase 2's assertion that nothing outside `kullback/agent/` imports the agent core, which this phase's `builder/agent.py`, `builder/extension.py`, `builder/tools.py` and `builder/pipeline.py` now do on purpose. `tests/agent/` was not this phase's to edit, so the review that closed phase 7 rewrote it: it now asserts that only the two application packages and the frontends reach into the core, and that `runner/` and `gates/` never do, which is the boundary D121 and D123 actually decided and the import-linter contract enforces.

## What phases 5 and 6 build on

The Examiner (phase 5) is a second `setup(api)` over the same harness shape: its tools go through `api.register_tool`, its findings reach the Builder as follow-up prompts on a harness that already has the target vocabulary and the hooks, and the probe pool and loosening gate land in `kullback/gates/` bound to artifacts by name so `gates_over` runs them in the same `tool_result` hook. The rounds and `round_end` are events on the stream the stage events already use. Phase 6's repair verbs are tools beside the six here, its ratchet and lesson are further `tool_result` hooks on `compile_tool` reading `details["gate_rulings"]`, and its skills replace the stage prompts `build.py` still holds; the stage's `code_version` is where a skill's hash enters the cache key so an artifact records the skill it was compiled under.
