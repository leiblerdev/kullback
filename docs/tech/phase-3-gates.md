# Phase 3: `gates`

Landed 2026-09-02, the third phase of `rebuild-phases.md` (D122, D129, D130). No behavior changed. Every accept-or-reject check over what the Builder makes now lives in `kullback/gates/`, a package with one registry, no model call, no import of the Builder, the Examiner or the agent core, and a content hash of its own recorded beside the Runner's. The pipeline calls each gate where it called the old code, so `bodies.json`, `constraints.json`, `intents/`, `gates.json` and every Run are byte-identical; `runner_version.json` is the one artifact that changes on purpose.

## What a gate is

A gate is a plain function over an artifact (or two) that returns a `GateResult`, the record `records.py` already had: `stage` is the gate's name, `passed` (alias `pass`) is the ruling, `failures` are the reasons in words a person or an agent reads, `metrics` the numbers behind the ruling. The record was not extended. Two things the old code returned as loose values, a list of confinement lines and the replay stage's inline `gate("replay_reference", ...)` call, now come back as the same record through a named function (`predicate_confinement_gate`, `reference_replay_gate`), so that every gate in the package has the one shape and phase 4 can hand any of them to a `tool_result` hook without a wrapper. A gate reads only what it is given, calls no model, executes no Run and keeps no state between calls; the one that reads a directory (the scorecard) reads the directory it is handed and nothing else.

`kullback/gates/__init__.py` holds the registry: `GATES`, an ordered tuple of `GateSpec(name, over, fn, rulings)` in the order the build meets them, from `ingest` to `scorecard`, and `gate_named()` to look one up. `rulings` lists the `stage` values one call may return, which for a single gate is its own name, for the compile-tools sequence up to five, and for the D79 suite the nine `verifier_*` stages. `tests/gates/test_package.py` checks that every registered function lives under `kullback.gates`, that every stage name a function in the package rules under is registered, and that every gate over an empty input still returns a `GateResult` with a registered stage. The registry does not yet cover every stage a build writes into `gates.json`: the fixture build records fifteen stage names and ten of them are outside the registry, the five sandbox gates and `refuses_unknown` (subprocess gates that stayed in `builder/sandbox.py`, below) and the rulings `build.py` still makes inline with `gate_support.gate()` for `cluster`, `compile_tools`, `intent`, `rerolls`, `tau2_export` and `vocabulary`, which rule on a stage's own bookkeeping rather than on an artifact the phase named. The same test pins that list, so phase 4 sees exactly what is left to register and a new inline ruling cannot appear in `build.py` unnamed.

## What moved where

`gates/verifier_suite.py` is the D79 suite out of `builder/verifier.py`: reading a Run off disk (`load_run`), scoring one against a Verifier (`check_run`), the Runs code builds to break a Verifier (`_empty_run`, `wrong_run`, `unfinished_run` for check 9, D119, the mutant of check 8), the leak check, the loophole probe's ruling, and `validate_verifier` running the nine checks in order, plus the atom vocabulary both sides need (`atom_payload`, the predicate wrappers, `_hard_holds`, provenance classification, the write and communicate extractors). It went to `gates/` whole rather than check by check because the checks share the scorer and the scorer shares the atom vocabulary with derivation; splitting the vocabulary would have put one copy in each package. What stayed in `builder/verifier.py` is derivation, `derive_verifier` and the tau2 export, 158 lines that import the vocabulary back from the suite. The one seam that had to be cut was the Hard-atom wrapper, which embeds `policy.HELPERS_SRC` (the helper functions a compiled predicate may call) into the predicate source: the suite's `_predicate` and `_atom` take `helpers` as a parameter, the Builder's `_atom` passes `HELPERS_SRC`, and the mutant hard atom the mutation check builds passes none because its rule (`_NEVER_HOLDS`) calls no helper. Results are unchanged, which the byte-identical check below confirms.

`gates/artifacts.py` is `runner/validate.py`'s check list under a new name: ingest, mine, the four compile-tools gates over evidence, policy, environment, user rules, the D79 tally (`verifier_gate`), leak, verdict golden, setup review, candidate Runs, budget, audit, regrade. `gates/fidelity.py` is the fidelity bar: `replay_fidelity_gate` (the fifth compile-tools gate, D80), `oracle_replay_gate` (Gate A), and the two functions the replay stage used from `runner/replay.py` (`summarize`, `unconfirmed_reason`) with the new `reference_replay_gate` over them, the per-Task ruling that a replayed Run clears fidelity (D108). They left `replay.py` because they rule; `replay.py` scores one replay and stops. `gates/confinement.py` holds both confinement gates: `predicate_confinement` over a compiled constraint (which is `runner.confinement.confine`, one primitive) and `source_confinement` plus `gate_confined` over a generated tool body, out of `builder/sandbox.py` with its allowlists (`ALLOWED_IMPORTS`, `DENIED_BUILTINS`, `ALLOWED_DUNDERS`). The tool-body gate does not call `confine`: `confine` certifies a predicate that runs in the Runner's process under `SAFE_BUILTINS`, while the tool-body gate has to let `json`, `datetime`, `re` and the rest of a working tool through and refuse everything else by name, a different rule with a different list. Both lists are in one module now so a reader can see the difference. `sandbox.py` re-exports only the row helpers the five subprocess gates and `synth.py` read (`parse_result`, `id_pattern_for`, `id_field`, `match_table`, `args_text`) beside `TOOLS_CLASS`, `gate_confined` and the `body_*` gates; `compile_env.py` imports the confinement names from `gates/confinement.py` directly, as does `scripts/env_fidelity.py`; the five gates that run a body in a subprocess stayed in `sandbox.py`, because a gate that spawns a process is not one a hook runs, and phase 4 decides what to do with them.

`gates/scorecard.py` is `runner/scorecard.py`. It moved because its one ruling, the scorecard gate that is never green over nothing, is built on `replay_fidelity_gate`, and the Runner cannot import `gates`; had the scorecard stayed, `runner/` would have imported upward. The deferred import that used to break the cycle between `validate.py` and `scorecard.py` is gone with the cycle.

`runner/validate.py` is fifteen lines: it re-exports `import_boundary_check` and `runner_version` from `runner/boundary.py`, the two checks that rule on the Runner itself rather than on the Builder's work, so `kullback.runner.validate` still names them and `builder/memory.py`'s read-only list, which names `runner/validate.py` as a file no lesson may propose editing, still points at a file. The list is otherwise untouched; the gates package is written by people and read by both agents, and the hook that refuses an agent's write to it is phase 4's.

The runner primitive stayed where phase 1 put it. `runner/confinement.py`'s `confine` is called by `verdict.py` (the atom gate at Verdict time), by `_hard_holds` (the same check at D79 time, which the tests pin to the same answer) and by `predicate_confinement`. It sits in `runner/` because `verdict.py` needs it and the contract lets `gates` import `runner`, not the reverse. Derivation stayed in `builder/` because it is what the Builder writes and phase 5 rebuilds it over the probe pool; moving it now would have moved it twice.

## The contract, read for `gates`

The import-linter layers contract from phase 1 already placed `gates` above `agent` and `runner` and below `builder` and `examiner`, and forbade `gates` from importing `agent`. What this phase adds is the reading of "imports `runner` only for types and primitives": `gates` imports `records` (the record types), `canon` (`CanonRules`, `canon_value`), `confinement` (`confine`, `SAFE_BUILTINS`, the predicate builtins) and `gate_support` (the `gate()` constructor and the field readers), and no execution module. `lint-imports` keeps the package direction; `tests/gates/test_package.py` scans every file under `gates/` for an import of `kullback.ai`, `kullback.agent`, `kullback.builder`, `kullback.examiner` or a frontend, and for any call named `query`, `stream` or `complete`, which is how a Model is asked. Three contracts kept over 61 files and 159 dependencies at the time of writing.

## The gates hash

`RunnerVersion` carries two new fields, `gates_version` and `gates_file_hashes`, next to `runner_version` and `file_hashes`. `runner_version()` in `runner/boundary.py` hashes every `.py` under `kullback/gates/` the same way it hashes `kullback/runner/`, sorted by path relative to the package, and records `content_hash({"files": ...})` of them as `gates_version`. It is recorded beside the Runner's hash and never folded into it: a gate that changes does not change what executes or grades a Run, so the Runner's hash holds still when a gate tightens and a regrade that names both can say under which Runner a Run was graded and which gates accepted the artifacts it ran in (D122). `kullback freeze-runner` writes both and echoes both. A RunnerVersion frozen before this phase has `gates_version` null, which the record allows so old files still load; every workdir needs `freeze-runner` again before its next `verdict` or `regrade`, as after phase 1, because `runner/validate.py`, `boundary.py`, `records.py` and `replay.py` changed and `scorecard.py` left the package, all of which move `runner_version`.

## The byte-identical check

The offline build the tests run (the `build` fixture of `tests/test_e2e.py` and the full `build.build()` over `tests/fixtures/tau2_retail_small.json` with `RecordedModel` and `TestModel`) was snapshotted before the first edit of this phase and again after the last, in one fixed working directory, and compared with `diff -r`. `bodies.json`, `constraints.json`, `intents/`, `gates.json` (fifty-seven rulings, the same stage names in the same counts), `environment.json`, `replays.json`, `task_status.json`, the eleven Runs under `runs/` (the oracle, the candidate, three replays, six re-rolls) and the contents of every stage cache entry are byte-identical. What differs is `runner_version.json` (the new fields, and the Runner's hash over the changed files), `wall_ms` in `budget.json` and the nonce in each tool sandbox's `out.json` (wall-clock noise, the same on two runs of one tree), and the names of ten of the fifteen cache entries. A cache entry's name carries the stage's code version, which is the source of the stage's own closure plus the modules it delegates to (R42), so it moved for every stage whose closure now says `artifacts.` where it said `validate.`, for the stages that hash `compile_env.py` (whose imports were repointed), and for the two that now hash `gates.fidelity` and `gates.verifier_suite` as well; `ingest`, `canon_rules`, `compile_policy`, `judge_lessons` and `rerolls` kept their names. An `--iterate` build over an existing workdir recomputes those ten stages once. Each of those differences was checked to be nothing else: `budget.json` is equal with `wall_ms` removed, every `out.json` differs in `nonce` alone, and every cache entry's bytes are equal under its new name. The reviewer re-ran the after snapshot from the finished tree and got the same result.

## Tests

The tests moved with the code and mirror the packages: `tests/gates/test_verifier_suite.py` holds the suite's tests out of `tests/builder/test_verifier.py` (reading Runs, the footer state, the Hard-rule gate, the scorer, the nine checks), with the hand-built Runs both files use in `tests/gates/verifier_fixtures.py`; `tests/gates/test_artifacts.py`, `test_fidelity.py`, `test_confinement.py` and `test_scorecard.py` split `tests/runner/test_validate.py` by module, and its boundary and RunnerVersion tests are `tests/runner/test_boundary.py`, its field-reader tests `tests/runner/test_gate_support.py`. New tests cover the registry and the no-model-call scan (`test_package.py`), `reference_replay_gate` and `gate_confined` as records, the failure cap on named confinement failures, `gates_version` moving when a gate changes and holding when the Runner does, and freeze-runner writing it. 1,451 tests were collected after phase 1. The tree now collects 1,544, of which 151 are under `tests/gates/`; 164 of the total are phase 2's `tests/agent/` and `tests/ai/`, and 100 of those (`test_pricing.py`, `test_provider.py`, `test_scaffold_provider.py`, moved in phase 1) were already counted in phase 1's figure, so the comparable count is 1,480 against 1,451, every moved test present under its new path and the difference the tests this phase added. The full suite passes with `ruff` and `lint-imports` clean.

## What the next phases build on

Phase 4 turns the pipeline into the Builder's DAG scheduler and runs the gates from a `tool_result` hook: every gate is already a pure function over an artifact returning one record, registered by name with the stages it may return, so the hook is a lookup in `GATES` and a call, and the same `GateResult` lands in `gates.json` whichever side calls it. The read-only rule over `kullback/gates/` that `memory.py` states for lessons becomes the hook that refuses an agent's write there. Phase 5 builds the probe pool and the one-directional loosening gate (D127, D133): the suite's `check_run`, `wrong_run` and `unfinished_run` are the scorer and the code-built probes it draws on, `verifier_gate` is the tally it extends, and derivation, left in `builder/verifier.py` with the atom vocabulary imported from the suite, is what it rebuilds over the pool. Phase 6's skill gate over two rounds of the memory tree is a gate like any other here: a function over two artifacts, one record back, one more entry in `GATES`.
