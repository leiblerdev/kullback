# ADR-0008: A built Environment exposes a Run anyone can drive, and the loop's step is split into asking a policy and advancing the world

Status: accepted 2026-09-18. Implementation pending at decision time; current status is recorded in docs/decision-log.md.

Context: replay fidelity is the number the harness answers to, and it is measured by the Builder driving its own Runs. A customer has no benchmark reward to compare against, and every other consumer of an Environment (a solve-rate stage, a property harness off the recorded path, a code adversary against Verifiers, a check that a synthetic Task is solvable, a measurement of the Simulated user's cost per Run) needs a Run it can drive. No such interface exists: `runner/loop.py:77` is one step that asks the model for the next assistant message and advances the world in the same function, `kullback/hub/__init__.py` exports nothing, and the only driver of a Run is the Builder's `run_batch`.

Decision: a built Environment exposes a thin interface (reset, step, a reward computed by code, a seed) that imports no part of the Builder, and a solve-rate stage runs a cheap model through the Tasks over it. Underneath, step is divided into its two jobs, asking a policy for the next assistant message and advancing the world given one (tool calls through the router, then the Simulated user, then the stop rules), with the old step kept as a thin wrapper over the new core so the Builder and the Examiner are unchanged and there is one code path with two faces. The split lands on a re-freeze of its own, bundled with nothing, because as a pure refactor its acceptance test is exact: regrade every stored Run and require identical Verdicts, replay every Trace and require identical fidelity. Replay fidelity stays the public headline and the priority order stands; the interface is a measuring instrument, not a trainer and not the training experiment.

Why: three jobs want three owners. The policy decides, the Environment advances the world, the Verifier scores. A function that asks a model and moves the world cannot hand either half to anyone else, so every new consumer would otherwise reimplement the loop and drift from the one the Builder grades against. Decisions here are taken for the longer term, and each part has one job.

Considered: leaving the loop where it is, which is enough for episode-level GRPO as `docs/training-plan.md` states it and costs nothing today, but leaves no seam for any of the measurements above; riding the split along with the next planned re-freeze, proposed and withdrawn, because bundled with any other Runner change the identical-Verdicts and identical-fidelity test is lost and the refactor can no longer be proved inert; and making the training experiment itself the second number, refused because the harness measures Environments rather than trains models.

Consequences: a re-freeze is a new baseline on all three corpora, and a second instrument competes for builder slots. A solve-rate stage on retail inherits the two open cross-domain gaps (confirmation-string write results, the initialization overlay). Whether the interface records each Run (seed, cost, route per call) from day one is Claude's open follow-up, to be confirmed. See decision log D252 and D253; the property harness that stands on this interface is D258.
