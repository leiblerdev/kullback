# The Builder and the Examiner are separate agents, and the gates are a package neither can write

Status: accepted 2026-09-02.

Kullback is rebuilt as an agent loop (observe, act) on a shared agent core, and the loop is mostly repair: build, read what a gate rejected, change something, run the gates again. Two things could have been one. The agent that builds the Environment could also write its Verifiers, and the code that accepts or rejects what an agent made could live next to the agent that made it. We chose neither. The Builder builds and repairs the Environment and never writes a Verifier; the Examiner writes the Verifiers and the probes and never edits the Environment; `gates` holds every accept-or-reject check, contains no model call, is written by people, and is importable by both agents and writable by none (a raising `tool_call` hook blocks the write). The two agents share a workdir and one event stream and talk only by messages into each other's queue. The Runner is a tool of both, never an agent.

Why: the evidence on reward hacking is that when the same model produces and grades work, hacking arises on its own once generator and judge share context, and the fix is structural, not a rule in a prompt. A Builder that writes its own Verifiers can loosen an atom so a fidelity problem stops mattering, and no gate can tell a loosened Verifier from a right one as long as the oracle passes and the empty Run fails. A gate that lives inside an agent's package is code that agent can reach. The literature's hardening loop (a hacker that tries to pass without solving, a fixer that patches the verifier, a solver that confirms real solutions still pass) needs the roles apart; here the Examiner is the fixer and writes the hacker's probes, the frontier's re-rolls are the solver, and `gates` rules. Two further gates keep the Examiner honest in the same way: probes are monotone (every probe ever written stays in its pool and every later Verifier must fail it), and loosening is one-directional (a new Verifier may newly pass only the Reference, a frontier re-roll from any round, or a live production Run; the pool grows from the solver, never from a model's opinion, D133).

Considered: one agent with two hats (one prompt, one session, cheaper; the one place a boundary cannot be replaced by a rule); the D79 suite inside the Examiner's package because the Examiner "builds the checks" (it builds Verifiers and probes, not gates, and the suite exists to rule on the Verifiers it writes); a model evaluator for the Builder's own prompt edits (rejected by D110: a judge never awards a pass; the evaluator is a gate over gate counts across rounds).

Consequence: the cost is a second prompt, a second session, and messages between two loops, all on one shared core. The Examiner writes atoms from what the Runner produced and from the traces, never from tool bodies, so atoms bind to the Intent rather than the implementation. Anything the model contributes to the checking side is a probe, never a gate. See decision log D120 to D130 and the glossary entries Builder, Examiner, Gate, Probe, Runner.
