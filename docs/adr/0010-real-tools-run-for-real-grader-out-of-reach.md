# ADR-0010: A tool that can be run for real is run for real, the harness rules which, and the grader lives where the Candidate cannot reach it

Status: accepted 2026-09-18. Implementation pending at decision time; current status is recorded in docs/decision-log.md.

Context: every tool in a built Environment today is a body compiled from recordings, which is a guess about a system that exists. Some of those systems can be obtained and run: a terminal corpus is a container, its files and a real shell. Founder, 2026-09-18: "Run it for real, have the bash tool with it. We should always run it for real." This is also the coding-domain question left open since 2026-09-10, and it decides what an Environment is when the only tool is a shell. Skills already exist as workdir `skills/<name>/SKILL.md` with a code-only gate (`kullback/builder/skills.py:1-26, 148, 190`), versioned by content hash and promoted or reverted by code over gate counts (D130, D132).

Decision: the Runner gains a route that executes a tool for real inside a sandboxed container, beside the routes that imitate a tool from recordings, and the order of preference is real, then compiled code, then the recording, then the model stand-in, which never counts toward trusted. The harness rules per tool, not the customer: a route skill guides the Builder to propose how each tool could be run for real (which image, which command), then code plays the recorded calls through the real candidate and compares with the recorded results, so a tool is a Real tool only when the real candidate reaches the fidelity bar and is an Imitated tool otherwise, a kept route is replaced only by one that beats it (D184), and the ruling with its measured reason is published per tool. "Can be run" therefore means "reproduced the recordings when run", never a guess from a name or a shape. With a real shell the grader moves out of reach: when a Run ends the end state is exported and checked in a fresh grader container with the tests and answers mounted only there; at birth every Task must defeat a code-written cheat suite (delete the tests, fake the exit code, hard-code the expected output), the do-nothing Run must fail, and the starting container is scanned for ground-truth strings, a fix commit in the history and hidden tests. Fidelity for such a Run is the end state, "end state, be as close as possible to the truth": files, exit codes and test results rule, and terminal text is reported beside them and never cleaned into agreement. For the whole of it, Kullback still supplies Task grouping, the Intent, a code Verifier, the gates, difficulty labels and the Run interface of ADR-0008.

Why: where the real tool is available, running it is both higher fidelity than any reconstruction and the only way to find the problems at build time rather than at replay. Founder, on who decides: "The customer is not going to say which tools to run or imitate. Mostly we should run all the tools to check the problems then and there, and then the harness infers from the traces where to imitate and where to run." The grader has to move because a real shell is the first World in which a Candidate can reach the files its own Verifier reads, a reward hole the imitated worlds never had.

Considered: imitating every tool from recordings as today, which stays the answer for a customer's refund or booking tool (no access to their database, and a real write moves real money) but throws away fidelity wherever the tool is obtainable; a customer manifest naming which tools to run, refused by the founder in the words above; deciding from a tool's name or shape, refused because only a replay of the recorded calls through the real candidate is evidence; grading inside the Run's own container, refused because the Candidate can edit or delete what grades it; and cleaning terminal text into agreement, refused because that is where leniency crept in before (`docs/learnings.md` section 3), so the text is reported and the end state decides.

Consequences: a new kind of World and a large build while airline is under 0.90; trying every tool for real costs container time on every build and a second container per Run costs time ahead of the speed pass. A real candidate can match the recordings on the recorded calls and still differ off the path, so the Environment consistency laws (D258) apply to it too, and real tools need their own answer for time, randomness and new ids (a pinned clock and seeds inside the sandbox, D271). Most sampled AgentTrove rows lack the starting container and the outcome. Tasks whose recording showed the tests to the agent change when the tests are hidden, which lowers fidelity to the Trace for an honest reason and is reported as such. Two scopings are Claude's, to be confirmed: that "always" means wherever the real tool is available and safe to run in a sandbox, and that a Real tool runs only in a sandbox nothing can leave, with no outside network by default. See decision log D262, and D263 for the cheat checks at intake.
