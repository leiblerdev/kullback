# AppWorld

## Link and owner

Benchmark: https://github.com/StonyBrookNLP/appworld (Stony Brook NLP). Project site:
https://appworld.dev (and https://appworld.dev/appworld). Paper: https://arxiv.org/abs/2407.18901
(pages 1 to 6 read in the earlier scout pass). Authored by a team from Stony Brook, AI2 and Saarland.

## What a row is

One task: a natural-language instruction against a simulated ecosystem of 9 apps, solved by writing and
running Python code that calls the apps' APIs. A published trace (see Provenance) is one model agent's
attempt at one task.

## Provenance

(a) App data: not real world, procedurally generated by the authors' own code, which invokes the apps'
APIs on behalf of 106 simulated people to populate their histories, with ChatGPT used narrowly for
realistic free text where exact semantics do not matter (spam emails, payment messages); the paper calls
this "procedural data population, with sparing and careful use of ChatGPT." (b) Tasks: human written.
Instructions are natural-language Scenario templates with placeholders, authored by the 8 paper authors,
not crowdworkers or an LLM; the paper states "over 100K lines of code meticulously written over 14 months
by a subset of the authors... rather than by crowdworkers or LLMs." A Setup program, also author-written
code, instantiates each template by searching or editing the base DB. (c) Ground-truth solutions: authored
by the same team as a Validation Solution per scenario, checked by running it against the initial state and
confirming it passes evaluation. (d) Published traces: model generated, a coding/tool-use agent (ReAct+GPT-4o
in AppWorld's own baselines; Gemini 3 Flash, Qwen3.5 variants and others elsewhere) acting against this
simulated environment, no simulated user turn. The traces themselves are entirely model generated; the world
and tasks are human-designed and mostly procedurally generated, not scraped from real usage.

## Counts and size

9 apps: Amazon, Spotify, Venmo, Gmail, Todoist, SimpleNote, Splitwise, FileSystem, Phone, plus two helper
apps (ApiDocs, Supervisor). 457 APIs (avg 50/app), 101 DB tables, about 370K rows, about 106 simulated
people. 250 task scenarios times 3 instantiations, 750 tasks: Train 105, Dev 60, Test-Normal 168,
Test-Challenge 417 (paper Section 3.4). `data-0.2.0.bundle` (the encrypted app/task data): 34,908,601
bytes. `experiment-outputs-0.1.3.bundle` (the authors' own baseline outputs): 179,524,924 bytes
(Content-Length from a HEAD request; not fully downloaded, too large and encrypted for this pass, see
below).

## Schema

Native format: `data/base_dbs/{app}.db`, one SQLite file per app (9 files), about 370K rows across 101
tables; each task's `data/tasks/{task_id}/dbs/` stores only the diff from the base DB. Tool schema:
`data/api_docs/{standard,function_calling,openapi}/{app}.json`, built by `api_docs.py` from
FastAPI-generated OpenAPI schemas, three renderings of the same 457 APIs, all inside the encrypted data
bundle. A task's own native output is `logs/environment_io.md` (numbered interaction blocks, each the
Python code the agent wrote plus its printed stdout or stack trace) and `logs/api_calls.jsonl` (method,
url, data per API request, no response body).

optional MCP server interface, how the HF redistribution below captured its data.

## Tool-call shape against our Trace record

Read from kullback/runner/records.py: `ToolCall` has `name`, `args`, `result`, `raw_ptr`, `result_ptr`;
`Turn` has `role`, `content`, `tool_call_ids`. The MCP-shaped redistributions (HALO, and the Exgentic
`tool_calling` harness sessions, see below) map onto this directly: one call, one JSON result, integer ids
throughout. AppWorld's own native format (`environment_io.md` plus `api_calls.jsonl`) does not: several
`apis.*` calls can sit in one code block (one `Turn`, several `ToolCall`s with no individual boundary
markers), and `api_calls.jsonl` has no response body at all, so a `ToolCall.result` would have to be parsed
out of printed stdout, not structured data.

## Environment and reference verdict

`evaluator.py` and `common/evaluation.py` run a per-task battery of pytest-style `assert_plus` unit tests
(avg 8, max 22 per task) querying the resulting DB/ORM directly; the paper frames this as expected changes
contained in the actual diff, contained in expected plus allowed changes, but the executable form is
hand-written assertion code per scenario, not one generic diff comparator.

## Licence

Public code (harness, agents, guides) is plain-text Apache 2.0. Task/app/API-specific code and data (API
implementations, docs, solutions, eval tests) ship as encrypted `.bundle` files, Apache 2.0 plus a clause
that public redistribution of it, or derivatives, must stay encrypted. A canary string is embedded against
training leakage.

## How to download

`download.py` builds URLs from `S3_BASE_URL = https://s3.us-west-2.amazonaws.com/appworld.dev/`, version
`0.2.0` for data, `0.1.3` for experiment outputs. `data-0.2.0.bundle` and `experiment-outputs-0.1.3.bundle`
are both reachable with a plain curl (200 OK, confirmed 2026-09-24) but are AES-256-CFB ciphertext, key via
PBKDF2-HMAC-SHA256 from a password and salt hardcoded in `common/constants.py` (comment: not secret, just
discourages scraping); `head -c64` of the data bundle is random bytes, not a zip or JSON header. Decrypting
needs the `cryptography` package, excluded by this brief's no-pip-install rule, so not attempted; reachable
and encrypted, not decrypted here.

## Which AppWorld traces to use

Three trace sources exist for AppWorld, and all three are usable, because AppWorld's own environment runs
offline: any of them can be re-executed against a fresh `data-0.2.0.bundle` (once decrypted) to recover
missing pieces, such as response bodies the trace itself never logged, since the app/task state that
produced a given call is reconstructible from the same base DBs and task diffs the trace's own model agent
ran against.

1. **The authors' own experiment outputs** (`experiment-outputs-0.1.3.bundle`, 179,524,924 bytes,
   encrypted, not decrypted here): native format, code blocks in `logs/environment_io.md` plus
   `logs/api_calls.jsonl` (method, url, data, no response body). This needs the most work to ingest: several
   `apis.*` calls can sit in one code block with no individual call boundary, and response bodies are only
   recoverable by re-executing the call against the environment or by parsing printed stdout when the
   agent's code happened to print it.
2. **The Hub MCP redistributions** (HALO: `inference-net/HALO-Gemini-3-Flash-AppWorld`, 168 traces, one
   Gemini 3 Flash agent run per `test_normal` task, full coverage of the 168-task split; plus
   `LukaszTP/AppWorld-Tasks`, `hamishivi/rlenv-appworld*`, `satyakic/appworld-rollouts-recursive-14b-mar06`,
   none of which state a licence, unverified): one MCP tool call per turn, integer ids, matches our
   `ToolCall` shape directly, needs the least work of the three.
3. **The Exgentic `agent-llm-traces-v2` AppWorld share** (see
   docs/trace-sources/exgentic-agent-llm-traces-v2.md): 1,500 `test_normal` sessions across 15
   (harness, model) configurations, 100 sessions each; only the `tool_calling` and
   `tool_calling_with_shortlisting` harness sessions (700 of the 1,500) hold one-call-per-turn shape without
   further scaffold-specific parsing.

Runs per AppWorld task across all three, counted or reasoned through where a task-level id was available:

- HALO: 1 run per task, for all 168 tasks in `test_normal` (168 traces / 168 tasks in that split).
- Exgentic: up to 15 runs per task for `test_normal`, if the 100-task sample is the same set of tasks
  across all 15 configurations (each configuration samples exactly 100 of the 168 `test_normal` tasks, but
  whether the same 100 recur across configurations was not confirmed at the task-id level; see
  docs/trace-sources/exgentic-agent-llm-traces-v2.md, Open questions).
- The authors' own experiment outputs: not counted directly, the bundle was not decrypted in this pass
  (179 MB, encrypted, `cryptography` needed, ruled out by this brief's no-pip-install rule). AppWorld's
  paper reports one baseline accuracy figure per task per agent configuration in its main results tables, no
  seed or trial count is mentioned in the sections read; unverified whether the bundle itself holds more
  than one run per task per configuration (for example repeated seeds), since the paper text gave no
  indication either way and the bundle's contents were not inspected.

Because HALO covers the full 168-task split once and the Exgentic set (if the task overlap holds) adds up
to 15 more runs on a 100-task subset, combining the two already gives every `test_normal` task at least one
run, and about 60% of them up to 16. The one-call-per-turn sets (HALO in full, the 700 `tool_calling`
sessions of Exgentic) need the least ingest work; the native and non-`tool_calling` Exgentic sessions need
re-execution or scaffold-specific parsing to recover call boundaries and response bodies, but are not
unusable, since the same offline environment that produced them can reproduce what's missing.

## Map onto our pipeline

- Ingest would read `logs/environment_io.md` (code and stdout blocks) as the trace and
  `logs/api_calls.jsonl` (method, url, data, no response) as the structured call log for the native
  format; the MCP redistributions (HALO, Exgentic `tool_calling`) need no such reconstruction.
- Starting state: `data/base_dbs/{app}.db` (9 SQLite files, base) plus per-task diffs in
  `data/tasks/{task_id}/dbs/` plus a frozen datetime per task via `freezegun`; relational, not one JSON
  blob.
- Reference verdict: a per-task battery of hand-written `assert_plus`/pytest tests over the resulting
  DB/ORM state.
- Harness assumptions AppWorld breaks: one shared `db.json` per customer (D56) is wrong, it's 9 relational
  SQLite files with per-task diffs; a wall clock is wrong, time is frozen per task (confirmed by the
  excerpt's `2023-05-18T12:00:00Z` matching the code constant); a multi-turn simulated user is absent, only
  one instruction plus a queryable Supervisor API; string ids are also wrong here, all ids observed are
  integers.

## Fit for Kullback

Gives a relational, replayable, offline environment (once the encrypted bundle is decrypted) with
hand-written per-task verdicts and, across its three trace sources, both full-split coverage and
multi-run-per-task coverage on a subset. What it breaks: relational multi-file state instead of one
customer db.json, frozen rather than wall-clock time, integer rather than string ids, no simulated user
turn, and an environment that ships encrypted (needs the `cryptography` package to decrypt, which this
brief's no-pip-install rule blocks, so it stays reachable-but-unopened here). Several traces per task,
counted above per source.
