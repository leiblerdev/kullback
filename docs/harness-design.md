# Harness design: Builder and Runner

Status: proposal for grilling, 2026-08-27, revised after R25 (principles re-derived from environment-generation pipelines, D61). Terms (Harness, Builder, Runner, Environment, Run, Verifier, Verdict, Simulated user, Provenance, Assisted) are used as the decision log defines them. Decisions are cited as D-numbers from `decision-log.md`. Research is cited as R-numbers from `../research/`. This document answers "get back to me with design recommendations." Every section is open to challenge.

Founder's philosophy, verbatim: "it should be simple enough and gets the job done in high quality", "as efficient and simple as possible", "care much more about generalizability than the overfitting".

## 1. What the Harness is, in one paragraph

Two programs work over one set of data records. The **Builder** reads a customer's traces and writes an Environment: state, tools, Hard constraints, and Simulated user rules, plus one Verifier per Task, in tau2's file shape first (D56). The **Runner** takes an Environment, a Run, and a Candidate model. It executes the agent loop and routes every tool call to code, a recording, or an LLM stand-in (D49). It writes one JSONL file per Run, and a separate pass computes the Verdict from that file by code alone (D43, D46). Nothing else gets persisted. Nothing decides without a code gate.

## 2. Principles, from environment-generation pipelines (D61, R25)

The sources are RL environment-generation pipelines (EnvFactory, Envs-FORGE, Agent-World, AgentSynth, ClawEnvKit, EvoEnv, EnvHarness/EnvRigger, LOGIGEN, ScaleEnv, Westworld, OpenEnv, Prime Intellect) and the learn-harness-engineering lectures, used where they agree. Coding-agent harnesses are cited only for support.

## 3. Shape: three layers, two programs

This follows Tau's cut, "separate the brain, the environment, and the face" (D53):

- **Brain**: `Model.query(messages, tools) -> Message`. One class has three implementations: a live provider, `RecordedModel` (replays a stored Run's model outputs), and `TestModel` (scripted tool calls for tests). No other code knows which provider sits behind it.
- **Environment**: the tool list, built as a capability seam (DeepSeek Harness). The **Service Definition** is the tool's `name, description, parameters`, copied from the traces and never changed by the Builder. The **Providers** are SQLite code, the recording, and the LLM stand-in, tried in that order. The **Consumer** is the one tool the Candidate sees. The Runner stays frozen at the Service Definition; the Builder improves the Providers. Hard constraints get checked in the seam before a write lands. The Simulated user is a message source, on the same footing as a tool result.
- **Face**: the report reads JSONL and Verdict files. No UI code touches the core.

Dependency direction: `report -> runner -> records <- builder`. The Builder and the Runner share only `records.py`. The Candidate's context is always the production setting: the system prompt, tool definitions, and conversation the customer's agent gave it, with production's own compaction if the traces show one. The Harness never caps or compacts it (D65). Two runtime invariants are asserted in code. **Model-visible means logged**: every prompt the Candidate received is reconstructable from the Run's events. **Runner frozen**: `RunnerVersion` is the hash of `loop.py`, `route.py`, `verdict.py`, and the routing config; a Verdict carries it, and a comparison across two `RunnerVersion`s is refused.

## 4. Modules, one file each, one sentence each

Builder:

1. `records.py`: the data records from section 5, as Pydantic models that round-trip through JSON. Nothing else.
2. `ingest.py`: stores the customer's files byte for byte, content-hashed, as the source of truth (D66). It then derives `Trace` records from them, with a raw pointer (file, offset) on every field so each one is re-derivable whenever the schema grows. It maps a customer export (tau2 native, OpenTelemetry GenAI in both dialects, Claude Code JSONL; R23) into `Trace` records with content hashes. It strips benchmark grader fields (`reward_info`, `task_id`, `action_checks`, `nl_assertions`, trial ids) before anything else reads the trace. It normalizes tool errors into the D67 taxonomy plus the verbatim payload (code for flagged sources, rules then LLM for string-only sources, with `classified_by` recorded). It marks truncated results with the visible length and a cut marker; the Builder reconstructs the rest from the result schema and complete calls, tags it, and such calls stay Assisted until the customer supplies the full result (D95). The module is pure code except for the error-classification and reconstruction passes.
3. `mine.py`: builds `ToolSig` records from the traces (name, argument schema, result schema, read or write decided by an LLM over code-gathered context with observed effects overriding it, D68, observed error classes) and `EntitySchema` records (tables, columns with class exempt, hard, or semantic, id patterns). It makes one LLM call per tool whose result schema cannot be inferred from observed results, and marks those `source: llm`.
4. `compile_env.py`: writes `data_model.py`, `tools.py`, `db.json`, `policy.md`, and `tasks.json` (D56). There is one shared `db.json` per customer, built by inverse replay over the whole corpus (D33), where the latest observation wins in the shared rows. Each Task also gets an overlay of the rows its own Runs touched, in the version they saw (D74; the overlay lookup happens in `route.py`, never in tool bodies; overlays are merged only when emitting for tau2's harness, and a conflict there is a Gate failure). Tagged synthetic rows are added for reads (D40, D41). An LLM writes each tool body; code writes the signature, docstring, and schema. A body that fails a gate is rewritten up to three times with growing evidence each time (failing call, all failing calls, full call table), and each attempt is a Builder tree node. Every rewrite is re-checked against all recorded calls with a held-out split, and after three misses the tool is marked assisted (D75). Tools are compiled a few at a time on threads (`--workers`, D118), as are policy sentences, Intents and re-rolls; the results are assembled in order, so the artifacts do not depend on the count. While it drafts, the model may call `lookup_rows` (a row of the Starting state, read-only) and `test_body` (its draft against the shown calls' gates, never the held-out split), at most six rounds per attempt (D117).
5. `policy.py`: turns policy and system-prompt sentences into `Constraint` records, each a before-write predicate in Python with one positive and one negative test. Sequence rules ("never write X without a prior user confirmation") become predicates over the transcript (D43 case 3). An uncompilable rule is first rewritten into a checkable form for the setup review, with the original kept beside it. If it still cannot be turned into code, it becomes a judge atom evaluated by `judge.py`. A rejected rule goes to `residual` and is reported as not checked (D76).
6. `user_sim.py`: builds per-Run Simulated user rules from the trace (facts exact, style representative, D44): a disclosure rule for every fact the agent asked for, plus refusals and walk-away branches where the trace shows them. If the Candidate asks for a fact the trace lacks, the answer comes from the Task's Starting state as that user; if the world lacks it too, the Simulated user says so and the event is tagged `fact_unavailable` (D77). The LLM only fills in the utterances; the rules themselves are data in the `Run` record.
7. `cluster.py`: groups Runs into Categories by write-tool signature (code), then into Tasks by Intent similarity inside each Category (D83). The output is a `Task` record listing its Run ids. An LLM only names the cluster; code decides membership. A Run that fits no cluster becomes its own Task instead of being forced into one.
8. `intent.py`: writes the one-line grounded Intent for each Task (step 6, D47). Every noun phrase in it must point to a span in a member Run: a tool argument, a user utterance, or a written value. The cross-family grounding check refuses an Intent whose spans all come from one Run. The Intent is what the customer sees as the Task name, and it's what `verifier.py` derives from.
9. `canon.py`: the canonicalizer (D39), as its own module with its own tests: numbers (`25` vs `25.0`), whitespace and case, timestamps, id formats, and list order where the order doesn't matter. Both `route.py` (for recording lookup) and `verdict.py` (for atom comparison) use it, so both sides agree by construction. The rules are data, learned per customer from the traces and reviewed in the setup check. `semantic` columns whose canonical strings differ go to `judge.py`, and the (column, a, b, verdict) result is cached in a per-customer equivalence table that reviewers can overturn, which triggers a regrade (D84).
10. `verifier.py`: builds the atoms for one Task from confirmed References (step 7): a write-set diff over successful re-runs, Provenance per value (D42), required versus allowed atoms by re-run agreement (D43) over k frontier re-runs (k comes from config, chosen by the D78 experiment), questions asked as atoms, communicated facts, Hard constraints, and an entity-count check. It writes these to the sidecar next to `tasks.json` and exports them into `evaluation_criteria.actions` for tau2's harness.

Runner:

11. `loop.py`: a `step(run) -> run` function that advances one turn (`msg = model.query(messages, tools); calls = parse(msg); results = [route(c) for c in calls]; messages += ...`), plus a `run()` function that calls it until stop, writing one JSONL line per event. It runs 100 to 150 lines (mini-swe-agent shape), written this way so the OpenEnv wrapper is mechanical later (D90).
12. `route.py`: tries code first, then a recording (exact match on tool, canonical args, pre-state hash), then an LLM stand-in. The route taken is recorded on the event. Any stand-in marks the Run Assisted (D49). A bad call is answered in the customer's own error encoding (D45).
12a. `reference.py`: decides which Runs a Verifier may be derived from, before the Verifier exists (D111). A recording that broke a compiled Hard constraint is a failed recording; the rest are grouped by End state (tool, entity, canonical values) and the References are the one group that agrees; when two groups remain a judge may fail one side and never pass it (D110). Re-rolls (D112, `build.py`'s `rerolls` stage, `--rerolls`, default 3) enter the same rule below the recordings. It also checks every compiled constraint against the confirmed recordings corpus-wide and demotes the ones they mostly break, since a rule the frontier broke in a quarter of its own recordings is a miscompiled rule (D76). `build.py`'s `intent` stage writes the Intent the judge reads; the live builds before it ran with every `Task.intent` empty.
12b. `replay.py`: drives `loop.py` with a recorded Trace, its assistant turns as the model and its user turns as the user, over the same Router a Candidate gets, and scores every routed answer against the recorded one (same, cosmetic, refused on one side, differs). A Trace whose writes agree and whose reads never differ in substance confirms its Reference; `build.py`'s `replay_reference` stage runs it over every Trace and `derive_verifier` derives from the confirmed seed replays (D108).
13. `verdict.py`: reads a Run's JSONL and the Task's Verifier, and canonicalizes it (D39). It checks required atoms, allowed atoms, forbidden writes, questions asked, communicated facts, Hard constraints fired, and side-effect count. It emits pass or fail with the failing atom and same-path or different-path (D46), and the class `transferred_without_acting` where that applies. It never calls a model itself; it combines `judge.py` results for judge atoms and sets `judge_used` (D76).
13b. `judge.py`: the agentic judge (D92). Two judges, using different models or personas, each get read tools over the Starting state, the End state, and the Verifier's output, and each must run at least one tool check before a verdict and cite spans. It's used for judge atoms (D76), semantic equality (D84), failure cause (D88), Reference confirmation (D57), and the dispute path. A disagreement between the two judges goes to a queue listed in the report; it never blocks a build. The disagreement rate travels with every result, and the audit rate sits beside it once a person has resolved the queue items.
14. `regrade.py`: re-runs `verdict.py` over stored Runs against a new Environment or Verifier version without re-executing (tau3 `--fresh-tasks`).
15. `validate.py`: the gates in section 6, each a function returning `GateResult`.
16. `pipeline.py`: a content-addressed, idempotent stage runner, modeled as a graph. It has one explicit rollback edge: a failed gate returns the artifact to its generating stage with the failure summary, logged as an edge traversal ("attempt 2 of 3, gate replay_fidelity failed"). It also has one anchor: a fixed share of every Task's Runs (20%, at least one; Tasks under three Runs are marked unguarded; D81) is held out and never touched by the Builder. The Builder must keep replaying that anchor, so its iteration cannot drift from the customer's production behavior.
17. `cli.py`: the commands are `ingest`, `build --iterate`, `freeze-runner`, `run`, `verdict`, `regrade`, and `report`. `build --iterate` is expected to run often and change. `freeze-runner` writes the `RunnerVersion` and asks for confirmation. Every command reads and writes records on disk, and there is no hidden state.

Shared by both (D69):

18. `report.py`: the face. It's one Markdown or JSON report per Environment build and per Run batch. It opens with whether the Environment was built at all (Gates, scorecard raw and explained, assisted tools, unguarded Tasks, overlay counts), and ends each Task with its numbers and then a suggestion, with the decision left to the person (D85). It reports the scorecard (D62), Gate results, per-Task Verdicts with the failing atom and same-path or different-path (D46), assisted share per tool (D49), Task names with the customer's corrections (D47), and cost per stage. It reads records and never computes a Verdict.
19. `budget.py`: handles cost and token accounting. Every model call records provider, model, input and output tokens, cache reads, price, and wall time on the event, rolled up into per-stage and per-Environment totals. It enforces the 40% context cap on Builder calls (D65) by refusing the call, and it enforces a per-build spend ceiling: at the ceiling, the Builder stops where it is, reports as is (stage, item, cost so far, cost to finish), and resumes only with a person's permission and a new ceiling (D86).
20. `provider.py`: puts `Model.query(messages, tools) -> message` behind one interface, with adapters for Anthropic, OpenAI, and OpenAI-compatible local endpoints (R26, from OpenCode). A model id is `provider/model`, with a separate wire id and base URL per model; the base URL comes from config with `${VAR}` substitution, and keys come from the environment. It retries only on 5xx errors, network errors, and rate limits, honoring `Retry-After`, with exponential backoff and jitter, five attempts, and never retries on context overflow. It applies three defensive normalizations: dropping empty messages and empty reasoning parts for Anthropic, restricting tool-call ids to `[a-zA-Z0-9_-]`, and stripping unpaired surrogates. It places prompt-cache points on the system messages and the last two non-system messages. It uses three explicit reasoning branches and no effort tables. Usage (input, output, cache read, cache write) is returned on every call for `budget.py`. There is no live model registry and no output clamp; the Runner uses the recorded `max_tokens`. The module runs 250 to 400 lines.
21. `memory.py`: the Builder's memory for its improvement loop (D63, D64). It's a tree of Builder versions, where each node is a set of files (prompts, checklists, gate thresholds, canonicalizer rules, tool-writing instructions) plus its scorecard on the anchor sample. The improvement agent writes failure notes after each build. There is also a cross-customer lessons file (pattern, fix, confirming anchor result, relevance condition; no customer data, with an anonymization gate on save), which the Builder reads at the start of a build and must judge lesson by lesson for relevance to this customer's traces; set-aside lessons are listed in the report (D87). The tree is grepped, never loaded whole (D65).

The Builder can modify itself (D69). The improvement agent may edit any file under the Builder's own directory (its prompts, `mine.py`, `compile_env.py`, `policy.py`, `user_sim.py`, `intent.py`, `cluster.py`, `canon.py` rules). It commits the edit as a new node in `memory.py`'s tree, and the evaluator outside the loop (D64) accepts or rejects it on the anchor sample and held-out Runs. The improvement agent has read-only access to `loop.py`, `route.py`, `verdict.py`, `validate.py`, `budget.py`, the runs directory, the raw store, and the evaluator itself (Weng, AHE; section 12 items 1 and 2).

Deliberately left out: an event bus, a plugin system, MCP inside the core, subagents, a UI framework, and session trees for Runs (a fork is just a new Run with `parent_run_id`; the Builder's own tree lives in `memory.py`). Deferred to `todo.md` (D69): Filter and Screen, Reference confirmation as a module (the tau2 slice uses tau2's own references), the dispute path, the statistics module, a sandbox for model-written tool code, anonymization, secrets handling, a cache store beyond content-addressed files, a review UI, scenario generation and seed augmentation, dataset export for the Student, deploy and route, and production monitoring.

## 5. Data records

- `RawFile`: `raw_hash`, `path`, `format_detected`, `bytes`; never modified, never committed.
- `Trace`: `trace_id`, `raw_hash`, `ingest_version`, `source`, `turns`, `tool_calls` (name, args, result, latency, `error: {class, payload, encoding, classified_by}` with the D67 classes), `tools_declared` (the `tools` list as sent, when present), `system_prompt`, `hash`; every field carries a `raw_ptr` (file, offset) to where it came from.
- `ToolSig`: `name`, `args_schema`, `result_schema` (union of every observed field, each with `count`, `first_seen`, `last_seen`, `declared`; D72), `kind: read | write | generic`, `kind_confidence, unclassified (D70: read by default, flagged for review)`, `kind_reason`, `effects_observed: [(trace_id, field)]`, `error_shapes`, `evidence: [trace_id]`, `evidence_strength` (observed call count, error count), `source: observed | llm`.
- `EntitySchema`: `tables`, `columns` with `class: exempt | hard | semantic` (code proposes by rule with evidence, LLM verifies per column, re-runs override; `class_rule`, `class_confidence`, `class_reason`, `classified_by: rule | llm | observed | human`; D73), `id_patterns`, `synthetic_rows: [row_id]`.
- `Constraint`: `id`, `text`, `span` (trace or policy location), `predicate_src`, `tests: {pos, neg}`, `compiled`, `residual_reason`.
- `UserRules`: `facts` (field, value, span), `disclosure` (what is given only on request), `refusals`, `walk_away`, `style_sample: [trace_id]`.
- `Environment`: `env_id` (hash of the five files, schema, constraints), `schema_version`, `tools_version`, `policy_version` (D97, per R29), `version`, `parent_env_id`, `assisted_tools: [name]`.
- `TaskOverlay`: `task_id`, `rows: [(table, id, version_hash, trace_id)]` pinned from the Task's own Runs (D74); read before the shared `db.json`.
- `Verifier`: `task_id`, `atoms` each with `kind: required | allowed | forbidden | question | communicate | hard`, `provenance`, `spans`, `predicate_src`; `verifier_version`.
- `Run`: `run_id`, `env_id`, `trace_id`, `task_id`, `model`, `seed`, `user_rules`, `events`, `end_state_hash`, `termination_reason`, `cost`, `route_counts`, `assisted: bool`, `parent_run_id`.
- `Event`: `idx`, `ts`, `type: model_call | tool_call | tool_result | user_turn | error | stop`, `payload`, `route: code | recording | llm`, `cache_key`.
- `RunnerVersion`: content hash of `loop.py`, `route.py`, `verdict.py`, routing config; written by `freeze-runner`.
- `Verdict`: `run_id`, `env_id` with its three sub-versions (D97), `verifier_version`, `verdict_version`, `runner_version`, `pass`, `failing_atom`, `same_path`, `class: pass | fail | transferred_without_acting | env_error`, `judge_used: bool`.
- `GateResult`: `stage`, `pass`, `metrics`, `failures`.

One JSONL per Run, one JSON per Environment version, one JSON per Verifier version, one JSON per Verdict.

## 6. Stages and their gates

| Stage | LLM or code | Gate (code) | On failure |
|-------|-------------|-------------|------------|
| ingest | code | every tool call has a parseable result or error; hashes stable across two runs; grader fields stripped | reject trace with reason |
| mine | code; LLM only for missing result schemas | each `ToolSig` has at least 3 observed calls or is flagged `llm`; recorded args validate against the schema | flag, do not synthesize |
| compile tools | LLM body, code signature | six gates in order so a failure localizes (EvoEnv): parses; executes on S0; deterministic across two runs; non-trivial (does not return a constant where the recorded tool did not, D114); replay of held-out recorded calls (30 to 50 per tool, D51): hard columns match, errors match by shape, success and error fidelity reported separately (R22 item 8); refuses an unknown reference on a write tool (the refusal probe, D114). A call that follows a write on the same row in its own trace is not gate evidence (D74, D114) | one bounded repair round with the failing gate and diff, then mark the tool `recording-only` |
| compile policy | LLM predicate, code tests | positive and negative tests pass; every Reference's own path is reachable (no gold-violates-policy, R22 1.5) | constraint to `residual`, never into a Verdict |
| build Environment | code | tau2 shape loads in tau2's harness; `db.json` holds every id the traces reference; synthetic rows tagged | fail build |
| derive vocabulary | code; LLM lists ask words off fetched pages | every field has a source in the corpus; a web alias appears on a fetched page; never fails (D115) | field left with its name as its only cue |
| build user rules | code; LLM utterances | a disclosure rule for every fact the agent asked; a refusal branch where the trace shows one; fact consistency check on re-run (D44) | Run flagged `user_rules_incomplete`, still runnable, Verdict not counted |
| Gate A, oracle replay | code | replaying the Reference's own calls reaches its End state: writes 100% after canonicalization, semantic read mismatches 0, on seed and held-out Runs separately (D39, D51) | Environment rejected for that Task |
| derive Verifier | code over k re-runs; LLM for Provenance classification, audited | oracle passes, null agent fails, the Reference cut one step short fails (D119), alternative-path re-rolls pass, mutation of any hard atom flips the Verdict, leakage grep clean (step 8) | Task not verdicted, "Verifier immature" |
| setup review | human (ours, then customer) | prominent Tasks by D36 priority (D48 check 1) | Task marked "setup not reviewed" |
| Candidate runs | LLM | k runs per Run, fixed seeds, complete JSONL each | retry on infrastructure error only |
| verdict | code | golden files: oracle Run passes, empty Run fails, plausible-wrong fails, two valid orders both pass | block that verdict version |
| audit | human, blind | sample per Task, agreement published (D48 check 2) | Task to "under review" |
| regrade | code | env, verifier, verdict and runner versions on every Verdict; environment regrade re-runs the Builder gates on a new Environment version without touching stored Runs | none |

## 7. LLM versus code

LLM, always with its output validated by a code gate: tool function bodies, policy predicate proposals, missing result schemas, Provenance classification (audited like the Intent), Simulated user utterances, the loophole-probe agent, the Candidates under test, and the Reference-confirmation judge with abstain to human (D57).

Code, without exception: every gate, routing, hashing, canonicalization, diffing, the Verdict, persistence, and every description or schema the model sees.

## 8. Caching

- Model calls: content-addressed on (model, messages, tools, config, seed, epoch), Inspect's key; makes regrade and re-verdict free.
- Recorded tool results: keyed by (tool, canonical args, pre-state hash), so the recording route is an exact lookup and a stale recording cannot answer a changed state.
- Stage outputs: keyed by (input record hash, code hash of the stage module).
- Nothing keyed by wall-clock time or run order.

## 9. Testing

- Golden files: three anonymized traces (one tau2 retail, one OTel-format, one self-generated with real errors), with their expected `ToolSig`, Environment files, and Verdicts checked in. Any output change then shows up as a diff.
- Offline models: `TestModel` scripted, `RecordedModel` replaying a stored Run; `ALLOW_MODEL_REQUESTS=False` in CI.
- Verdict invariants: oracle Run passes, empty Run fails, plausible-wrong Run fails, two different valid orders both pass, a skipped required question fails (D43), a different wording of an allowed value passes (D42).
- Replay fidelity per generated tool on held-out calls, in CI against the checked-in traces.
- One end-to-end test: ingest, build, oracle replay, one Candidate run with `RecordedModel`, verdict, regrade, on a 20-call trace, under 30 seconds.

## 10. Size

## 11. The first slice, concretely (D55)

Input: tau2 retail trajectories from Sierra's public S3 bucket (R23 rank 1; Claude 3.7 retail file, about 25 MB), with grader fields stripped at ingest.

1. `ingest` the retail file. Gate: every call parsed, hashes stable. Done when: the printed count of Runs and tool calls matches a hand count on 3 Runs.
2. `mine`. Done when: every retail tool has a `ToolSig` with `source: observed`, and the schemas validate against tau2's real `tools.py` signatures (this is the one place we have the ground truth).
3. `compile_env` and `policy`. Done when: the five files load in tau2's harness, and each generated tool passes replay fidelity on 30 held-out recorded calls.
4. Gate A on seed and held-out Runs. Done when: writes hit 100%, semantic reads hit 0, and the held-out number is reported beside the seed number.
5. `verifier` for one Task (the cancel-pending-order Task, tau2 retail 38 and 36, R19). Done when: the oracle passes, the null case fails, the mutation test flips, and the sidecar shows Provenance for every written value.
6. Runner with one cheaper model in our rebuild (the official tau2 files hold gpt-4.1-mini and o4-mini Runs; R21). Done when: k=4 JSONL files per Run exist and route counts show zero LLM stand-ins.
7. `verdict` and comparison with tau2's reward per Run. Done when: agreement is reported, with every disagreement labeled either "by decision" (D42, D43, D45 cases) or "unexplained", and the unexplained rate is the number we discuss.
8. `regrade` after one deliberate Environment fix. Done when: stored Runs re-score without re-execution.

Then the same eight steps run on the OTel-format copy of the same trajectories (Exgentic, R23 rank 2), which must produce the same `env_id`. That's the first generalizability check on the ingestion path.

## 12. Harness engineering from first principles (Lilian Weng, 2026-07-04, and what is different for us)

Weng's definition: the harness is "the system surrounding a base model that orchestrates execution and decides how the model thinks and plans, calls tools and acts, perceives and manages context, stores artifacts, and evaluates results." Her post is about harnesses that improve the agent they wrap. Ours wraps two things that are not ours: a customer's recorded agent and a Candidate model. That single difference decides most of the design.

1. **The Runner is frozen; the Builder may learn.** Weng's whole second half treats the harness as an optimization target (ACE, Meta-Harness, Self-Harness, AHE, DGM). For the Runner, that's exactly wrong: the frontier and the Candidate must get the same tools, descriptions, error text, user rules, and context handling, or the gap we report becomes a harness gap, not a model gap (R24 disagreement 7, arXiv 2606.25447). For the Builder, it's exactly right: every Gate A failure, every unexplained Verdict disagreement, and every audit disagreement is a failure pattern. The Builder's editable surface (tool bodies, policy predicates, canonicalizer rules, user rules) can improve through a propose, validate on held-out, accept loop (Self-Harness, AHE). That's how the Builder gets better across customers without a human rewriting it.
2. **The evaluator sits outside the loop.** Weng writes: "Evaluator and permission control should likely sit outside the loop that evolves harness, with held-out tests, trace audits, and human review at decision points." In ours, Gate A, the Verdict invariants, the held-out Runs (D51), and the two human checks (D48) are never editable by the Builder's improvement loop. We adopt AHE's rule verbatim: the runs directory, tracer, verifier, and LLM config are read-only (principle 10).
3. **The file system is the memory; the log is the state.** Weng's pattern 2 ("keep durable state in files") and AHE's component observability (every editable component is a file) already match our shape: one JSONL per Run, one JSON per Environment, Verifier, and Verdict version, and `tools.py`, `policy.md`, and user rules as files a reviewer can open in the setup check.
4. **Observability before optimization.** AHE names the bottleneck as knowing which component caused a failure. Our failing atom (D46), the route on every event (D49), the per-tool assisted share, and the seed-versus-held-out fidelity split give us that observability, and they exist before any Builder self-improvement is attempted.
5. **Diversity collapse and reward hacking are Builder risks, not Runner risks.** A Builder loop that optimizes Gate A will learn to make Environments that just replay recordings (100% strict reads, flagged in D39), unless held-out Runs and the "unexplained disagreement" number are the actual objective. Weng warns that "a self-improvement loop optimizes whatever signal it is given", which is why the objective is agreement with the customer's verdicts on held-out Runs, never fidelity on seed Runs.
6. **Humans move up the stack.** Weng writes: "Humans should move up the stack, not be removed from the loop." Our two checks sit at the level of the checklist and the sample verdict, not at individual tool calls.
7. **Founder's principles for the Builder (D63, D64, D65).** (1) No Builder model call exceeds 40% of its window, including the evaluator's own calls; a call that would is refused, not compacted. (2) Keep it minimal and compact. (3) Load tools, prompts, and records only when needed and drop them after; the improvement agent greps the runs directory instead of reading it all into context. (4) The model studies its failures and proposes edits to prompts, tools, middleware, and memory; Builder history is a tree of versions with scorecards, and an evaluator outside the loop decides what stays. None of this applies to the Candidate under test, which always runs under the production setting.
8. **How the Builder improves, concretely (R25).** There are three mechanisms, all on the Builder side, none touching `loop.py`, `route.py`, or `verdict.py`. (a) Failure patterns from Gate A, unexplained Verdict disagreements, and audit disagreements get read and turned into edits of the Builder's prompts, checklists, gates, and seed corpus (Agent-World's diagnosis agent shape); each edit is paired with a prediction checked on the anchor sample next round (AHE decision observability). (b) The anchor sample of held-out real Runs must keep passing, so the Builder can't drift while chasing an internal number. (c) A monthly ablation (learn-harness-engineering lecture 12) disables one gate or strategy, re-runs the anchor and the audit sample, retires what doesn't change quality, and keeps or replaces what does. Stop condition: D62.
9. **What we don't take from the post.** Sub-agents and parallel hypothesis search (pattern 3), context engineering machinery (ACE, MCE), and evolutionary search over harness code are meant for agents doing open-ended work. The Runner is a 150-line loop on purpose. The Builder's improvement loop, when it arrives, will be bounded edits with held-out validation (Self-Harness shape), not evolutionary search.
