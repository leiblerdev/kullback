# Harness design: Builder and Runner

Status: proposal for grilling, 2026-08-27, revised after R25 (principles re-derived from environment-generation pipelines, D61). Terms from `/CONTEXT.md` (Harness, Builder, Runner, Environment, Run, Verifier, Verdict, Simulated user, Provenance, Assisted). Decisions cited as D-numbers from `decision-log.md`; research as R-numbers from `../research/`. This document is the answer to "get back to me with design recommendations"; every section is open to challenge.

Founder's philosophy, verbatim: "it should be simple enough and gets the job done in high quality", "as efficient and simple as possible", "care much more about generalizability than the overfitting".

## 1. What the Harness is, in one paragraph

Two programs over one set of data records. The **Builder** reads a customer's traces and writes an Environment (state, tools, Hard constraints, Simulated user rules) plus one Verifier per Task, in tau2's file shape first (D56). The **Runner** takes an Environment, a Run and a Candidate model, executes the agent loop with every tool call routed to code, recording, or LLM stand-in (D49), writes one JSONL file per Run, and a separate pass computes the Verdict from that file by code alone (D43, D46). Nothing else is persisted; nothing decides without a code gate.

## 3. Shape: three layers, two programs

Tau's cut, "separate the brain, the environment, and the face" (D53):

- **Brain**: `Model.query(messages, tools) -> Message`. One class, three implementations: a live provider, `RecordedModel` (replays a stored Run's model outputs), `TestModel` (scripted tool calls for tests). Nothing else in the code knows which provider is behind it.
- **Environment**: the tool list, built as a capability seam (DeepSeek Harness): the **Service Definition** is the tool's `name, description, parameters`, copied from the traces and never changed by the Builder; the **Providers** are SQLite code, the recording, and the LLM stand-in, tried in that order; the **Consumer** is the one tool the Candidate sees. The Runner is frozen at the Service Definition; the Builder improves Providers. Hard constraints are checked in the seam before a write lands. The Simulated user is a message source on the same footing as a tool result.
- **Face**: the report reads JSONL and Verdict files. No UI code touches the core.

Dependency direction: `report -> runner -> records <- builder`. The Builder and the Runner share only `records.py`. The Candidate's context is always the production setting: the system prompt, tool definitions and conversation the customer's agent gave it, with production's own compaction if the traces show one; the Harness never caps or compacts it (D65). Two runtime invariants, asserted in code: **model-visible means logged** (every prompt the Candidate received is reconstructable from the Run's events), and **Runner frozen** (`RunnerVersion` = hash of `loop.py`, `route.py`, `verdict.py` and the routing config; a Verdict carries it; a comparison across two `RunnerVersion`s is refused).

## 4. Modules, one file each, one sentence each

Builder:

1. `records.py`: the data records in section 5, Pydantic, round-trip through JSON, nothing else.
2. `ingest.py`: stores the customer's files byte for byte, content-hashed, as the source of truth (D66), then derives `Trace` records from them with a raw pointer (file, offset) on every field, re-derivable whenever the schema grows; maps a customer export (tau2 native, OpenTelemetry GenAI in both dialects, Claude Code JSONL; R23) into `Trace` records with content hashes; strips benchmark grader fields (`reward_info`, `task_id`, `action_checks`, `nl_assertions`, trial ids) before anything else reads the trace; normalizes tool errors into the D67 taxonomy plus verbatim payload (code for flagged sources, rules then LLM for string-only sources, `classified_by` recorded); marks truncated results with the visible length and cut marker, the Builder reconstructs the rest from the result schema and complete calls, tagged, and such calls stay Assisted until the customer supplies the full result (D95); pure code except the error-classification and reconstruction passes.
3. `mine.py`: `ToolSig` (name, argument schema, result schema, read or write decided by an LLM over code-gathered context with observed effects overriding it, D68, observed error classes) and `EntitySchema` (tables, columns with class exempt, hard, or semantic, id patterns) from the traces; one LLM call per tool whose result schema cannot be inferred from observed results, marked `source: llm`.
4. `compile_env.py`: writes `data_model.py`, `tools.py`, `db.json`, `policy.md`, `tasks.json` (D56); one shared `db.json` per customer by inverse replay over the whole corpus (D33), latest observation wins in the shared rows, plus a per-Task overlay of the rows that Task's Runs touched in the version they saw (D74; overlay lookup in `route.py`, never in tool bodies; overlays merged only when emitting for tau2's harness and a conflict there is a Gate failure) plus tagged synthetic rows for reads (D40, D41); LLM writes each tool body, code writes signature, docstring and schema. A body that fails a gate is rewritten at most three times with growing evidence (failing call, all failing calls, full call table), each attempt a Builder tree node; every rewrite is re-checked against all recorded calls with a held-out split, and after three misses the tool is assisted (D75).
5. `policy.py`: policy and system-prompt sentences into `Constraint` records, each a before-write predicate in Python with one positive and one negative test; sequence rules ("never write X without a prior user confirmation") are predicates over the transcript (D43 case 3); an uncompilable rule is first rewritten into a checkable form for the setup review (original beside it); if it still cannot be code, it becomes a judge atom evaluated by `judge.py`; a rejected rule goes to `residual` and is reported as not checked (D76).
6. `user_sim.py`: per-Run Simulated user rules from the trace (facts exact, style representative, D44): disclosure rules for every fact the agent asked for, refusals and walk-away branches where the trace shows them; a fact the Candidate asks for that the trace lacks is answered from the Task's Starting state as that user, and when the world lacks it too the Simulated user says so and the event is tagged `fact_unavailable` (D77); the LLM only fills utterances; rules are data in the `Run` record.
7. `cluster.py`: groups Runs into Categories by write-tool signature (code), then into Tasks by Intent similarity inside each Category (D83); output is a `Task` record listing its Run ids; an LLM only names the cluster, code decides membership; a Run that fits no cluster becomes its own Task rather than being forced in.
8. `intent.py`: writes the one-line grounded Intent per Task (step 6, D47): every noun phrase must point to a span in a member Run (a tool argument, a user utterance or a written value); the cross-family grounding check refuses an Intent whose spans come from one Run only; the Intent is what the customer sees as the Task name and what `verifier.py` derives from.
9. `canon.py`: the canonicalizer (D39) as its own module with its own tests: numbers (`25` vs `25.0`), whitespace and case, timestamps, id formats, list order where order is not meaningful; used by `route.py` for recording lookup and by `verdict.py` for atom comparison, so both sides agree by construction; rules are data, learned per customer from the traces and reviewed in the setup check. `semantic` columns whose canonical strings differ go to `judge.py`, and the (column, a, b, verdict) result is cached in a per-customer equivalence table that reviewers can overturn, triggering a regrade (D84).
10. `verifier.py`: the atoms for one Task from confirmed References (step 7): write-set diff over successful re-runs, Provenance per value (D42), required vs allowed by re-run agreement (D43) over k frontier re-runs, k from config and chosen by the D78 experiment, questions asked as atoms, communicate facts, Hard constraints, entity-count check; written to the sidecar next to `tasks.json` and exported into `evaluation_criteria.actions` for tau2's harness.

Runner:

11. `loop.py`: a `step(run) -> run` function that advances one turn (`msg = model.query(messages, tools); calls = parse(msg); results = [route(c) for c in calls]; messages += ...`) and a `run()` that calls it until stop, one JSONL line per event; 100 to 150 lines (mini-swe-agent shape); written this way so the OpenEnv wrapper is mechanical later (D90).
12. `route.py`: code, then recording (exact match on tool, canonical args, pre-state hash), then LLM stand-in; the route taken is on the event; any stand-in marks the Run Assisted (D49); a bad call is answered in the customer's error encoding (D45).
13. `verdict.py`: reads a Run's JSONL and the Task's Verifier; canonicalizes (D39); checks required atoms, allowed atoms, forbidden writes, questions asked, communicate facts, Hard constraints fired, side-effect count; emits pass or fail with the failing atom and same-path or different-path (D46) and the class `transferred_without_acting` where it applies; never calls a model itself, combines `judge.py` results for judge atoms and sets `judge_used` (D76).
13b. `judge.py`: the agentic judge (D92): two judges (different models or personas), each with read tools over the Starting state and End state and the Verifier's output, at least one tool check before a verdict, cited spans; used for judge atoms (D76), semantic equality (D84), failure cause (D88), Reference confirmation (D57) and the dispute path; disagreement between the two goes to a queue listed in the report, never blocks a build; the disagreement rate travels with every result, the audit rate beside it once a person has resolved queue items.
14. `regrade.py`: re-runs `verdict.py` over stored Runs against a new Environment or Verifier version without re-executing (tau3 `--fresh-tasks`).
15. `validate.py`: the gates in section 6, each a function returning `GateResult`.
16. `pipeline.py`: content-addressed, idempotent stage runner, modeled as a graph with one explicit rollback edge (a failed gate returns the artifact to its generating stage with the failure summary, logged as an edge traversal: "attempt 2 of 3, gate replay_fidelity failed") and one anchor: a fixed share of every Task's Runs (20%, at least one, Tasks under three Runs marked unguarded; D81) held out and never touched by the Builder, which must keep replaying, so Builder iteration cannot drift from the customer's production behavior.
17. `cli.py`: `ingest`, `build --iterate`, `freeze-runner`, `run`, `verdict`, `regrade`, `report`; `build --iterate` is expected to run often and change; `freeze-runner` writes the `RunnerVersion` and asks for confirmation; every command reads and writes records on disk; no hidden state.

Shared by both (D69):

18. `report.py`: the face; one Markdown or JSON report per Environment build and per Run batch, opening with whether the Environment was built (Gates, scorecard raw and explained, assisted tools, unguarded Tasks, overlay counts) and ending each Task with numbers then a suggestion, the decision being the person's (D85): scorecard (D62), Gate results, per-Task Verdicts with the failing atom and same-path or different-path (D46), assisted share per tool (D49), Task names with the customer's corrections (D47), cost per stage; reads records, never computes a Verdict.
19. `budget.py`: cost and token accounting; every model call records provider, model, input and output tokens, cache reads, price and wall time on the event; per-stage and per-Environment totals; enforces the 40% context cap on Builder calls (D65) by refusing the call, and a per-build spend ceiling: at the ceiling the Builder stops where it is, reports as is (stage, item, cost so far, cost to finish), and resumes only with a person's permission and a new ceiling (D86).
20. `provider.py`: `Model.query(messages, tools) -> message` behind one interface with adapters for Anthropic, OpenAI and OpenAI-compatible local endpoints (R26, from OpenCode): model id as `provider/model` with a separate wire id and base URL per model, base URL from config with `${VAR}` substitution; keys from environment; retry only on 5xx, network errors and rate limits with `Retry-After` honored, exponential backoff with jitter, five attempts, never on context overflow; three defensive normalizations (drop empty messages and empty reasoning parts for Anthropic, tool-call ids restricted to `[a-zA-Z0-9_-]`, strip unpaired surrogates); prompt-cache points on the system messages and the last two non-system messages; three explicit reasoning branches, no effort tables; usage (input, output, cache read, cache write) returned on every call for `budget.py`; no live model registry, no output clamp (the Runner uses the recorded `max_tokens`); 250 to 400 lines.
21. `memory.py`: the Builder's memory for its improvement loop (D63, D64): a tree of Builder versions, each node a set of files (prompts, checklists, gate thresholds, canonicalizer rules, tool-writing instructions) plus its scorecard on the anchor sample; failure notes written by the improvement agent after each build; a cross-customer lessons file (pattern, fix, confirming anchor result, relevance condition; no customer data, anonymization gate on save) that the Builder reads at build start and must judge lesson by lesson for relevance to this customer's traces, with set-aside lessons listed in the report (D87); the tree is grepped, never loaded whole (D65).

The Builder can modify itself (D69): the improvement agent may edit any file under the Builder's own directory (its prompts, `mine.py`, `compile_env.py`, `policy.py`, `user_sim.py`, `intent.py`, `cluster.py`, `canon.py` rules), commits the edit as a new node in `memory.py`'s tree, and the evaluator outside the loop (D64) accepts or rejects it on the anchor sample and held-out Runs. Read-only for the improvement agent: `loop.py`, `route.py`, `verdict.py`, `validate.py`, `budget.py`, the runs directory, the raw store, and the evaluator itself (Weng, AHE; section 12 items 1 and 2).

Deliberately absent: an event bus, a plugin system, MCP inside the core, subagents, a UI framework, session trees for Runs (a fork is a new Run with `parent_run_id`; the Builder's tree lives in `memory.py`). Deferred to `todo.md` (D69): Filter and Screen, Reference confirmation as a module (the tau2 slice uses tau2's own references), the dispute path, the statistics module, a sandbox for model-written tool code, anonymization, secrets handling, a cache store beyond content-addressed files, a review UI, scenario generation and seed augmentation, dataset export for the Student, deploy and route, production monitoring.

## 5. Data records

- `RawFile`: `raw_hash`, `path`, `format_detected`, `bytes`; never modified, never committed.
- `Trace`: `trace_id`, `raw_hash`, `ingest_version`, `source`, `turns`, `tool_calls` (name, args, result, latency, `error: {class, payload, encoding, classified_by}` with the D67 classes), `tools_declared` (the `tools` list as sent, when present), `system_prompt`, `hash`; every field carries a `raw_ptr` (file, offset) to where it came from.
- `ToolSig`: `name`, `args_schema`, `result_schema` (union of every observed field, each with `count`, `first_seen`, `last_seen`, `declared`; D72), `kind: read | write | generic`, `kind_confidence, unclassified (D70: read by default, flagged for review)`, `kind_reason`, `effects_observed: [(trace_id, field)]`, `error_shapes`, `evidence: [trace_id]`, `evidence_strength` (observed call count, error count), `source: observed | llm`.
- `EntitySchema`: `tables`, `columns` with `class: exempt | hard | semantic` (code proposes by rule with evidence, LLM verifies per column, re-runs override; `class_rule`, `class_confidence`, `class_reason`, `classified_by: rule | llm | observed | human`; D73), `id_patterns`, `synthetic_rows: [row_id]`.
- `Constraint`: `id`, `text`, `span` (trace or policy location), `predicate_src`, `tests: {pos, neg}`, `compiled`, `residual_reason`.
- `UserRules`: `facts` (field, value, span), `disclosure` (what is given only on request), `refusals`, `walk_away`, `style_sample: [trace_id]`.
- `Environment`: `env_id` (hash of the five files, schema, constraints), `schema_version`, `tools_version`, `policy_version` (D97, per R29), `version`, `parent_env_id`, `assisted_tools: [name]`.
- `TaskOverlay`: `task_id`, `rows: [(table, id, version_hash, trace_id)]` pinned from the Task's own Runs (D74); read before the shared `db.json`.
- `Verifier`: `task_id`, `atoms` each with `kind: required | allowed | forbidden | question | communicate | hard`, `provenance`, `spans`, `predicate_src`; `verifier_version`.
- `Run`: `run_id`, `env_id`, `trace_id`, `task_id`, `model`, `seed`, `user_rules`, `events`, `end_state_hash`, `termination_reason`, `cost`, `route_counts`, `assisted: bool`, `parent_run_id`.
- `Event`: `idx`, `ts`, `type: model_call | tool_call | tool_result | user_turn | error | stop`, `payload`, `route: code | recording | llm`, `cache_key`.
- `RunnerVersion`: content hash of `loop.py`, `route.py`, `verdict.py`, routing config; written by `freeze-runner`.
- `Verdict`: `run_id`, `env_id` with its three sub-versions (D97), `verifier_version`, `verdict_version`, `runner_version`, `pass`, `failing_atom`, `same_path`, `class: pass | fail | transferred_without_acting | env_error`, `judge_used: bool`.
- `GateResult`: `stage`, `pass`, `metrics`, `failures`.

One JSONL per Run, one JSON per Environment version, one JSON per Verifier version, one JSON per Verdict.

## 6. Stages and their gates

| Stage | LLM or code | Gate (code) | On failure |
|-------|-------------|-------------|------------|
| ingest | code | every tool call has a parseable result or error; hashes stable across two runs; grader fields stripped | reject trace with reason |
| mine | code; LLM only for missing result schemas | each `ToolSig` has at least 3 observed calls or is flagged `llm`; recorded args validate against the schema | flag, do not synthesize |
| compile tools | LLM body, code signature | five gates in order so a failure localizes (EvoEnv): parses; executes on S0; deterministic across two runs; non-trivial (does not return a constant); replay of held-out recorded calls (30 to 50 per tool, D51): hard columns match, errors match by shape, success and error fidelity reported separately (R22 item 8) | one bounded repair round with the failing gate and diff, then mark the tool `recording-only` |
| compile policy | LLM predicate, code tests | positive and negative tests pass; every Reference's own path is reachable (no gold-violates-policy, R22 1.5) | constraint to `residual`, never into a Verdict |
| build Environment | code | tau2 shape loads in tau2's harness; `db.json` holds every id the traces reference; synthetic rows tagged | fail build |
| build user rules | code; LLM utterances | a disclosure rule for every fact the agent asked; a refusal branch where the trace shows one; fact consistency check on re-run (D44) | Run flagged `user_rules_incomplete`, still runnable, Verdict not counted |
| Gate A, oracle replay | code | replaying the Reference's own calls reaches its End state: writes 100% after canonicalization, semantic read mismatches 0, on seed and held-out Runs separately (D39, D51) | Environment rejected for that Task |
| derive Verifier | code over k re-runs; LLM for Provenance classification, audited | oracle passes, null agent fails, alternative-path re-rolls pass, mutation of any hard atom flips the Verdict, leakage grep clean (step 8) | Task not verdicted, "Verifier immature" |
| setup review | human (ours, then customer) | prominent Tasks by D36 priority (D48 check 1) | Task marked "setup not reviewed" |
| Candidate runs | LLM | k runs per Run, fixed seeds, complete JSONL each | retry on infrastructure error only |
| verdict | code | golden files: oracle Run passes, empty Run fails, plausible-wrong fails, two valid orders both pass | block that verdict version |
| audit | human, blind | sample per Task, agreement published (D48 check 2) | Task to "under review" |
| regrade | code | env, verifier, verdict and runner versions on every Verdict; environment regrade re-runs the Builder gates on a new Environment version without touching stored Runs | none |

## 7. LLM versus code

LLM, always with its output validated by a code gate: tool function bodies, policy predicate proposals, missing result schemas, Provenance classification (audited like the Intent), Simulated user utterances, the loophole-probe agent, the Candidates under test, and the Reference-confirmation judge with abstain to human (D57).

Code, without exception: every gate, routing, hashing, canonicalization, diffing, the Verdict, persistence, and every description or schema the model sees.

## 8. Caching

- Model calls: content-addressed on (model, messages, tools, config, seed, epoch), Inspect's key; makes regrade and re-verdict free.
- Recorded tool results: keyed by (tool, canonical args, pre-state hash), so the recording route is an exact lookup and a stale recording cannot answer a changed state.
- Stage outputs: keyed by (input record hash, code hash of the stage module).
- Nothing keyed by wall-clock time or run order.

## 9. Testing

- Golden files: three anonymized traces (one tau2 retail, one OTel-format, one self-generated with real errors) with their expected `ToolSig`, Environment files and Verdicts checked in; any output change shows as a diff.
- Offline models: `TestModel` scripted, `RecordedModel` replaying a stored Run; `ALLOW_MODEL_REQUESTS=False` in CI.
- Verdict invariants: oracle Run passes, empty Run fails, plausible-wrong Run fails, two different valid orders both pass, a skipped required question fails (D43), a different wording of an allowed value passes (D42).
- Replay fidelity per generated tool on held-out calls, in CI against the checked-in traces.
- One end-to-end test: ingest, build, oracle replay, one Candidate run with `RecordedModel`, verdict, regrade, on a 20-call trace, under 30 seconds.

## 10. Size

`loop.py` 100 to 150; `route.py` under 100; `verdict.py` 200 to 300; `records.py` 150 to 200; `pipeline.py` plus `validate.py` 250 to 350; `compile_env.py` plus `policy.py` 400 to 500; `mine.py` plus `ingest.py` 300 to 400; `user_sim.py` 150 to 200; `verifier.py` 200 to 300; `cli.py` under 150. About 2,000 to 2,700 lines, Tau's core plus tau2's evaluator in size, generated Environment bundles not counted. Past 3,000 lines, the first cuts are the LLM stand-in route and the residual policy list, never a gate.

D69 adds seven modules (`cluster`, `intent`, `canon`, `report`, `budget`, `provider`, `memory`), roughly 700 to 1,000 lines, so the whole is 2,700 to 3,700 lines. `canon.py` and `budget.py` are small; `provider.py` and `memory.py` carry most of it.

## 11. The first slice, concretely (D55)

Input: tau2 retail trajectories from Sierra's public S3 bucket (R23 rank 1; Claude 3.7 retail file, about 25 MB), with grader fields stripped at ingest.

1. `ingest` the retail file; gate: every call parsed, hashes stable. Done when: count of Runs and tool calls printed and matches a hand count on 3 Runs.
2. `mine`; done when: every retail tool has a `ToolSig` with `source: observed`, and the schemas validate against tau2's real `tools.py` signatures (we have the truth here and nowhere else).
3. `compile_env` and `policy`; done when: the five files load in tau2's harness, and each generated tool passes replay fidelity on 30 held-out recorded calls.
4. Gate A on seed and held-out Runs; done when: writes 100%, semantic reads 0, and the held-out number is reported beside the seed number.
5. `verifier` for one Task (the cancel-pending-order Task, tau2 retail 38 and 36, R19); done when: oracle passes, null fails, the mutation test flips, and the sidecar shows Provenance for every written value.
6. Runner with one cheaper model (official tau2 files hold gpt-4.1-mini and o4-mini Runs; R21) in our rebuild; done when: k=4 JSONL files per Run exist and route counts show zero LLM stand-ins.
7. `verdict` and comparison with tau2's reward per Run; done when: agreement is reported with every disagreement labeled either "by decision" (D42, D43, D45 cases) or "unexplained", and the unexplained rate is the number we discuss.
8. `regrade` after one deliberate Environment fix; done when: stored Runs re-score without re-execution.

Then the same eight steps on the OTel-format copy of the same trajectories (Exgentic, R23 rank 2), which must produce the same `env_id`; that is the first generalizability check on the ingestion path.

## 12. Harness engineering from first principles (Lilian Weng, 2026-07-04, and what is different for us)

Weng's definition: the harness is "the system surrounding a base model that orchestrates execution and decides how the model thinks and plans, calls tools and acts, perceives and manages context, stores artifacts, and evaluates results." Her post is about harnesses that improve the agent they wrap. Ours wraps two things that are not ours: a customer's recorded agent and a Candidate model. That single difference decides most of the design.

1. **The Runner is frozen; the Builder may learn.** Weng's whole second half treats the harness as an optimization target (ACE, Meta-Harness, Self-Harness, AHE, DGM). For the Runner that is exactly wrong: the same tools, descriptions, error text, user rules and context handling must be given to the frontier and to the Candidate, or the gap we report is a harness gap, not a model gap (R24 disagreement 7, arXiv 2606.25447). For the Builder it is exactly right: every Gate A failure, every unexplained Verdict disagreement, every audit disagreement is a failure pattern, and the Builder's editable surface (tool bodies, policy predicates, canonicalizer rules, user rules) can be improved by a propose, validate on held-out, accept loop (Self-Harness, AHE). That is how the Builder gets better across customers without a human rewriting it.
2. **The evaluator sits outside the loop.** Weng: "Evaluator and permission control should likely sit outside the loop that evolves harness, with held-out tests, trace audits, and human review at decision points." Ours: Gate A, the Verdict invariants, the held-out Runs (D51) and the two human checks (D48) are never editable by the Builder's improvement loop; AHE's rule that the runs directory, tracer, verifier and LLM config are read-only is adopted verbatim (principle 10).
3. **The file system is the memory; the log is the state.** Weng's pattern 2 ("keep durable state in files") and AHE's component observability (every editable component is a file) are already our shape: one JSONL per Run, one JSON per Environment, Verifier and Verdict version; `tools.py`, `policy.md`, user rules as files a reviewer can open in the setup check.
4. **Observability before optimization.** AHE names the bottleneck as knowing which component caused a failure. Our failing atom (D46), the route on every event (D49), the per-tool assisted share, and the seed-versus-held-out fidelity split are that observability, and they exist before any Builder self-improvement is attempted.
5. **Diversity collapse and reward hacking are Builder risks, not Runner risks.** A Builder loop that optimizes Gate A will learn to make Environments that replay recordings (100% strict reads, flagged in D39) unless held-out Runs and the "unexplained disagreement" number are the objective. Weng's warning that "a self-improvement loop optimizes whatever signal it is given" is why the objective is agreement with the customer's verdicts on held-out Runs, never fidelity on seed Runs.
6. **Humans move up the stack.** Weng: "Humans should move up the stack, not be removed from the loop." Our two checks are placed at the abstraction level of the checklist and the sample verdict, not at individual tool calls.
7. **Founder's principles for the Builder (D63, D64, D65).** (1) No Builder model call exceeds 40% of its window, the evaluator's calls included; a call that would is refused, not compacted. (2) Minimal and compact. (3) Tools, prompts and records are loaded when needed and dropped after; the improvement agent greps the runs directory instead of reading it into context. (4) The model studies its failures and proposes edits to prompts, tools, middleware and memory; Builder history is a tree of versions with scorecards; an evaluator outside the loop decides what stays. The Candidate under test is never subject to any of this: it runs under the production setting.
8. **How the Builder improves, concretely (R25).** Three mechanisms, all on the Builder side, none touching `loop.py`, `route.py` or `verdict.py`: (a) failure patterns from Gate A, unexplained Verdict disagreements and audit disagreements are read and turned into edits of the Builder's prompts, checklists, gates and seed corpus (Agent-World's diagnosis agent shape), each edit paired with a prediction checked on the anchor sample next round (AHE decision observability); (b) the anchor sample of held-out real Runs must keep passing, so the Builder cannot drift while chasing an internal number; (c) a monthly ablation (learn-harness-engineering lecture 12): disable one gate or strategy, re-run the anchor and the audit sample, retire what does not change quality, keep or replace what does. Stop condition: D62.
9. **What we do not take from the post.** Sub-agents and parallel hypothesis search (pattern 3), context engineering machinery (ACE, MCE), and evolutionary search over harness code are for agents that do open-ended work. The Runner is a 150-line loop on purpose; the Builder's improvement loop, when it comes, is bounded edits with held-out validation (Self-Harness shape), not evolutionary search.
